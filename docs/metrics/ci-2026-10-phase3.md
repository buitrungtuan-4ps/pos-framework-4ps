# CI after phase 3, October 2026

**Status** Accepted · **Owner** @maintainers-architecture · **Measured** 2026-10-13

What CI costs after phases 1 and 3 of the standardisation work
([ADR-0171](../adr/0171-ci-runs-what-a-change-affects.md)), measured against
[the baseline](baseline-2026-10.md) §2. This file records one moment. It is not regenerated, and a
later measurement goes in a file of its own.

## How it was measured

The figures come from the GitHub check runs of the pull requests that built phase 3, using each
one's last head commit. Each figure is a check run's `completed_at` minus its `started_at`. Runs
that GitHub skipped at job level are left out of the sums.

The terms in the tables mean:

- **Span:** from the first job's start to the last job's finish. This is how long a pull request waits for CI.
- **Longest job:** the single slowest job.
- **Job minutes:** the sum of all jobs. This is what the runners cost.

## What this shows

- **The span is set by a chain of jobs, not by one long job.** The chains are
  `changes` → `test-archive` → `test-shard`, and `changes` → `replay-build` → `replay-shard`.
  Each comes to about 5 minutes. The longest single job is now about 3–4 minutes, against the
  ~3-minute target; `console-replay` and `postgres` are the jobs at that ceiling.
- **Sharding did not add runner minutes.** Total runner minutes went down (38 to 33–34) even though
  there are more jobs, most likely because building once (#723, #724) compiles less than each job building
  its own; this was not measured separately.
- **A docs-only pull request is about 17 times faster than the baseline:** 0:34 against 9:28. This
  is the case the path classes (#720) were for.
