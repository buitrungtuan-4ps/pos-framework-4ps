# The first crates, October 2026

**Status** Accepted · **Owner** @maintainers-architecture · **Measured** 2026-10-15

This file records what the first crates of phase 6 cost and what they changed
([ADR-0170](../adr/0170-repository-layout-code-naming-and-size-rules.md) decision 4,
[plan](../plans/standardisation.md) row 6). Decision gate 2 is taken on these figures. The file
records one moment and is not regenerated; a later measurement goes in a file of its own.

## What phase 6 did so far

| Pull request | What it did | Size |
|---|---|---|
| #816 | The response helpers every area shares, and the record version, moved out of `pos-cloud/src/http.rs` and `version.rs` into `pos-cloud-api` | 12 files, +820/−694 |
| #817 | `pos-cloud-config`: the config tree, the publish every area writes through, the org registry, settings and QR ordering's switch, with their store impls | 40 files, +1,361/−1,029 |
| #818 | `pos-cloud-inventory`: the inventory, its routes and its store impl | 27 files, +524/−323 |
| #819 | `pos-cloud-devices`: activation, claims, device onboarding, their routes and store impls | 35 files, +1,121/−923 |

All four were move-only. No route, permission, event, setting, OpenAPI entry or snapshot changed.
The committed OpenAPI documents and snapshots were byte-identical before and after each one, and
the 1,153 tests of the cloud crates were the same 1,153 after each.

Before the crates, a boundary survey ranked the candidates by how much each one used from the rest
of its crate. It found two things:

- No cloud area could leave `pos-cloud` while the configuration base stayed inside it. Eight of
  the nine named areas publish through it.
- The edge's billing, shift and floor commands are inherent `impl Edge` blocks. Rust allows such
  blocks only in `Edge`'s own crate, so they cannot become crates by moving code.

Those findings set the order: the base first (#816, #817), then the two areas with no other area
in their way (#818, #819).

## How it was measured

- **Machine:** one machine with 4 cores, `CARGO_BUILD_JOBS=2`, no incremental compilation and no
  debug info, as CI builds (`CARGO_INCREMENTAL=0`, `CARGO_PROFILE_DEV_DEBUG=0`,
  `CARGO_PROFILE_TEST_DEBUG=0`). mold is not installed on this machine, so it was not used.
- **Two sides, two directories:**
  - "Before" is `main` at 4db130e, the commit #816 started from.
  - "After" is `main` at 51d39df, after #819.
  - Each side was built in its own worktree with its **own target directory**. A shared directory
    lets cargo reuse the other side's artefacts and silently corrupts the comparison.
  - Each side was warmed once (`cargo build -p pos-cloud` and `cargo test -p pos-cloud --no-run`)
    before any timed run.
- **The figures:** each one is the median of three runs, and each run follows a `touch` of one
  file. The three runs are in brackets. Other sessions on the machine may have overlapped some
  runs, so a difference inside the bracketed ranges is noise.
- **The files touched:**

  | Area | Before | After |
  |---|---|---|
  | Inventory route | `pos-cloud/src/http/inventory/recipes.rs` | `pos-cloud-inventory/src/routes/recipes.rs` |
  | Devices route | `pos-cloud/src/http/devices/terminals.rs` | `pos-cloud-devices/src/routes/terminals.rs` |
  | Configuration base | `pos-cloud/src/http/config_publish.rs` | `pos-cloud-config/src/publish.rs` |
  | Outside these areas | `pos-cloud/src/http/reason_codes/authoring.rs` | the same file |

## Findings

1. **The edit loop moved; the binary did not.**
   - A change inside an area now builds its crate in 1.0–1.9 s and builds that crate's tests in
     1.5–3.0 s.
   - Building `pos-cloud` takes what it took before, about 70 s, with ranges that overlap except
     for the inventory touch. Building its tests takes about 90 s.
   - This is the pilot's result again, three times over.
2. **The route tests still live in `pos-cloud`.** Every moved area's HTTP tests drive the whole
   router, so they stayed in `pos-cloud/tests/cloud.rs`. That is 444 tests, unchanged. Checking a
   route still means the 89–94 s test build, as pilot finding 3 found.
3. **`affected` widens, and the base widens it most.**
   - An area change runs one crate more than before.
   - A change to the configuration base runs four crates, because every area crate depends on it.
   - Each further area crate adds one more to that list.
4. **Adapter impls moved with their traits every time,** as pilot finding 1 said they would:
   - 442 lines into `pos-cloud-config`;
   - 269 into `pos-cloud-inventory`;
   - 376 into `pos-cloud-devices`.

   Each new crate depends on `store-postgres`.
5. **What a move needed besides the moves:**
   - Public items met clippy's pedantic lints: `#[must_use]` and `# Errors` sections, 59 lines in
     #817.
   - Doc links into `pos-cloud` were renamed as code: 4 in #817 and 7 in #819.
   - One test fixture was repeated across a crate boundary, because a dependency's
     `#[cfg(test)]` code is not compiled into other crates' tests.
   - The route-coverage tests had to read the area crates' route files. They read source files
     from disk, so a moved route looked unregistered until `ROUTE_CRATES` named its crate (#818).
6. **The cost per pull request.** The moves measured (the share of added lines that
   `git diff --color-moved` shows as moved) as follows:
   - #817: 920 of 1,213 added lines;
   - #818: 271 of 430;
   - #819: 839 of 1,043.

   The rest is manifests, module headers, imports and visibility. CI ran everything on each,
   because the manifests, the lockfile and `CODEOWNERS` changed.

## Recommendation for gate 2

**Continue, area by area, and only where the boundary is clean.** The figures behind this:

- **For continuing.** An area crate turns a 70–94 s edit loop into a 1–3 s one, and cuts what a
  change means reading by a factor of four to six. Each largest file goes from 4,116–5,750 lines to
  347–634. That is the outcome ADR-0170 decision 4 was taken for.
- **For caution.** `pos-cloud` builds no faster. CI runs more crates for every area change, and
  the base change now runs four. The move PRs were 524–1,361 lines each.
- **What decides the order.** The remaining areas do not have the clean boundaries inventory and
  devices had. Each extraction either needs another one first or needs edits that are not moves,
  as below.

### Edge billing, shift and floor

**The superseding ADR is needed now, before `pos-edge-app` starts.**

- The command code of all three is `impl<S: EventStore> Edge<S>` blocks:
  - `app/bills`: 10 files, 2,949 lines;
  - `app/shifts`: 9 files, 1,661 lines;
  - `app/floor.rs`: 343 lines.
- They are 29 inherent impl blocks across `app/` in all. Rust allows them only in `Edge`'s own
  crate (E0116).
- What `pos-edge-app` contains therefore depends on the decision: it holds these commands. Only
  their HTTP handlers could move further, and those handlers come to 1,078, 794 and 537 lines.

ADR-0170 decision 4 lists `pos-edge-billing`, `-shift` and `-floor` as crates. Starting the edge
crates without superseding that line would build against a list that cannot be met by moves.

## Decision gate 2

**Taken 2026-10-15 by the orchestrator, under the owner's standing approval of 2026-10-14:
continue, one area at a time, and only where the boundary is clean.**

- The edit loop inside an extracted area goes from 70–94 s to 1–3 s, and what one change means
  reading shrinks four to six times. Nothing on the wire, in the snapshots or in the test count
  changed.
- `pos-cloud` itself builds no faster, and CI runs more crates per change. Both are accepted.
- Before `pos-edge-app` starts, an ADR supersedes ADR-0170 decision 4's crate list where moves
  cannot meet it: edge billing, shift and floor stay inside `pos-edge-app`, and catalog and fees
  become one crate, `pos-cloud-catalog`.
- `pos-cloud-integrations` and `pos-cloud-admin` wait until a sub-state design is written down;
  neither is a move today.
