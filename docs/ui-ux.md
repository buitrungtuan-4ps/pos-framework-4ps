# UI and UX guideline

**Status** Accepted · **Owner** @maintainers-domain · **Last reviewed** 2026-08-18

The real users are staff standing for eight-hour shifts, with wet or greasy hands, during a rush, on devices ranging from a phone to a kitchen display read from two metres away. Every rule below serves that person first and the office user second.

**Philosophy: minimal frame, dense content, no surprises.**

| Direction | How it applies here |
|---|---|
| Modern minimal | Minimal in *decoration* — no gradients, no showcase animations. **Not** minimal in *information density* on cashier and kitchen screens: operators need to see many things at once. |
| Light and responsive | The server already answers in under 5 ms; the UI adds optimistic updates and a sub-100 ms perceived response. |
| Device adaptive | One application, **a distinct layout per device class** — not one layout that stretches. |
| Context aware | Adapts by role, system state, and shift phase — with one hard constraint: primary controls never move. |

---

## 1. Ten principles

1. **Perceived speed is feature number one.** Optimistic UI: a tap updates the screen immediately and synchronisation follows (the outbox guarantees correctness). Skeletons instead of spinners; never a blank waiting screen. Animations last at most 150 ms and never appear in a money path.
2. **Touch targets for real fingers.** Minimum 48 px; 56–64 px for cash keypads and primary actions; at least 8 px between targets. No hover-only affordances, no hidden gestures on primary paths.
3. **Stable positions — muscle memory is an asset.** Pay, fire, and open-table buttons never move. Adaptive behaviour may change *what is shown and in what priority*, never *where the primary controls live*.
4. **Disciplined context awareness.** By role: a server starts on the floor plan, a cashier on the payment queue, a cook on their station. By state: offline and printer errors surface where they matter. By phase: end-of-shift raises the close action. Never hide a function that is currently needed to "keep it clean".
5. **System state is always visible.** A thin persistent bar shows online/offline, print queue, and sync lag. No modals, no covering content. Offline is a normal working state, not an error.
6. **One screen answers one question.** Common actions take at most two taps from the role's home screen; rare actions at most three. **This is measured, not asserted** (roadmap-v3 **Q7**), by two gates over one declaration. `ui/scripts/step-tasks.mjs` declares the tap count of the selling tasks (thirty-two today) and what each one must reach. `ui/scripts/step-budget.mjs` resolves every declared tap against the source — the route must exist in `App.tsx`, an interactive element on that screen must really call the named action, and it must carry `data-step="<action>"` — and fails the `ui` CI job if a flow exceeds its budget or the declaration has drifted from the code. Run it alone with `pnpm steps`; it prints every task and marks the ones sitting at their ceiling, which are the flows to defend hardest. `ui/tests/replay.spec.mjs` then **clicks those same taps in a browser** against a real `examples/minimal-edge` and asserts each flow still reaches its `data-outcome` ([ADR-0109](adr/0109-counting-the-taps-an-operator-makes.md)), which is what catches the case the analyser cannot see: a required tap nobody declared. Run it with `pnpm replay`; the `replay` CI job runs it on every pull request.

**The budget governs the steps a task *requires*.** An optional enhancement to a flow — a tip on a
settle, say — is declared as its own task with its own ceiling, rather than counted against the flow
it sits inside. Without that distinction the rule pushes an optional control behind a button to keep
a number down, which costs the operator a tap in the case they *do* want it and buys nothing in the
case they do not. Two tasks here are declared at **four** on that basis (the two tipped settles) and
each says in its own note why it is not three. Three flows are several guests paying, and are declared
per guest rather than per act. The even split is four for two guests: one tap to say how many, then
one per guest. **Split by item** is seven: three to split one guest's lines off (the rare-action
ceiling), one tender per guest, and one to move to the next bill. Picking is one tap per line, so no
partition of lines can be shorter than naming them. **Split by seat** is five: the seats are already
on the lines, so the split is one tap, and the rest is the guests. Each note says so. What it **cannot** see is a required tap nobody declared: catching that needs a browser driving a running edge, and that harness does not exist yet ([gate register](gate-register.md)). So the gate stops a budget being quietly raised and a flow being quietly renamed; a reviewer still owns "did this change add a step?", and the printed map is what makes that a five-second question.

**The console is measured too, and its ceiling is not yet decided.**
`dashboard/scripts/step-budget.mjs` (roadmap-v3 **Q7**, the second half) does the same resolution for
the back-office flows: a click is a sidebar entry, an in-app link, or a handler on a screen, and each
is checked against `SCREENS`, `NAV_GROUPS`, `COMPONENTS` and the screen's own source. It runs from
`pnpm build`, so the `dashboard` CI job fails on drift.

What it deliberately does **not** do yet is rule. The two-and-three-tap ceiling above is about a till
in service; applying it unchanged to a console would be a number chosen to look strict rather than
one anybody had argued for. So every console flow declares `budget: null`, the gate fails only on an
unresolvable declaration, and it *reports* the measured cost. The first run's numbers:

| Console flow | Clicks |
| --- | --- |
| Change an item's price on a menu **and publish it** | **8** |
| Provision a new store and get its installer | 5 |
| Turn a capability off for a store and publish it | 3 |
| Acknowledge a firing alert | 2 |
| Check whether a shop is online | 1 |

The price flow is the one to argue about, and the argument is not really about the eight. Six of the
clicks author the change and the last two publish it — and a price saved without that second step
leaves the till charging the old one, with nothing on either screen saying so. **Shortening this
should shorten the first six, not merge the publish into the save**: the two-step shape is what makes
"change a price in the office at 11am, effective at the counter when you say so" possible at all.

The gate also earned its keep on its first run: it refused a declaration that claimed the new-store
wizard was one sidebar click away. It is in `SCREENS` and in no nav group — it is reached from the
Stores screen — so the flow is five clicks, not four, and nothing but a resolver would have noticed.
7. **Errors always have an exit.** Every error state offers the next action — retry, switch to the backup printer, call a manager by PIN. No dead ends, and never a raw error code in front of staff. **And a refusal never destroys what the operator has typed since:** a request takes a moment, the operator does not wait, and a field cleared on the answer's arrival takes the next attempt with it. Clear an input only if it still holds what was refused, and hand the cursor back so recovering costs no tap.
8. **Money is king.** The largest type on the screen, tabular figures, locale-aware thousands separators, and never a displayed value that differs from the real one for cosmetic rounding.
9. **Four device classes, four layouts.** **The till names them** (`ui/src/styles/tokens.css`) rather than adapting on pixel widths: `tablet:` is 768 px, `terminal:` is 1024 px, and **the phone is the base, with no prefix at all** — a layout that has to be asked for on the smallest screen is one that was designed for the largest and narrowed afterwards. The tokens are added beside Tailwind's stock names rather than replacing them, because that file is mirrored into `dashboard/` and the console has forty-five responsive rules in the stock vocabulary — so the vocabulary is enforced where it applies instead: `ui/scripts/device-classes.mjs` fails the `ui` job on a stock prefix under `ui/src`, and also fails if nothing adapts at all, so it cannot pass by the rules being deleted. `ui/tests/replay.spec.mjs` then loads **every screen at each of the three widths** in a browser and asserts the page does not scroll sideways and that no status-bar control — nor any control on the order and pay screens — is under 48 px — both of which were false until it did: the status bar's ten destinations sat in a row that could not wrap, 488 px wide and 20 px high, so every route scrolled sideways on a phone and the one control a finger could not hit was the navigation.
   - *POS terminal* (13"+): two columns — categories and items on the left, the open bill on the right.
   - *Tablet*: large item grid, bill slides up; usable one-handed.
   - *Phone*: single column, primary action anchored at the bottom within thumb reach — on the order screen the send and pay buttons are `sticky`, so a large table's order is sent without scrolling past it.
   - *Kitchen display*: readable from two metres — 24–28 px type, high contrast, dark background, whole-card tap targets or a bump bar. Not a width, and deliberately not a breakpoint: it is `/kds` and `/expo`, which take over the theme when they mount.
10. **Internationalisation from the first commit.** No hardcoded strings; dates, numbers, and money render per the store's locale; layouts survive text 30% longer than English; language is configurable per store and per device.

## 2. Design tokens

| Group | Values |
|---|---|
| Spacing | 4 px scale: 4 · 8 · 12 · 16 · 24 · 32 |
| Touch targets | **Two scales** (Wave 4 · D1/D3). *Till* (`ui/`): 48 px standard, 56–64 px for money and primary actions — a thumb, at arm's length, during service. *Console* (`dashboard/`): 40 px default, 32 px in a table row or a toolbar, 48 px kept for a full-width primary and for anything a finger presses on a tablet. A back office operated with a mouse does not need the till's target, and paying it made every list half again as tall as it needed to be. |
| Typeface | **Noto Sans, self-hosted**, six variable subsets under `dashboard/public/fonts` with a `unicode-range` each, so a page fetches only the scripts it paints (36 kB English, 50 kB Vietnamese). Chosen for coverage — "no tofu" in any script — because this framework already ships VN, JP and IN country modules. Thai, Devanagari and Arabic ship with the country module that needs them; CJK falls back to the system face. `tabular-nums` on every table and on the `.tabular` utility. |
| Type | 12 (meta) · 14 (label) · 16 (body) · 20 (heading) · 28 (KDS) · 40+ tabular (totals) |
| Brand vs. primary | **Two tokens, not one** (Wave 4 · D1). `--primary` is the ink a primary button is painted in: neutral, because this is a framework and "do the thing" belongs to the operator rather than to a brand. `--accent` is the one token a fork sets for itself — logo, focus ring, selected nav tint, links — and is never used on a button. Solid `--danger` is the button *inside* a confirmation; the control that opens one is `danger-ghost`. **Both surfaces follow the rule**: the console since Wave 4 · PR-2, the till since its thirteen primary buttons moved off `bg-accent` — the till's own `tokens.css` had said "never on a button" for a wave while thirteen buttons said otherwise, and a fork that sets a loud `--accent` was repainting the key that takes money. |
| Semantic colour | success / warning / error / info at WCAG AA contrast — every token pair measured in `docs/wcag-contrast-audit.md` and gated in CI (`pnpm contrast`). **Never carry meaning by colour alone** — always pair with an icon or text (8% of men have red-green colour deficiency). |
| Measure | Running text is bounded to 65 characters (`max-w-measure`); a page is bounded to 1280 px. A table may use the full width — its job is to fit its columns. |
| Shape | One radius (8 px), one border width (1 px). That is enough. |
| Motion | 100–150 ms ease-out, only for entrance and orientation |
| Theme | Light and dark across the product, configured per device (kitchen displays default to dark). Colour tokens are separate from structural tokens. |
| On-screen keyboard | **Two components, one rule** (`ui/src/components/`). `Keypad` is the money pad: digits in calculator order, 56 px keys, no decimal — `parseWhole` takes whole units — and it drops a leading zero, because `05` is not an amount anyone means. `CodePad` is the credential pad: A–Z above 0–9, 48 px keys, and it keeps every character pressed, because `0512` is a plausible PIN and `0012` a plausible badge code. The alphabet it draws follows the field being filled, so a letter is never offered to a field that would strip it, and a key press never takes the caret out of that field. Neither replaces the text input it sits under: `inputmode` asks the *platform* for a keyboard, which a phone and a tablet give and a fixed terminal gives only where its on-screen keyboard is switched on — these draw the keys for the case where it is not. The staff sign-in screen is the one that must work this way first: a till nobody can sign in to is every later screen too. From a terminal up it sets the fields and the pad side by side, because stacked, the pad's digit row sat below the fold of a 1366×768 till. **A manager approves the same way**: the badge and PIN on the fired-line void, the bill void and the discount are one component, `ApproverFields`, whose `CodePad` appears when either field takes focus and follows it. Before it, none of the three could be approved on a terminal with no keyboard. |

Tokens live in one theme file per surface (`dashboard/src/styles/tokens.css`, `ui/src/styles/tokens.css`), so per-tenant branding means changing tokens, not components. Since Wave 4 that promise is literal on both surfaces: a fork sets `--accent` and `--accent-ink` and nothing else moves.

## 3. Core screens

**Order (server, tablet or phone).** The floor plan is home: colour-coded table states, tap a table to open its order. **The floor is drawn as the store published it** — areas as sections, tables at the column and row the floor editor pinned them to, seat counts on the card — so the screen is a picture of the room rather than a list in publication order. An area whose tables are not all placed reflows instead, because a half-honoured grid puts a table somewhere its position does not mean. Item grid by category; sold-out items grey out and strike through on every device instantly. **A search box above the grid finds an item by name**, matching the price book's name and the caption the console wrote on its button, and folding diacritics so that `dac` reaches *đặc biệt* — a member of staff mid-service does not switch input mode, and a menu with two hundred items on it is longer than any grid or category tree can make quick. Typing is not a tap — §1 principle 6 counts taps, and the shift float and the manager's PIN are typed for the same reason — so selling from the tail of the book still costs the one tap selling from the grid costs. Adding an item is one tap; **a line carries its own stepper**, so three of something is one line saying three rather than three rows — and the stepper stops at one, because zero is not a smaller order but a void, which carries a reason. A line the kitchen already has shows its count without the controls. **required modifier groups open immediately** — the store's own groups, published on the `menu` node ([ADR-0127](adr/0127-modifier-groups-reach-the-edge.md)), so a tap on a pizza that has sizes becomes tap → size → add and a tap on one that has none stays a single tap. The picker enforces the group's `min_select`/`max_select` for the operator's sake and **the edge enforces it again**, because a required choice a forgetful device can skip is required in name only, and the money is already wrong by the time the kitchen reads the ticket. **What was chosen is shown wherever the line is** — under the item on the order list, under the dish on the kitchen board, and beside it on the pass — because a line that reads "Margherita" whether the server picked 25cm or 30cm cannot be checked back to a guest, and the cook is the person the choice was recorded for: a fired line consumes the base recipe plus one recipe per modifier (§8). The names come from the store's **current** price book, which is right for a screen showing an open order and is deliberately not the rule a document about a *past* sale follows — those take the name captured when the line was added (§14.2's line snapshot), because a bill already settled must not change under a rename. Half-and-half items are chosen in a single flow and appear as one line showing both halves. When seats are enabled, the seat is chosen before items and shown on each line — the choice is **sticky** until changed, because a server orders a whole seat's worth at once, and tapping the chosen seat again returns the next items to the table. The control is absent entirely where the store does not assign seats, since the edge refuses a seat there. The seat is part of what a device reads back at boot, so a till that reloads mid-service rebuilds the table with each line still against the person who ordered it. Each item displays **available-to-make** ("~6 left"), refreshed within 50 ms of any fire. The order's running total — subtotal, tax and total, read from the edge — sits on this screen, because the only other way to answer "how much so far?" was to open a bill, and a guest's question must not change the order's state. **The send button is fixed, shows the count of unsent lines, and sends them in one transaction**: a control per row cost one tap per line and could leave half an order with the kitchen. When two staff edit one table, the other person's lines appear live with their name.

**Cashier (POS terminal).** The right column is the bill: lines, discounts, service charge, tax, and the **total as the largest element on screen**. **A reduced bill says so and by how much** — a discount and a comp are two lines, not one, because a price decision and food given away are different facts and the receipt prints them apart. A total that simply came out smaller than the food on the table is the kind of figure a guest queries and nobody at the till can explain. Taking money off costs three taps (pay, discount, reason) with the amount and the manager's badge **typed**; it needs a manager today not because this screen says so but because `billing.discount.apply` is bounded by a role ceiling that **no store publishes yet**, so the edge reads the ceiling as zero and answers with the override permission. Cash offers **quick-cash** keys: the exact amount, then the smallest pile of each of the store's published notes that covers the bill, the four from the largest notes (a 655,600₫ bill offers 660,000, 700,000, 800,000 and 1,000,000). **Other amount** opens a numeric keypad for whatever pile no key names; the change shows as it is typed, and a figure short of the bill shows how much is missing and cannot be taken. A store that publishes no notes gets the exact amount and **Other amount** only. Payment methods are a fixed row of large buttons: cash, card for the exact amount, and **QR transfer**, which the cashier taps once the transfer shows in the store's account. The till does not confirm a transfer with a bank; no integration does yet. The counter screen charges the same three ways. Tips (when enabled) appear after a card method is chosen, as suggested percentages plus manual entry. **Splitting evenly:** a row of guest counts (2 to 6) on the pay screen divides what is owed into shares. A share is what is left divided by the shares still to pay, rounded up, and the last share is whatever remains, so the shares add up to the bill exactly. Each guest pays their own share by cash (with its own change), card or QR. The shares are held on the screen until the last one lands and then settled together, because the edge settles a bill in one step. A taken share can be given back with **Undo**. The tip row is hidden during a split, and the discount and void are disabled once a share is taken. **Splitting by item** ([ADR-0128](adr/0128-a-bill-splits-and-merges.md)): **Split by item** lists the bill's lines. The cashier taps what one guest is paying for, and **Split off** makes those lines a bill of their own. The rest stay open as the next bill. Each part reads what it is for ("For: 1 × Iced tea") and its own total. The edge assembles that total, with the part's own tax and rounding. When a part is paid, **Pay the next bill** puts the next part on screen. The table stays awaiting payment, and its order stays on the kitchen board, until the last part is paid. **Put the bills back together** merges the table's other open parts into the one on screen, for a split made by mistake. **Split by seat**, where the store assigns seats, is one tap with nothing to pick. It makes a bill per seat from the seat each line already carries. The table's own dishes, ordered for no seat, become a bill of their own, because a line cannot be halved. Each part says whose it is ("Seat 2 · For: 1 × Iced tea"). The table's running total on the order screen is every open part together. A till that reloads mid-split reads every open part and offers them oldest first. Every tender button waits for the edge's figure, so nothing can be tapped against an amount that has not loaded. Permission-gated actions open a PIN field in place — never navigate away. Opening the payment screen takes a **soft lock** and other devices see "X is taking payment"; the screen auto-locks after N idle minutes and reopens with a PIN.

**Guest orders (server).** QR orders held for staff confirmation ([ADR-0116](adr/0116-the-qr-hold-is-derived-and-it-gates-firing.md)) wait on `/guests`, one card per order headed by the table's **floor label**, with **Send to kitchen** and **Refuse** (which cites a reason from the store's list). The queue **reloads every 15 seconds** while the screen is open, because the orders arrive from the cloud rather than from this till; a failed reload keeps what is on screen. Nothing elsewhere on the till yet says an order is waiting.

**Before anyone signs in** — pairing, sign-in, store activation — the status bar shows no destinations and no **Sign out**: every destination only bounced back to sign-in. The language and theme stay.

**Kitchen display.** Cards by order and course, an age timer per card, colour changes at configured thresholds. Bump is a tap anywhere on the card. Recall keeps the last 60 seconds at the edge of the screen. Void tickets appear in red for 10 seconds with an audible alert. Nothing decorative — this screen is a production tool.

**What `/kds` does today.** One card per **ticket** — an order's fired lines for one station and one course, which is what a cook makes together — **oldest first**, aged from the ticket's oldest line; one tap bumps the whole ticket to the station it was fired to. Counter orders are on the board as well as table orders, and a ticket leaves the board when its order settles. **A counter ticket is headed by the guest's queue number** ("No. 12") on the board and the pass. The number is on the counter list (`GET /api/orders/open`), not on the live orders the boards are drawn from, so a board reads the counter list for the counter orders it shows. It keeps only those orders' numbers, and asks again at most every five seconds while one is missing. Until a number is known, the ticket shows the last four characters of the order's id, as it used to. Each line carries the station it was fired to (on the fan-out and on `GET /api/orders/live`), so a store with more than one station gets a row of station tabs, and `/kds?station=<id>` is a board for one station that survives a reload. Cards are keyed by the ticket and read their lines from the store, so a change redraws the card it touches rather than the board (finding F3: a bump on a 600-line board rebuilt 18,000 DOM nodes). **A board can ring for new food.** A toggle in its header turns the sound on for that device, which remembers the choice. It is off until a cook turns it on. When food reaches the board after the board's own first read of what is open, it plays two short notes. It never rings for what was already there when it came on, so a reload or a tablet waking stays quiet. A browser will not start sound on a page nobody has touched, so a reloaded board asks for one tap before it can ring again. The chime is made in the page rather than played from a file, so it works offline. **Still missing:** recall, void alerts, and published lateness thresholds (the board uses a fixed ten minutes).

**Admin dashboard (web).** Today's figures read from rollup tables (<10 ms): revenue, bill count, hourly curve, payment mix. A green/red fleet heatmap. Every configuration table can show which store is running which version. High information density is correct here — the user is an administrator, not a cashier.

**The store profile decides the starting screen and flow** ([pos-spec.md](pos-spec.md) §10): full-service starts on the floor plan and pays afterwards; a counter cafe starts on the order screen, pays first, and issues a queue number; retail starts on the barcode field. Same components, different assembly — not three applications.

**The till reads this now, for the first two of the three.** `GET /api/menu` publishes `tables_enabled` and `kds_enabled`; `/` draws the floor plan where the store does tables and the counter list where it does not, and the status bar drops the destinations the store has no use for — a link to a kitchen board nobody watches is an offer the store cannot honour, which is the same failure `tips_enabled` was published to stop. **Home stays `/` on every profile**: what changes is the screen, not the address, because a home that moved per shop would be three applications wearing one name. `examples/minimal-edge` publishes the counter profile under `POS_DEMO_PROFILE=counter`, and `ui/tests/replay.spec.mjs` drives both. **A counter store starts its own orders** ([ADR-0146](adr/0146-a-counter-store-starts-its-own-orders.md)): the counter list has **New order**, which opens a tableless takeaway order with the day's next queue number and lands on the same order screen a table uses, at `/order/:id`. The edge prices each line at the order's own channel, so the till sends only what the guest chose. **Take payment** returns to the counter list with that order's pad open. **Still missing:** retail has no barcode screen to start on (`Capability::Barcode` has no reader), and `pay_first_enabled` and `queue_number_enabled` have no readers: every tableless order gets a queue number, and payment follows the kitchen, because settling first would take the order off the live list before its ticket reached the board.

## 4. Degraded states

| Situation | What the UI does |
|---|---|
| No internet | Status bar reads "Offline — selling normally", counts pending events, and blocks nothing. It reads `GET /api/sync` — the outbox depth, its level against the planned depth, and what the outbox drain last saw of the cloud — and turns amber from half the planned depth and red from four fifths. **No depth refuses a sale** ([ADR-0137](adr/0137-a-deep-outbox-warns-and-never-refuses.md)) |
| Station printer failure | Red badge on that station's kitchen card plus exits: reprint, switch to backup printer; the print queue shows pending tickets |
| Offline beyond the configured threshold | Warning banner, escalating to a per-shift manager acknowledgement — never an automatic block on selling |
| Card result unknown | Bill parked in an amber state with two clear options (confirm manually against the terminal, or cancel), and it appears in the reconciliation list |
| Store server restarting | Clients reconnect via `pos.local` showing "Reconnecting…" for a few seconds; tables and shifts are preserved |
| **Device restarting** (browser reload, tablet waking, kitchen display switched on mid-service) | The device reads `GET /api/orders/live` at boot and redraws every open order, its lines and every bill still open on it (each part of a split table, oldest first), and `GET /api/shifts/current` for the shift that is open — blind, so the answer never carries the expected amount — which is what lets a reloaded till count and close the shift another device opened. A device learns lines from the fan-out, and the fan-out carries what happens *next* — without this read the order screen, the payment screen and the kitchen board all came back empty over live food. The same read answers a `resync`, which is the link telling a client it fell behind. |
| QR ordering unavailable (store or cloud offline) | The guest page reads "Please ask a staff member" — staff are always the fallback |

## 5. Dashboard screen inventory

**Specified:** setup wizard · configuration tree · fleet heatmap · Today · system status · audit log · device management and revocation · printer approval · invitation links · store export · Developers (API keys, webhook endpoints, delivery log with redeliver, test event) · Localization (enable languages, translation grid, completion, CSV).

**Shipped since this list was written** — four of its six entries, and part of a fifth. OTA release management with rollout progress and the kill switch (`Ota.tsx`) · the reconciliation viewer (`Reconcile.tsx`) · chain reports over date ranges (`Reports.tsx`, with a range picker and CSV) · tenant-level staff management across stores (`People.tsx`) · and the **store detail** panel on `Fleet.tsx`, which carries health, both config versions, the relay and publish backlogs and the store's audit trail.

**Still backlog:** the store detail's *last backup*, *installed version* and *invoice queue depth* — none of which the cloud holds per store today · the reconciliation viewer's *unknown-result payments*, which needs a payment-outcome projection that does not exist · **recovery actions** (reissue an activation code, reset a lease) — the lease half is the same gap as production-readiness **R4**: the edge never learns its lease standing, so there is nothing for a console button to reset yet.

## 6. Deliberately not done

Trend decoration (glassmorphism, parallax) · long onboarding tours — a sample menu plus a readiness checklist teaches by doing · dense tooltips · hidden gestures on primary paths · dark patterns · confirmation dialogs for reversible actions (offer undo instead, before firing or settling) · sound effects beyond the functional ones (bump, print failure, void ticket).

---

**Definition of success**, verified by observation during the pilot, not by survey: a new employee completes a full sale within five minutes without training, and an experienced cashier works an entire shift without ever hunting for a button.
