# ADR-0081 — Reports & analytics: windowed rollups, revenue & product-mix, and X/Z close semantics, on a registry-driven projector

**Status** Accepted · **Owner** @maintainers-cloud · **Last reviewed** 2026-08-28
**Relates to** [ADR-0036](0036-materialised-rollups.md) (the materialised-rollup projector this extends) · [ADR-0065](0065-cloud-org-registry.md) (the registry that replaces the `SELECT DISTINCT events` fleet scan) · [ADR-0075](0075-media-and-file-rail.md) (the CSV export rail this reuses) · [ADR-0073](0073-alerting.md) (the alert evaluator that already reads fleet/task health) · `docs/pos-spec.md` §6 (shifts & cash — the substrate an X/Z totals) · §14 (business-date cutoff) · §19 (billing) · `docs/roadmap.md` gap **D10** (the X/Z spec gap this resolves) · `docs/cloud-admin-ux-plan.md` (Track O4, which folds in "Perf wave 2")

**Context.** The cloud has one materialised rollup (ADR-0036): a background projector folds every store's event log into a per-trading-day `DailyRollup { business_date, total_events, by_type }` — **counts only**, no money, keyed one `jsonb` blob per `(tenant, store)`. Two read routes (`/v1/.../rollups/daily`, `/admin/.../rollups/daily`) serve it, and both **ship the store's entire retained history** — no date range, no window, no limit. The projector decides which stores to fold from `SELECT DISTINCT tenant_id, store_id FROM events` — a full scan of the event table on every 30s pass. There is a bare **Reports screen** (a counts table, the console's index route) with no range, no chart, no export. Revenue, product mix, and cross-store comparison do not exist. **X/Z reports are an open spec gap (D10)** — the spec never fixed whether an X read is non-resetting or a Z print is a one-time immutable artefact — and the cloud reads the cash/shift and settlement events only as type-counts, never as money.

Track O4 (roadmap) is: date-range/windowed rollups API (stop shipping all history), revenue/product-mix rollups (prices are **T2** → role-gated), charts + CSV export, cross-store comparison, and X/Z semantics; it also folds in "Perf wave 2" (projector reads the registry, dirty-marking, windowed blobs, config-blob delta, request-latency histograms).

**Decision.** Extend the one seam-isolated rollup cluster (`pos-cloud/src/dashboard/**`, the single `rollups` table, the `RollupStore`/`StoreCatalog` seam pair) additively. No new wire protocol, no event change — the projector reads events already ingested. Concretely:

1. **Windowed reads (stop shipping all history).** Add `?from=&to=&limit=` (inclusive business-date range, newest-first cap) to both daily-rollup routes. When no range is given the default is a **bounded** window (the last 90 trading days), never the full history. Filtering is in-process over the loaded blob for now (the storage reshape that would make the window a storage-level query is a flagged perf-wave-2 item); the API contract is what changes, so the window survives a later storage change.

2. **Registry-driven projector (perf wave 2).** `StoreCatalog::active_stores` stops scanning `SELECT DISTINCT … FROM events` and enumerates the **registry's Active stores** (`RegistryStore::list_tenants` × `list_stores`, `status == Active`; ADR-0065). This turns a full-table scan into a metadata read, and makes "the fleet" mean *provisioned, active* stores — a store is registered at provisioning (WS-C), so an event-bearing store is always registered. A store with no new events folds nothing (cheap); archived stores drop out of the sweep but their stored rollup is untouched and still readable.

3. **Revenue & product-mix rollups.** The projector gains a second fold that **decodes the money-bearing events** it previously only counted: `billing.bill.settled` (subtotal, reduction_total, service_charge, tax_total, rounding, total_due) for revenue, and `sales.order_line.fired` (menu item + line total) for product mix. It maintains a parallel `DailyRevenue { currency, gross, net, tax, reductions, bills, by_item }` per trading day, single-currency per store (§19). Money is **T2**: a new console permission **`console.reports.revenue`** (Owner/Admin only — not Ops/Viewer) gates every route and CSV that exposes an amount; the counts-only report stays on `console.data.read` as today. Revenue rollups carry **no T1 field** — product mix keys on `menu_item_id` (catalog metadata), never a customer or employee identifier.

4. **X/Z close semantics (resolves D10).** Fixed here, in the phase that needs them:
   - An **X report is a non-resetting, on-demand read**: the current period's running totals (the open shift, or the current business date), recomputed each call from the rollup, mutating nothing and repeatable any number of times.
   - A **Z report is a one-time immutable close artefact**: frozen when the cloud observes a business date's close (`cash.shift.closed` / the business-date rollover), stored keyed by `(tenant, store, business_date)`, and served **verbatim** thereafter — a re-request returns the stored artefact, never a recomputation that could differ. The Z is the operational daily-close record; it is **not** the country module's legal invoice/e-invoice artefact (that stays with the fiscal invoice-range work).
   The cloud aggregates these over the cash/shift + settlement events it already ingests; the edge keeps printing its own per-shift report (`print_shift_report`) for the drawer.

5. **Console & export.** The Reports screen is rebuilt on the F1/F2 kit: a date-range picker, inline-SVG charts (activity and — when permitted — revenue trend, and a product-mix top-N bar), cross-store comparison for a tenant, a revenue panel gated by `console.reports.revenue`, and the X/Z views. CSV export reuses the ADR-0075 rail (`csv_download_response`, audited by **row count only**, never contents); a revenue CSV is gated by the same permission and carries the T2/DPIA posture.

**Deliberately deferred (flagged, not silently dropped).**

- **Per-employee performance analytics** (sales/voids/discounts *by staff member*): out of scope on **policy** grounds, not effort. Reporting on individual employee behaviour is employee monitoring, which the org bars without a confirmed legal basis and notification, and which the metrics port already refuses by construction (A6). O4 reports on stores, trading days, products, channels, and tender — never on a named individual's conduct. Void/discount **totals** (not attributed to a person) are in scope as operational figures.
- **Perf-wave-2 storage reshapes** — dirty-marking the projector's per-store work, windowed rollup **storage** blobs (e.g. per-month rows so a windowed read is a storage query), and config-blob delta for the report payload. These change no behaviour and only bite well beyond the current fleet target; the projector's cursor-incremental single-writer design is adequate at target scale. Flagged at the seam points (`StoredRollups` shape, the projector cursor) so they land when scale demands.
- **Request-latency histogram aggregation** in metrics-vm: the producer today ships only the sparse `pos.cloud.up` liveness series (gated off below ~50 stores) and `MetricUnit` has no histogram/summary type. Per-request histogram instrumentation is a metrics-layer expansion better sequenced with the scale event that turns metrics on. Flagged.
- **Labour-vs-sales and tax-authority report formats** (D10's other named reports): the substrate (revenue, tax_total, shift hours) lands here; the specific statutory report layouts are per-country and sequence with the fiscal work.

**Consequences.**

- Additive throughout: the projector reads more of events it already ingests, one new console permission, a parallel revenue rollup persisted in the existing `rollups` seam (a new blob key or table column — an additive migration if a column, decided at implementation), new `/admin` read + export routes (no OpenAPI entry needed — `/admin` is not in the generated `/v1` doc, consistent with every other `/admin` route), and query params on the two existing daily routes. No protocol-version bump, no event change.
- The registry swap changes what "the fleet" means (provisioned-active, not ever-seen-in-events). Because provisioning registers every store, this is a superset in practice; the one behavioural edge — a store that emitted events but was never registered — cannot occur through the supported provisioning path, and its stored rollup would remain readable regardless.
- Revenue and product mix are **T2**. They are a tenant's own commercial figures, shown to that tenant's Owner/Admin for the legitimate internal purpose, role-gated, export-audited by row count, and never aggregated across tenants or shared externally by the tooling. No T1 (customer/employee) field enters a rollup. A revenue CSV export is the point to re-confirm retention and the DPIA posture before it leaves the console.
- Because the counts fold, the revenue fold, and the X/Z aggregation all run in `pos-cloud/src/dashboard/**` over the same event log through the same `RollupStore`/`StoreCatalog` seams, a full re-scan and the maintained rollup cannot drift, exactly as ADR-0036 guarantees for the counts today.

**Delivery note (O4 complete).** All eight slices shipped:

1. This ADR.
2. Windowed reads — `?from=&to=&limit=` on both daily-rollup routes, defaulting to the last 90 trading days (`dashboard::rollup::RollupWindow`); the API stops shipping a store's whole history.
3. Perf wave 2 — the projector's `StoreCatalog::active_stores` reads the registry's Active stores instead of `SELECT DISTINCT … FROM events`.
4. Revenue & product-mix rollups — `fold_revenue` decodes `billing.bill.settled` and `sales.order_line.added`; `DailyRevenue`/`ItemMix`; new `console.reports.revenue` (Owner/Admin) gating `GET /admin/stores/{id}/revenue/daily`.
5. X/Z reports (D10) — `fold_cash` over the shift/drawer events, `DailyCash`, and `XzReport` (X = current day, Z = a closed day, served verbatim) at `GET /admin/stores/{id}/reports/xz`.
6. CSV export — `export::{rollups_csv, revenue_csv}` and `.../rollups/export` + `.../revenue/export`, audited by row count.
7. The rebuilt Reports console screen — window, inline-SVG charts, revenue/product-mix/X-Z/cross-store panels (revenue T2-gated), CSV buttons, en/vi.
8. This delivery note; exit sweep.

The revenue/cash rollups ride the existing `rollups` blob under `#[serde(default)]` fields, so no migration; revenue accrues from the projector's cursor forward, and a `rollups/reset` backfills a store's history. The deferrals above stand and are unstarted: **per-employee performance analytics** (an employee-monitoring boundary the org and the metrics port both draw), the **scale-only perf reshapes** (dirty-marking, windowed storage blobs, config-blob delta, request-latency histogram aggregation), and the **country-specific statutory report layouts** (the substrate — revenue, tax, shift hours — is here; the fiscal formats sequence with the invoice-range work). This completes Track O4 (reports & analytics + perf wave 2).
