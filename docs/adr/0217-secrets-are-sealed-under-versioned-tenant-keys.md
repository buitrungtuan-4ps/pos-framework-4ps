# ADR-0217 — Secrets are sealed under versioned per-tenant keys that one environment key wraps

**Status** Accepted · **Owner** @maintainers-architecture · **Date** 2026-11-13
· Relates to [ADR-0151](0151-a-headless-linux-box-seals-its-secrets-with-systemd-creds.md),
[ADR-0153](0153-a-vendor-is-a-provider-the-cloud-chooses.md),
[ADR-0198](0198-a-store-reaches-the-internet-only-through-the-cloud.md),
[ADR-0216](0216-integrations-come-in-three-tiers-and-functions-wait.md)

## Context

The cloud seals every vendor credential and gateway secret header with XChaCha20-Poly1305 under
one key, `integration_secret` in `cloud.toml`, bound to tenant, connection and field. A sealed
value does not record which key sealed it, so the key cannot be changed: a new key makes every
stored secret unreadable and every connection must be entered again. The key sits in a file that
anyone who can read the host can copy, one key protects every tenant, and a tenant that leaves
cannot have its secrets made unreadable short of deleting rows.

## Options considered

1. **Keep one file key.** Cannot rotate; one leak exposes every tenant.
2. **A managed KMS now.** Sound, but ties the cloud to a provider before production's host is chosen.
3. **Envelope encryption: an environment key, behind a port, wraps one versioned key per tenant**
   (chosen).

## Decision

1. **Three layers.**
   - **The environment key** wraps tenant keys and nothing else. There is one per environment
     (development, staging, production, and one per country when its law keeps data in the country),
     and none is ever shared between environments.
   - **A tenant key** is random, generated by the cloud on first need, and stored only wrapped by
     the environment key.
   - **A secret** (a vendor credential or a gateway header) is sealed under its tenant's key, still
     bound to tenant, connection or endpoint, and field.

   Vendor credentials themselves stay per connection, scoped to tenant, brand or store
   (ADR-0153), so each brand's or store's vendor key is its own record.
2. **Every key has a version, and every sealed value names it.** A sealed value carries a short
   prefix naming the tenant-key version, and a wrapped tenant key the environment-key version. A
   value with no prefix is the format before this decision, read under `integration_secret` as
   version 0.
3. **Rotation never stops the service.** `pos-cloud keys rotate` (environment or one tenant)
   creates the next version. New seals use it, old versions keep opening, and a bounded background
   pass re-seals old values and records progress. A version is retired only when nothing is sealed
   under it. The same command is the emergency path when a key may have leaked. A leaked vendor
   credential is also replaced at the vendor.
4. **A tenant's secrets can be erased by key.** Deleting a tenant's key versions makes all its
   sealed secrets unreadable at once, for a tenant that leaves or an erasure request. Running it
   needs the owner's confirmation and is audited.
5. **The environment key sits behind a `KeyKeeper` port** (wrap and unwrap only) with three
   adapters. A deployment picks one by configuration, and the code does not change:
   - **file:** `integration_secret` as today, for development and demos only;
   - **systemd-creds:** the key is sealed to the host's TPM2 when it has one, as ADR-0151 does
     for the edge;
   - **a managed KMS:** added by its own ADR when production's provider is chosen, because it
     adds a dependency.
6. **Nobody handles a key by hand.** Keys are generated by the cloud or the keeper, never typed or
   copied. Logs and the audit trail name a key's version, never its bytes.

## Consequences accepted

- A port and its contract tests, a format prefix, a re-seal pass and a CLI command; existing values
  keep working through version 0 until the pass re-seals them.
- Erasing a tenant's key cannot be undone.
- Production should not run on the file keeper; `deploy/` says so.
