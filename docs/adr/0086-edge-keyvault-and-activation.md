# ADR-0086 — The edge's OS-keyring KeyVault, and composing activation into the shipped binary

**Status** Accepted · **Owner** @maintainers-edge · **Last reviewed** 2026-09-01
**Relates to** [ADR-0003](0003-cattle-not-pets.md) (activate once, credentials in the OS key store; five-minute replacement) · [ADR-0007](0007-in-house-vs-dependency.md) (what we buy vs. hand-roll) · [ADR-0018](0018-http-websocket-stack.md) (the edge HTTP/UI surface this extends) · [ADR-0026](0026-port-shapes.md) (why `KeyVault` is async) · [ADR-0050](0050-activation-code-exchange.md) (the activation exchange this composes) · [ADR-0051](0051-device-credential-provisioning.md) (the `posdev_` credential it stores) · [ADR-0053](0053-cloud-sync-port.md) / [ADR-0054](0054-edge-cloud-http-client.md) (the `CloudSync` adapter activation runs against) · [ADR-0085](0085-edge-cloud-sync-transport.md) (E1; this is E2, and completes the credential story E1 flagged) · `docs/roadmap-v3.md` (roadmap v3, slice E2)

**Context.** [ADR-0050](0050-activation-code-exchange.md) built the edge's activation flow — `POST /api/activate` exchanges a one-time code over the `CloudSync` port for a device credential, stores it in the [`KeyVault`](../../crates/pos-ports/src/key_vault.rs) under `SecretName::DeviceCredential`, and `boot_standing` reads the vault to decide whether the box is activated ([ADR-0003](0003-cattle-not-pets.md)'s "activate once, then durable"). All of it is written, exported, and tested.

None of it runs in the shipped binary. `serve()` composes only the store, the fan-out, pairing, and the domain routes; `activation_router` and `boot_standing` are never merged or called, and `main.rs` constructs no `KeyVault` and no `CloudSync` adapter. The only `KeyVault` implementation in the tree is `pos-fakes`' in-memory `FakeKeyVault`. This was deliberate and is written down — the CHANGELOG records that composition "waits on the OS-keyring `KeyVault` adapter, deferred as a gated hardware/OS handoff (it needs a live credential store its contract suite cannot get in the pull-request gate)," and the provisioning guide flags the same. E2 is that slice: build the real vault, compose activation into the binary, and give the operator a `/setup` screen to type the code.

The hard part is the vault, and specifically **Linux**. The store box is a headless mini-PC: the systemd unit runs as `User=pos` with `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`, and **no desktop session or D-Bus session bus**. That rules out the Secret Service (gnome-keyring/KWallet) the usual "Linux keyring" means. The kernel keyring (keyutils) works without a session, but it is **not durable across a reboot** — which collides with ADR-0003's "activate once." A fully durable, sessionless Linux secret store means the TPM (a sealed blob, e.g. via `systemd-creds`), and that needs real hardware to validate and a privileged decrypt-at-start path — exactly the hardware gate the deferral named. Windows (a real edge target, roadmap E4) has a clean answer already — the Credential Manager, per-user and durable — but Windows is not this slice.

So E2 must deliver the flow and the adapter without being blocked on a TPM box, and be honest about what is not yet solved.

**Decision.**

- **The KeyVault adapter is a new crate `key-vault-keyring`, built on the `keyring` crate.** Implementing `pos_ports::key_vault::KeyVault` (async `store`/`load`/`delete` over the `Secret` newtype) against the OS's own credential store: **Windows Credential Manager** (the E4 target — durable, per-user, runtime-writable, sessionless), the **macOS Keychain** (developer machines), and on **Linux the kernel keyring via `keyring`'s `linux-native` (keyutils) backend**. Buying this is squarely the [ADR-0007](0007-in-house-vs-dependency.md) call: three platform credential-store FFIs (keyutils syscalls, `CredWrite`/`CredRead`, `Security.framework`) are the "general, fiddly, platform-specific" work we do not hand-roll, and `keyring` is the maintained, de-facto crate for exactly this. It is the first new runtime dependency since the tree's HTTP/DB stacks; it gets a `deny.toml` review and any duplicate-version it introduces is a curated `skip` with a review date (the nightly reports the list). **Linux uses `linux-native` only — not `secret-service`** — so no `zbus`/D-Bus subtree enters the graph and the adapter works under the headless service user.

- **The adapter honours the port contract, including "never a file."** `load` of an absent secret is `Ok(None)`; `store` replaces; `delete` is idempotent; and a store that cannot be reached is `PortError::unavailable` — it **never** falls back to writing a secret beside the binary ([`key_vault.rs`](../../crates/pos-ports/src/key_vault.rs) contract §4). It passes the shared `key_vault_suite!` (`pos-contract-tests`), including the all-256-byte-values round-trip, so it must be binary-safe, not UTF-8. Because the suite needs a live credential store, it runs in the **gated integration lane** (a keyring provisioned in the CI job), not the ten-minute pull-request gate — the same real-dependency split `store-postgres` (real Postgres) and `cloud-sync-http` (real socket) already draw.

- **Activation is composed into the shipped binary.** `main.rs`/`serve()` construct the vault and a `cloud-sync-http` `CloudSync`, thread `Arc<V>`/`Arc<C>` to `serve()`, and merge `activation_router(edge, cloud, vault)` into the app router beside the infra and domain routers. The SPA fallback already serves a client-routed path, so `/setup` resolves.

- **The boot gate gates cloud sync, not local trading.** `boot_standing` reads the vault: `Activated` (a `DeviceCredential` is present) or `NeedsActivation`. An unactivated box still binds, pairs, and serves the LAN **offline** — the offline-first invariant ([ADR-0001](0001-offline-first-store-autonomy.md)) is not weakened, and a box with no cloud has nothing to sync anyway — but the config-pull and heartbeat loops (E1) spawn **only** when the box is activated, and the operator UI routes an unactivated box to `/setup`. Activation is the earliest gate, ahead of pairing: a box with no device credential is set up first, then devices pair, then staff sign in.

- **The E1 sync key moves into the vault, with the env override kept.** [ADR-0085](0085-edge-cloud-sync-transport.md) planned this: a new `SecretName::SyncKey` holds the tenant-scoped `read_config` key beside the device credential; the single E1 call site (`server.rs` `spawn_cloud_loops`) becomes vault-first, falling back to `POS_EDGE_SYNC_KEY` for a headless bring-up. `SecretName` is `#[non_exhaustive]`, so adding the variant is source-compatible; the three coordinated edits (the variant, `ALL`, `as_label`) and the `ALL.len()` unit-test bump land together, and the existing `wipes_every_secret_a_machine_holds` contract case then covers the new secret automatically.

- **The `/setup` screen mirrors the S0b sign-in.** A `Setup.tsx` at `/setup` (an activation-code field, `busy`/`error` state, `role="alert"`), an `api.activate(code)` / `api.activation()` pair in the typed client, a `setup.*` i18n namespace (en + vi, parity-linted), and an activation branch in `App.tsx`'s boot gate ahead of the pairing/sign-in branches. It reuses the `Pairing.tsx` single-code-input pattern; the code is `XXXX-XXXX-XXXX`, so a text input with format hinting rather than the numeric pairing input.

**Deliberately deferred (flagged, not silently dropped).**

- **Headless-Linux reboot durability is the remaining hardware gate.** The `linux-native` keyring is sessionless but volatile across a reboot, so a headless Linux box re-activates after a power cycle unless its keyring is made durable. The production answer is a **TPM-sealed credential** — `systemd-creds` (`LoadCredentialEncrypted=` decrypting into `$CREDENTIALS_DIRECTORY` at start, sealed to TPM2), which is durable, sessionless, and adds no Rust crate — or a boot-unlocked keyring. Both need real hardware to validate and a privileged path the non-root service user does not have at runtime, so they stay the flagged hardware handoff. Until then, a headless Linux box uses the documented interim: the device credential provisioned at install and the `read_config` key via `POS_EDGE_SYNC_KEY` (the env override this slice keeps). Windows Credential Manager (E4) has no such gap.
- **`boot_standing` does not yet block a misconfigured box from re-activating.** Re-activation is refused while a credential is present (`409`, ADR-0050); wiping-on-revocation across `SecretName::ALL` is the lease path (ADR-0049), unchanged here.
- **The service unit's `EnvironmentFile`.** ADR-0085 specified a mode-0600 env file for the sync key; the shipped `deploy/edge/pos-edge.service` does not yet carry it. E2's implementation adds it (and a keyring note) so the interim path is real, ahead of the TPM hardening.

**Rejected.**

- **The `keyring` crate's Secret Service backend** (`sync-secret-service`/`async-secret-service`) — rejected for the store box: it needs a D-Bus session bus and a running secret service daemon, which a headless kiosk under a system service user does not have. It would also drag a `zbus` subtree in for nothing. `linux-native` is the sessionless backend that fits.
- **A hand-rolled per-platform vault** (raw keyutils syscalls + `CredWrite` + `Security.framework` FFI) — rejected by [ADR-0007](0007-in-house-vs-dependency.md): three fiddly, security-sensitive platform integrations to maintain on a thousand unattended machines, where a maintained crate exists. The port seam means the crate can be swapped later without touching activation.
- **A TPM-sealed file adapter as *this* slice** — the right production Linux answer, but it needs a TPM box to validate and a privileged decrypt-at-start path; making it the E2 blocker would stall the whole flow (adapter + composition + UI) on hardware. It is the flagged follow-up, and the `KeyVault` seam means it lands as a second adapter behind the same trait with no change to activation.
- **Shipping the `FakeKeyVault` in the real binary to unblock composition** — rejected: an in-memory vault loses the credential on restart and protects nothing, so it would ship a security regression dressed as progress. A real adapter (even one with a flagged durability gap on one platform) is the honest floor.
- **Blocking local trading until activated** — rejected: it breaks offline-first (ADR-0001). The gate withholds cloud sync and routes the UI to `/setup`; it never stops the counter serving the LAN.

**Consequences.**

- A fresh box can be **activated from its own screen**: install, open `/setup`, type the code, and the device credential lands in the OS keyring — the ADR-0003 five-minute replacement, end to end, on any platform with a runtime keyring (Windows now; Linux durably once the TPM hardening lands). The activation flow that was written-but-dark since ADR-0050 is finally reachable in the shipped binary.
- **No wire, protocol, or migration change.** `POST /api/activate` / `GET /api/activation` and the `CloudSync` exchange are exactly as ADR-0050/0053 built them; E2 is a new adapter crate, a new `SecretName` variant (additive, `#[non_exhaustive]`), the composition in `serve()`, and the `/setup` UI. No `pos-proto` change, no `PROTOCOL_VERSION` bump.
- **One new dependency, contained.** `keyring` (Linux `linux-native` only) enters via one adapter crate; `pos-core`/`pos-proto` are untouched (the dependency rule still holds); the contract suite proves the adapter against a real keyring in the gated lane. Any duplicate-version it introduces is a curated, dated `skip`.
- **The credential story E1 left open is closed but for the hardware gate.** The sync key moves from the environment into the vault (env kept as override), so a provisioned store keeps one protected credential store rather than a secret in a service-unit env file — with the headless-Linux durability of that store the one remaining, clearly-flagged hardware handoff.
- **Delivery shape.** This ADR is PR A. The implementation follows as: the `key-vault-keyring` adapter crate + `SecretName::SyncKey` + its contract harness (backend), then the `serve()` composition (activation + `cloud-sync-http` + boot gate + vault-first sync key) + the `/setup` UI + the deploy/guide docs — split so each PR stays reviewable, every one behind the same green gate.
