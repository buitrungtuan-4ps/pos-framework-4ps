# ADR-0085 — The edge dials its cloud: config-pull and heartbeat over the tree's rustls stack, keyed by the store's scoped credential

**Status** Accepted · **Owner** @maintainers-edge · **Last reviewed** 2026-09-01
**Relates to** [ADR-0001](0001-offline-first-store-autonomy.md) (the store trades without the cloud; these loops are background, never blocking) · [ADR-0004](0004-cloud-owned-configuration.md) (configuration is cloud-owned; this is the receiver) · [ADR-0018](0018-http-websocket-stack.md) (the async runtime and HTTP stack live at the binary layer) · [ADR-0037](0037-api-keys.md) (the scoped bearer the `/sync` routes verify) · [ADR-0039](0039-config-delivery.md) (the authenticated `/sync` config-pull surface and its `read_config` scope) · [ADR-0044](0044-fork-and-deploy.md) (server-generated secrets in a mode-0600 env file) · [ADR-0051](0051-device-credential-provisioning.md) (the `posdev_` device credential activation grants) · [ADR-0053](0053-cloud-sync-port.md) · [ADR-0054](0054-edge-cloud-http-client.md) (the edge→cloud HTTP client this reuses) · [ADR-0061](0061-order-relay.md) (the relay seam that shares this transport) · [ADR-0068](0068-fleet-liveness.md) (the heartbeat's purpose) · `docs/roadmap-v3.md` (roadmap v3, slice E1)

**Context.** The edge already carries three background loops as pure, seam-based, fake-tested library code: the config-pull loop ([`config_client`](../../crates/pos-edge/src/config_client.rs), ADR-0039), the liveness heartbeat ([`heartbeat_client`](../../crates/pos-edge/src/heartbeat_client.rs), ADR-0068), and the order relay ([`relay_client`](../../crates/pos-edge/src/relay_client.rs), ADR-0061). Each hides its HTTP behind a transport seam (`ConfigTransport`, `HeartbeatTransport`, `RelayTransport`) so its control flow — backoff, never-blank config application, idempotent ack — is tested with no socket.

But **`serve()` spawns none of them, and no field implementation of any of the three seams exists** — the only implementers in the tree are test fakes. The shipped edge therefore connects to its cloud for exactly one thing (the first-boot activation exchange over the `CloudSync` port, ADR-0050/0053/0054) and then goes dark: a menu, price, tax table, or staff roster published from the dashboard never reaches the counter, and the fleet view shows every running store as never-seen. The whole cloud-owned-configuration design (ADR-0004) is inert on real hardware until these loops actually dial.

Slice E1 closes this for the two loops that matter first — config-pull and heartbeat (the relay is E3). Wiring them needs two things the edge does not have yet: a real outbound HTTP client that can `GET` with a bearer, and a credential the cloud's `/sync` routes will accept. This ADR settles both, and how `serve()` runs the loops, before the implementation slice writes them.

Two facts constrain the choice. First, the cloud already serves the routes and already fixes their auth: `GET /sync/stores/{id}/config?held_version=…` and `POST /sync/stores/{id}/heartbeat` both verify a **tenant-scoped API key** `pos_<id>_<secret>` carrying the `read_config` scope (ADR-0037/0039) — not the `posdev_` device credential that activation drops in the vault (ADR-0051). ADR-0039 called this out as a known interim: the device-scoped credential is "the right long-term credential, but it belongs to P9… the tenant-scoped `read_config` key is the pragmatic credential." Second, the edge already dials its cloud once, at activation, over raw `hyper` + `tokio-rustls` (`ring`) behind an `HttpTransport` seam — the `cloud-sync-http` adapter of ADR-0054 — and that exact rustls/hyper pin is the tree standard, present verbatim in five crates (ADR-0038's webhook sender, ADR-0054's sync client, and three courier/ERP adapters). E1 should not invent a second way to make an HTTPS request.

**Decision.**

- **The field transports live in `pos-edge`, over the tree's standard rustls/hyper stack.** `ConfigTransport`/`HeartbeatTransport`/`RelayTransport` are **edge-internal application seams**, not ports: they are defined in the `pos-edge` binary crate and speak edge-local types (`serde_json::Value`, the relay DTOs mirrored from `pos-cloud`), not clean `pos-ports` shapes. Their implementations therefore belong at the edge's composition layer, which is exactly where [ADR-0018](0018-http-websocket-stack.md) puts the async runtime and the HTTP stack. The client is built on the same direct dependencies ADR-0038/0054 pinned — `hyper` (client, http1), `hyper-util`, `http-body-util`, `bytes`, `tokio-rustls` (`default-features = false`, `ring`/`tls12`/`logging`), `webpki-roots`, `url` — all already in `Cargo.lock` at these versions, so **no new crate, no new version, and no new `cargo-deny` entry** enters the graph. The `ring` provider is pinned explicitly so feature unification cannot pull `aws-lc-rs`; roots are the bundled `webpki-roots` Mozilla set, hermetic for a fork-and-deploy edge. As at activation and for the webhook sender, the destination is the store's own cloud — a trusted host set at activation, not attacker-influenced input — so there is no SSRF surface and the client resolves and connects the ordinary way (the DNS-rebinding guard of ADR-0032/0038 is for arbitrary tenant endpoints, not this one).

- **One small HTTP primitive, in a `pos-edge` `cloud_http` module.** Parse the configured base URL once; per call, dial `host:port` → rustls-handshake against the hostname → one HTTP/1.1 request carrying `Authorization: Bearer <key>` → read the full bounded body, all under a `tokio::time::timeout`. This is `TlsHttpTransport` (ADR-0054) generalised in the two ways config-pull needs and activation did not: a `GET` verb as well as `POST`, and an `Authorization` header. Each of the three transports is then a few lines over it — build the request, map `(status, body)` to `SyncedConfig`/`()`/the relay DTOs or to the seam's error. Copying the ~130-line connect-handshake-request primitive once into `pos-edge`, rather than a cross-crate extraction that would reach into `cloud-sync-http`'s contract-tested adapter, is the E1-sized move; consolidating the two copies into one shared internal helper is a flagged follow-up (below), kept open by the seam.

- **`cloud_url` joins `EdgeConfig` as an optional bootstrap field.** A store activated against a cloud carries its cloud base URL, written into `config.toml` by the new-store wizard's generator (ADR-0065's provisioning path) beside `store_id`. It is `#[serde(default)]` (`Option<Url>`): **absent means the edge runs LAN-only and spawns no cloud loops**, exactly as it does today — the on-fakes `minimal-edge` example, a demo box, and a not-yet-provisioned machine all keep booting unchanged. Adding an optional field with a default touches neither the existing fields nor the example, so this is strictly additive.

- **For E1 the credential is the tenant-scoped `read_config` key, supplied out-of-band — never committed, never in `config.toml`.** The edge presents `Authorization: Bearer pos_<id>_<secret>`, the key the `/sync` routes verify today (ADR-0037/0039). It is read from the environment (`POS_EDGE_SYNC_KEY`), which the store's service unit supplies from a **mode-0600 `EnvironmentFile`** — the same shape the cloud injects its own secrets with (ADR-0044's server-generated secrets). A bearer secret does not go in `config.toml` (the world-readable bootstrap an operator may inspect) and never in the repo (the `gitleaks` gate would reject it regardless). If the key is absent, the edge logs that it is running LAN-only and spawns no cloud loops — the same graceful degradation as an absent `cloud_url`, rather than a loop spinning on `401`.

- **`serve()` spawns the loops it is configured for, under the existing graceful-shutdown signal.** When `cloud_url` and the sync key are both present, `serve()` builds the config and heartbeat transports and `tokio::spawn`s `ConfigClient::run(shutdown)` and `HeartbeatClient::run(shutdown)` beside the axum server, each selecting on one shared shutdown future so Ctrl-C / SIGTERM drains the loops and in-flight requests together. The loops already back off and retry on a transport error and never surface it, so the store keeps trading on its last-known-good session while the link is down (ADR-0001 unchanged). **The relay loop's spawn (and NATS event publish) is E3**, over the same primitive and credential decided here.

**Deliberately deferred (flagged, not silently dropped).**

- **The durable home for the key is the OS-keyring KeyVault — that is E2.** The `KeyVault` port's only real adapter (the OS keyring) is slice E2; until it lands, the mode-0600 `EnvironmentFile` is the interim store. E2 moves the `read_config` key into the vault beside the `posdev_` device credential (a new `SecretName`), with the env var kept as an override for a headless bring-up. The `cloud_http` credential source is a single call site, so this is a one-module change behind the seam.
- **The long-term identity is the `posdev_` device credential, not a tenant-scoped key.** ADR-0039/0051 name the device-scoped credential the correct one; making the cloud's `/sync` routes accept it — so the edge presents the single identity activation already gave it, and a store's `read_config` key is no longer copied to the box — is a **cloud-side auth change** owned by a later P9 / A·P4 slice. E1 stays additive and edge-only: it uses the key the cloud verifies today and changes no cloud code.
- **Consolidating the two hyper primitives.** `cloud_http` and `cloud-sync-http`'s `TlsHttpTransport` will hold near-identical connect-handshake-request code. Extracting one shared internal helper both compose (an `pos-http-client`-shaped crate, or a shared module) is worth doing once the shapes have settled; doing it inside E1 would drag a contract-tested adapter into a wiring slice for no behavioural gain.

**Rejected.**

- **`reqwest` / `ureq`** — a second TLS stack, and (reqwest) a default `aws-lc-rs` provider, for zero benefit over the `hyper` + `ring` wiring the tree already standardises on across five crates. The same call ADR-0038 and ADR-0054 made; nothing about a `GET` with a bearer changes it.
- **A new `edge-cloud-sync` adapter crate implementing the three seams.** The seams are defined in the `pos-edge` binary crate and speak edge-local types, so an adapter crate would have to depend on the binary (a layering inversion the dependency-rule test forbids), or the seams would have to move into `pos-ports` — a port-list change (ADR-0021) for what are internal application seams, not boundaries a third party plugs into. The composition layer is their right home (ADR-0018).
- **Reusing `cloud-sync-http`'s `TlsHttpTransport` directly.** It is `POST`-only and sets no `Authorization` header, so config-pull (a `GET` with a bearer) does not fit it as written; and taking a `pos-edge → cloud-sync-http` dependency to borrow a ~130-line primitive buys less than copying it, while coupling a binary to an adapter it does not otherwise use. The flagged consolidation keeps the shared-helper option open without blocking E1.
- **Presenting the `posdev_` device credential now.** It would require changing the cloud's `/sync` bearer verification in the same slice, turning an additive edge-only change into a cloud auth change with its own migration and test surface. Deferred to the P9/A·P4 slice that owns it.
- **Putting the sync key in `config.toml`.** The bootstrap config is world-readable and operator-inspectable by design (ADR-0030's pairing URL, the bind address); a bearer secret belongs in a mode-0600 env file now and the keyring at E2, not there.
- **Blocking `serve()` on the first successful pull.** The loops are background and best-effort by construction (ADR-0001): a store must boot and trade whether or not its cloud answers. `serve()` spawns and moves on; the first pull applies config when it arrives, and until then the edge runs its last-known-good (or bootstrap) session.

**Consequences.**

- The shipped edge finally talks to its cloud continuously. A dashboard menu / permission / tax / locale publish reaches the counter without a restart (config-pull hot-swaps the live `EdgeSession`, ADR-0039), and the fleet view sees the store as alive even in a quiet period between publishes (heartbeat, ADR-0068). This is what turns the cloud-owned-configuration design (ADR-0004) from a tested library into a running behaviour on real hardware.
- **No wire, protocol, or cloud change.** The routes, their bearer, and the config-document shape are exactly what the cloud already serves; E1 is an edge client, one optional `EdgeConfig` field, and an env-supplied key. No `pos-proto` change, no `PROTOCOL_VERSION` bump, no migration. **Upgrade note:** a provisioned store gains a `cloud_url` in its `config.toml` and a `POS_EDGE_SYNC_KEY` in its service unit's env file; an edge with neither behaves exactly as before (LAN-only).
- **Additive and reversible.** An edge with no `cloud_url` or no key runs precisely as it does today, so the example, demos, and pre-provisioned boxes are unaffected. The seam and the single `cloud_http` credential call site mean the E2 keyring move and the later device-credential `/sync` migration each touch one module, not the loops.
- **The fast pull-request gate is unchanged.** The loops keep their fake-transport unit tests (backoff, never-blank application, idempotent ack); the real socket stays the gated integration lane and the soak, the split ADR-0038 / ADR-0054 / ADR-0031 already draw. The implementation slice adds only a thin, socket-free test that `cloud_http` builds the right request line and `Authorization` header from a base URL.
