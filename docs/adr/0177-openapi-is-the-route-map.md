# ADR-0177 — OpenAPI is the route map: every route, its permission and its schemas

**Status** Accepted · **Owner** @maintainers-architecture · **Date** 2026-10-21 · Supersedes the
"success bodies are not documented" decision of [ADR-0019](0019-openapi-generation.md)'s amendment
of 2026-09-03 · Relates to [ADR-0111](0111-a-second-origin-may-address-the-edge.md),
[ADR-0158](0158-the-till-enforces-each-persons-own-permissions.md),
[ADR-0067](0067-multi-admin-console-rbac.md),
[ADR-0175](0175-the-crate-list-follows-what-a-move-can-reach.md)

The owner approved the direction on 2026-10-21 (P11, item 1). The decisions below are this record's,
and are reviewed in its pull request.

## Context

The cloud documents its `/v1` routes and 179 of its 196 `/admin` paths. The other 17 are in the
floor, kitchen and inventory crates, which have no `utoipa`. The edge's 73 published routes
(`docs/snapshots/routes.txt`), and its `/healthz` and `/ws`, have no document at all, and the
cloud's device-facing routes (`/sync`, `/activate`, `/claim`) have none either. No document carries
a response schema, because ADR-0019's amendment stopped at the request side rather than put `utoipa`
into `pos-proto`. So the till and the console mirror about 3,200 lines of response types by hand
(`ui/src/api/types.ts`, `dashboard/src/api/types.ts`), and nothing checks a mirror against the
server. Which permission a route needs is recorded twice and checked once: in the edge's
`ROUTE_PERMISSIONS` table, and in each console handler's `require_permission` call, which no
document shows.

## Options considered

| | Option | Against it |
|---|---|---|
| A | Keep the request-side documents and the hand-written TS | The mirrors keep drifting unseen; the route map stays scattered |
| B | Mirror the wire types as cloud-local schema structs | Reintroduces the second shape [ADR-0079](0079-inventory-and-suppliers.md) removed, forty times over |
| C | `utoipa` in `pos-proto`, **optional and off by default**; schemas from the wire types themselves | A backbone dependency, behind a feature. Chosen |

## Decision

1. **Every route is in a document.** There are four documents, each a generated, committed snapshot
   held by the ADR-0019 drift test and `POS_UPDATE_SNAPSHOTS=1`:
   - `docs/openapi.json` (`/v1`, integrators);
   - `docs/openapi-admin.json` (`/admin`, the console);
   - **`docs/openapi-edge.json`** (the edge's `/api`, `/healthz` and `/ws`, the till), generated by
     a `pos-edge` test;
   - **`docs/openapi-device.json`** (`/sync`, `/activate`, `/claim`, what a store box calls).

   Each crate's test fails on a registered route that is neither documented nor named in an
   exclusions list with its reason, and on a documented path that no router serves (the B5 tests,
   generalised). The edge's document covers exactly the routes in `routes.txt`, which stays
   ADR-0111's removal gate, plus `/healthz` and `/ws`. There are two exclusions, each listed with
   its reason: `/internal/*`, which is trusted-network only
   ([ADR-0097](0097-internal-route-authentication.md)), and `/health`, a liveness probe. The edge
   does not serve its document: it is committed, not a new route.
2. **`utoipa` reaches the crates that serve routes.** `pos-cloud-floor` and `pos-cloud-inventory`
   gain `utoipa` at the workspace's version, as `pos-cloud` and its other area crates already have
   it. **The store binary links nothing new.** `pos-edge` gains an `openapi` feature, off by
   default, that enables an optional `utoipa` and `pos-proto/openapi`. Its annotations are
   `#[cfg_attr(feature = "openapi", utoipa::path(…))]`. The only thing that turns the feature on is
   `pos-edge`'s dev-dependency on itself with `features = ["openapi"]`, so `cargo test` builds the
   document and checks it, while a release build of the edge never compiles `utoipa`. The first edge
   slice records the binary's size before and after once, as a measurement.
3. **Response schemas come from the wire types.** `pos-proto` gains an optional `openapi` feature,
   off by default, that adds `#[cfg_attr(feature = "openapi", derive(utoipa::ToSchema))]` to its
   wire types and a schema to the types `wire_enum!` makes. `utoipa` joins
   `tools/backbone-allowlist.toml` on the condition that it is optional and enabled by no default
   feature, and `deps-rule` fails if it is not. `deps-rule` already computes `pos-proto`'s closure
   with default features, so `pos-core`, `pos-ports`, the print agent and every other crate that
   does not ask for `openapi` links nothing new. `pos-cloud` enables it, and `pos-edge` only through
   its own `openapi` feature (decision 2). A type whose `serde` shape `utoipa` cannot read from its
   attributes (a hand-written `Serialize`) gets a hand-written `ToSchema` beside it, behind the same
   feature, with a test that compares the schema with a real serialized value, as the error-envelope
   mirror already does.
4. **`operationId` is the handler's function name.** It is `utoipa`'s default, so `operation_id =`
   is never written. A test fails on a duplicate within a document, so two handlers with one name in
   different modules are renamed. Item 5's route map finds a handler's file by that name.
5. **Authentication is OpenAPI's own `security`; authorization is `x-permission`.**
   - **Who must present what** is a standard security requirement, and each document declares its
     schemes:
     - `till_session`: the edge's device token, carried as a bearer token;
     - `session_cookie`: the console's session;
     - `device_credential`: a store box's credential on `/sync`, with its scope as the role;
     - `api_key`: a `/v1` scoped key, with the scope as the requirement's role, as OpenAPI 3.1
       allows.

     `security: []` means public. A public operation also carries `x-public-reason`, which says what
     gates it instead: an activation code, a one-time claim, nothing.
   - **What permission the caller must hold** is an `x-permission` extension, written in the
     annotation (`extensions(("x-permission" = json!(…)))`). Its value is a permission id
     (`"console.data.read"`), or a list of ids for an edge route that needs a different one
     depending on what it acts on, as `ROUTE_PERMISSIONS` lists them. An operation that needs only
     authentication carries none.
   - **Tests hold both to the code.**
     - The edge's `x-permission` values must equal `ROUTE_PERMISSIONS`, which stays the record.
     - Each console handler's `x-permission` must name the permission its `require_permission` call
       checks, read from the handler's source as the router's paths already are.
     - Every operation has a security requirement or `security: []` with an `x-public-reason`.

     A permission that only redacts part of a response (`console.reports.revenue` on a config read)
     goes in the description, not in `x-permission`.
6. **The TypeScript types are generated.** `openapi-typescript` is a pinned **dev** dependency of
   `ui/` and `dashboard/`, so neither ships it. A `pnpm gen:api` script writes
   `ui/src/api/generated/edge.d.ts` and `dashboard/src/api/generated/admin.d.ts`, each headed with
   the git blob id of the JSON it came from. `cargo xtask api-types --check`, in `just preflight`,
   compares that header with `git hash-object` of the committed JSON, so a document regenerated
   without its types fails with no Node in the gate and no new `xtask` dependency. `tsc`, already in
   each app's build, proves the types compile. The hand-written types are replaced module by module,
   with no behaviour change, and any that cannot be are listed with the reason at the top of the
   `types.ts` that keeps them.

## Consequences accepted

- **A backbone dependency, behind a feature.** `pos-proto`'s manifest names `utoipa`, and the
  `pos-proto` owner reviews the derives. Building `pos-proto --features openapi` compiles `utoipa`
  and its closure (`indexmap`, `hashbrown`, `equivalent`, `foldhash`); the default build does not.
- **The edge's annotations are written under `cfg_attr`.** That is noisier than a plain attribute,
  but it keeps `utoipa` out of the store binary. A plain `cargo build` of `pos-edge` does not check
  them; `cargo test` does.
- **Handlers get renamed** wherever `operationId` collides. These are edge-internal names, and no
  route changes.
- **The work is in slices** (P11 1b): the 17 cloud paths, then the edge about 20 routes at a time,
  then the device document, then security and `x-permission` everywhere, then schemas, then the TS
  types one module at a time. Each slice regenerates its documents through the tests, never by hand.
- **The route map, `docs/generated/route-map.md` (P11 item 5), is generated from these documents**,
  so a route is described in one place: its handler.
