# ADR-0122 — A store group is a delivery cohort, and a batch publish reports every store

**Status** Accepted · **Owner** @maintainers-cloud · **Last reviewed** 2026-09-10
**Relates to** [ADR-0033](0033-config-tree.md) (the four-level tree this deliberately does not extend, and whose closing "deliberately not here yet" this answers) · [ADR-0004](0004-cloud-owned-configuration.md) · [ADR-0066](0066-cloud-catalog.md) (the item master and menus that are already tenant-wide) · [ADR-0094](0094-console-optimistic-concurrency.md) / [ADR-0095](0095-conditional-writes-for-collections.md) (why the node publishes carry no precondition and the level write does) · [ADR-0074](0074-localization-and-tax.md) (the `tax` node a menu needs at the till) · [ADR-0106](0106-the-store-is-a-legal-person.md) and [ADR-0114](0114-region-is-required-recorded-visible.md) (the two nodes that cannot be batched) · [ADR-0109](0109-counting-the-taps-an-operator-makes.md) (the step budget the flows below are measured against)

**Context.** The owner asked how an estate is managed when *"cách quản lí hiện tại khá là thủ công và đơn lẻ từng store"* — the present way of managing is manual and one store at a time. An audit of the console answered it, and the answer was not the one the question implies.

**The data is already shared. Only delivery is serialised.** One `catalog_placements` row prices an item on a menu for the whole tenant — the table's primary key is `(menu_id, menu_item_id)` and it has no `store_id` column at all (`crates/adapters/store-postgres/migrations/0012_cloud_catalog.sql`). The same is true of the item master, tax rates, campaigns, reason codes and the inventory recipes. So the blast radius of an authoring mistake is *already* tenant-wide.

What is per-store is the **config tree**: `config_trees` is `PRIMARY KEY (tenant_id, store_id)` (migration `0004`), one `jsonb` document per store holding all four of ADR-0033's authored layers. And delivery follows the tree, not the data: `dashboard/src/api/client.ts` holds **16 publish helpers, every one of them taking a `store_id`**.

That is the worst of both arrangements — a shared master with no shared delivery — and it is what the measured costs are made of:

| Flow | Taps | Of which pure repetition |
|---|---|---|
| Publish one menu to 50 stores | 150 | 147 |
| Change one price and get it live in 20 stores | 65 | 60 |
| Push a tax-rate change to 12 stores | 37 | 34 |
| Flip one capability flag across *N* stores | 4*N* | 4(*N*−1) |
| Bring one new dine-in store to "sells correctly" | 19 publishes across ~12 screens | — |

ADR-0033 closes with, in as many words: *"**Deliberately not here yet:** a shared Tenant/Brand layer that fans out to every store under it is a future modeling step; today each store's tree holds its own four layers."* This record is that step — and it turns out not to need the shared layer.

**Decision.**

1. **A store group is a named, flat, tenant-scoped set of stores, and it is not the brand.** The registry already carries `stores.brand_id` (migration `0011`), and it was the obvious candidate. It is the wrong one. A brand is *identity* — which sign is over the door — and a store belongs to exactly one, whereas the cohorts an operator actually publishes to cut across it: the airport branches that run a reduced menu, the six shops in one city on one tax registration, the three pilot stores that take a change first. A store belongs to **one brand and any number of groups**. Groups do not nest: nesting buys a hierarchy nobody asked for and costs a resolution order that has to be explained on every screen that shows one.

2. **The group is a delivery cohort, not a fifth merge level.** ADR-0033's tree is untouched: still Tenant → Brand → Store → Device, still one row per `(tenant_id, store_id)`, still the same composition and the same `update_for`. A batch publish writes *the same document into N trees*, exactly as N individual publishes would have. Three reasons this beats a shared `Group` layer read at composition time. It keeps the store's sync hot path a single-row read, which is what ADR-0033's snapshot/delta decision is built on. It changes the effective document for *no* store, including every store in no group, so nothing about this record is wire-visible. And it is reversible: delete every group and the trees are byte-for-byte what they are today, because a group holds no configuration of its own.

3. **One batch route, over the node publishes that already exist.** `POST /admin/store-groups/{group_id}/publish` takes the node kind and that node's arguments, and calls the *same* per-store handler internals, once per member. Not 13 new routes, and not a second write path: the existing publish stays the only thing that touches a tree, so validation, the §10 capability rules, audit and the version append are inherited rather than re-implemented. The comment already in `client.ts` above `publishConfig` is what makes this safe — the node publishes "write one key of a layer and the server retries them around a competing write of a different key," and they carry no precondition, unlike the level write and the rollback, which do.

4. **13 of the 16 publishes are batchable; 3 are not, by construction.** The rule is mechanical: *a publish is batchable when its request body carries no store-specific argument.* That admits `capabilities`, `permissions`, `floor`, `tax`, `campaigns`, `channels`, `tender`, `origins`, `qr`, `vendor_policies`, `inventory`, `reason_codes` and `menu` — note that `floor` qualifies even though every store's floor plan is different, because the *instruction* ("recompile this store's own areas and stations") carries nothing store-specific. It excludes `locale`, whose `country_code` and `timezone` are per-store by definition and load-bearing under ADR-0114; `store_profile`, which is a store's legal identity under ADR-0106; and `publishConfig`, the generic level write, which replaces a whole layer under an `If-Match` precondition that only means something for one store.

5. **A batch is not atomic, and that is the decision, not a limitation.** Each store's tree is its own row, so an all-or-nothing batch would have to hold *N* row locks for the length of the fan-out, and its failure mode is the worst one available: nothing happened, at 200 shops, because of one. A partial success is both the honest outcome and a recoverable one — re-running the batch is idempotent for the stores that already succeeded, because a publish that produces an identical document is a no-op version. What must not be partial is the *reporting*.

6. **A batch is durable, and it names an outcome for every member.** Two tables (migration `0061`): `config_batches` holds one row per batch — a ULID `batch_id`, the tenant, the group, the node, the arguments as authored, the actor, and start/finish timestamps — and `config_batch_results` holds one row per `(batch_id, store_id)` carrying an outcome of exactly **`applied` | `skipped` | `failed`**, the resulting config version id when there is one, and the refusal's own message when there is not. Three outcomes because there are three real answers to "what happened at this shop", and a two-state report would file a store that was deliberately protected under the same heading as a store that broke. The per-store audit entries the existing handlers emit are unchanged; these tables are the batch-level view the audit trail cannot give, and they are what the group screen reads to show drift — a member whose last batch outcome was not `applied` is a store that is *not* running what its group runs, visibly, without diffing two documents.

7. **A store missing a prerequisite is refused before anything is written to it, and the batch carries on.** The concrete case that makes this non-negotiable: publishing a `menu` to a store whose tree has no `tax` node produces a shop that boots, syncs, shows the menu, takes the order — and then cannot close the bill, because `pos_core::billing` raises `DomainError::TaxRateNotConfigured` when no rate matches the line's tax class and channel. Nothing before the payment screen says so. A prerequisite failure is therefore a **`skipped`** with its reason named, per store, evaluated before the write; the batch continues to the rest. Seeded with two rules — `menu` requires the store's tree to hold `tax` and `locale`, and every node requires the store to be `active` in the registry — and extended as nodes acquire dependencies, in the same table as the node list so a new node cannot quietly arrive without an answer.

8. **A group holds at most 200 stores.** A batch runs synchronously inside the request and returns its report as the response body; at roughly 10–30 ms per store publish that is a handful of seconds at the cap. `docs/capacity-and-reliability.md` models tenants up to 1,000 stores, and such a tenant uses several groups — which is how an operator of that size already thinks (by city, by format, by pilot cohort). See the rejection below for why there is no job queue here yet.

9. **Same permission, same audit.** A batch publish is behind `console.config.publish`, the permission the single-store publish already requires; group CRUD is behind `console.stores.manage`. Group membership is itself a versioned write under ADR-0094 — two admins editing a cohort's membership is exactly the collision that record exists for.

**Rejected.**

- **The brand as the cohort** — rejected: one brand per store, and the sets operators publish to cut across brands (see decision 1). Brand stays what it is; a group may of course contain exactly the stores of one brand.
- **A fifth `Group` merge level inside the config tree** — rejected: it makes composition a multi-row read on the store sync hot path, it changes the effective-document semantics for every store in the fleet including those in no group, and it cannot be undone by deleting the groups. The shared-layer modelling ADR-0033 named as future work therefore stays unbuilt, deliberately, and this record supersedes the operational *need* for it rather than the idea.
- **An atomic batch** — rejected in decision 5. Recorded here because it was the intuitive answer and the owner asked directly.
- **Refusing the whole batch when any member fails a prerequisite** — rejected: it makes one un-configured shop block a fleet-wide price change, and the operator's remedy would be to remove that store from the group, which loses the record that it was ever meant to be in it. A per-store `skipped` keeps the membership and states the gap.
- **Composing at read time from a group document the store pulls** — rejected: it is decision 2's shared layer wearing a different hat, and it additionally means a store's effective configuration can change without any publish having happened, which the config version history (ADR-0069) would have no way to explain.
- **Thirteen batch routes, one per node** — rejected: thirteen places for the report shape, the cap and the prerequisite check to drift apart.
- **A background job queue for fan-outs above the cap** — rejected *for now*, and the trigger is named: build it when a real tenant needs one cohort of more than 200 stores. It is a scheduler, a retry policy, a progress endpoint and a failure-notification path — a machine considerably larger than the thing it would be delivering, and the `config_batches` row is already the durable record such a queue would need, so adding it later is additive.

**Consequences.**

*What an operator gets.* The four flows in the table above collapse to a constant. Publishing one menu to 50 stores becomes pick the group, pick the menu, publish — and then read a report that names all 50, rather than trusting that fifty repetitions of the same three taps all happened. The report is the part that matters and the part that does not exist today at any fleet size: right now a fan-out done by hand has no artifact, so "did every shop get the new price?" is answered by opening twenty screens.

*What this costs.* A second concept on the Stores screen, and a real risk that comes with it: a group makes it one action to be wrong at 200 shops. That risk was already present — `catalog_placements` has been tenant-wide since ADR-0066 and one bad price edit already reaches every store that later publishes — but it was slow, and slowness was doing some of the work of a safeguard. The prerequisite check (decision 7) and the durable per-store report (decision 6) are what replace it; a preview of the composed document before a batch is the obvious next safeguard and is **not** in this record.

*What is deliberately unfinished.* Group membership is a manual set — no rule-based membership ("every store in VN-South"), because a rule needs attributes the registry does not carry and would make the cohort change under the operator without a write. `admin_publish_rollout` (OTA) stays per-store and outside this record: it takes one `store_id` today, and rings are a cohort label *inside* a store's own node, so unifying the two cohort concepts is a separate decision and a wire-visible one. And the batch does not schedule: an effective-dated batch composes with ADR-0077's scheduled publishes and needs its own record.

*What does not change.* No wire type, no `PROTOCOL_VERSION` bump, no change to what any store receives or when. Every table is additive, and a fork that never creates a group behaves exactly as it does today.

**Tested by** `crates/pos-cloud/tests/cloud.rs` — the store-group section, which lands in the existing integration crate rather than the `store_groups.rs` this record first named, because the batch needs the same admin session, registry and config-tree fakes every other route test is built on and a second crate would have re-declared all of them. Its headline case is decision 5 stated as a property: one batch over three shops, one archived, one with no `tax` node and one ready, asserting that the third is published to regardless of the first two, that the two skipped shops were not written to at all, and that all three have a durable row. Beside it: an unpublishable instruction that records no batch and writes nowhere, an unknown node kind that lists the thirteen, the two refused cohorts (archived, empty), and the history read-back. `crates/pos-cloud/src/store_groups.rs` unit-tests the seam against its in-memory fake; `dashboard/tests/store-groups.test.tsx` pins the console half — the report renders one row per member, `skipped` and `failed` are drawn differently and quote the refusal's own sentence, a copy-from node refuses *before* the fan-out when its source has nothing to copy, and the picker offers exactly thirteen nodes.

**Delivered** on the branch that carries this record: migration `0061`, the `StoreGroupStore` seam with its `store-postgres` adapter, the four group-CRUD routes, `POST /admin/store-groups/{group_id}/publish` with the `BatchNode` registry over all thirteen node kinds, the two batch read routes, and the **Settings → Store groups** console screen. One departure from the plan above, in the console rather than the record: the six nodes whose value an operator types per store (`capabilities`, `channels`, `tender`, `origins`, `qr`, `vendor_policies`) are published to a cohort by *copying one named shop's current value* rather than by a second copy of each editor. The screen refuses before the fan-out when that shop has never published the setting — publishing an empty document to two hundred shops is the failure mode that choice exists to avoid.
