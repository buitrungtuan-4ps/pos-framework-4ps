# ADR-0080 — Channels & payments: author per-store channel enablement, accepted tender, QR guardrails, and vendor policy as config nodes

**Status** Accepted · **Owner** @maintainers-cloud · **Last reviewed** 2026-08-28
**Relates to** [ADR-0074](0074-localization-and-tax.md) (the `tax`/`locale` publish-only settings-node pattern this reuses) · [ADR-0071](0071-config-without-json.md) (the capabilities node + edge apply) · the QR ordering module (P11b: signed table tokens, guardrail `evaluate`) · [ADR-0053](0053-cloud-sync-port.md) and [ADR-0058](0058-shipping-adapters.md) (the marketplace/delivery surface) · `docs/pos-spec.md` §5 (channels), §19 (payments, purchasing) · `docs/cloud-admin-ux-plan.md` (Track M7)

**Context.** A store's *channels* and *payments* are effectively hardcoded. A sales channel is "enabled" only implicitly — by whether the menu/tax tables happen to carry a row for it — so an operator cannot turn delivery off for a store without emptying its delivery menu, and there is no authored, validated, visible enable list. The accepted **tender** set is fixed in the edge (`bills.rs::into_payment` refuses only an unspecified/unrecognised method, never a *disabled* one), so a cash-only store cannot say so. The **QR guardrail** engine is built and a `qr` config node is already *read by the cloud* (`qr_http.rs::qr_config_for`), but there is no authoring path (no publish route, no dashboard form) and the **edge never reads the `qr` node** — staff-confirmation is hardcoded to "any table-bearing QR order", and the cloud even computes `require_staff_confirmation` from the node and then discards it. **Marketplace vendor policy** (which vendors are on, per-vendor 86 lists, throttle/busy thresholds, prep-time defaults) has ports (`DeliveryVendor::{accept,reject,set_busy}`) but no authored policy — `set_busy` is driven only by the store being offline.

**Decision.** Add the M7 authoring surfaces as **publish-only per-store settings nodes**, in the exact `tax`/`locale`/`capabilities` shape: author in the console → `PUT /admin/config/<node>` composes the node and versions it through the config tree (behind `console.config.publish`, audited) → the edge applies it in `session_from_config`. No new authoring store, no migration, and no new console permission — these are settings a store publishes, like its locale, not a CRUD master-data domain (so, unlike campaigns/inventory, there is deliberately no `console.channels.manage`). The set of enabled channels and accepted tenders is small and stable; the source of truth is the published config, read back for the editor.

1. **`channels` + `tender` nodes** (this ADR, slices 1–2). `pos_proto::channels::{PublishedChannels, PublishedTender}` each carry a list of `Open`-wrapped enum tokens (`SalesChannel` / `PaymentMethod`). `pos_core::channels::{enabled_channels, accepted_tender}` build the domain sets, dropping unspecified/unrecognised. **Never-blank, opt-in:** an *absent* node means no restriction (today's behaviour exactly); a *present* node is authoritative. The edge gates repricing/intake on the enabled channel set and payment settlement on the accepted tender set, each with a clear refusal.
2. **QR guardrail authoring** (slice 3). A `config_qr_router` / `admin_publish_qr` composes the existing `qr` node from typed fields (enabled, staff-confirmation-required, per-table limit, rate window, business hours), and the edge applies the `qr` node so `staff_confirmation_required` finally drives the edge's staff-confirm instead of the hardcoded rule; the cloud QR path stops discarding `require_staff_confirmation`.
3. **Marketplace vendor policy** (slice 4). A `vendors` node authoring per-vendor enablement, busy-mode/prep-time defaults, and a per-vendor 86 (item-suppression) list, over the existing `DeliveryVendor` primitives.
4. **Console** (slice 5): a Channels & payments settings screen, a QR guardrail form editor, and a vendor-policy editor on the F2 kit.

**Deliberately deferred (flagged, not silently dropped).**

- **Live vendor-policy enforcement.** Authoring the vendor policy is this track; the runtime loop that pushes busy-mode/86 to a live marketplace from the policy (and reacts to store state) is store-side runtime work, the same shape as the campaign live-eval and inventory marketplace-notify deferrals. M7 delivers the authored policy and its edge/cloud read-back.
- **Card-terminal / hardware tender configuration.** Per-terminal routing, capture modes, and physical device pairing are gated on Track A A1 (hardware), out of scope here. M7 configures which *methods* a store accepts, not how a card terminal is wired.
- **Durable QR rate limiting.** The rate limiter stays the in-memory per-`(store,table)` nuisance guard it is today; the authored window/limit tune it, but a cross-restart durable counter is not part of this track.

**Consequences.**

- Additive throughout: new `pos-proto` and `pos-core` modules, new/extended config-node keys (`channels`, `tender`, `vendors`; `qr` extended in place), publish routes reusing `console.config.publish`. No protocol-version bump, no migration, no new permission. A store that never publishes a channels/tender/qr/vendors node behaves exactly as before M7 — the never-blank config contract keeps whatever the edge holds when a node is absent or unparseable.
- Channel and tender enablement, QR guardrails, and vendor policy are operational configuration (T2 where they touch commercial terms — vendor commission/policy — worked in the console, not reproduced verbatim). None carries a customer identifier or any T1 field.
- Because the domain sets and guardrail decision live in `pos_core`/the QR module and the nodes go through the same `CapabilityValidator` publish path, the cloud and edge cannot disagree about what a legal channels/tender/qr/vendors node is.
