# ADR-0027 — Country modules: a bundle, not an adapter, selected at compile time

**Status** Accepted · **Owner** @maintainers-architecture · **Last reviewed** 2026-08-18
**Amends** [ADR-0005](0005-country-neutral-core.md), [ADR-0013](0013-async-strategy.md)

**Context.** [ADR-0005](0005-country-neutral-core.md) settled the rule that matters — country
obligations live behind the `Fiscalization` port in per-country crates, and adding a country means
adding a crate rather than editing the core. That rule is not in question.

What it does not say is where those crates live, what else they carry, or **how a fork that wants
two countries out of five avoids compiling the other three**. `README.md` filed `fiscal-vn` under
`crates/adapters/` beside `store-sqlite` and `printer-escpos`, and that placement is a category
error with practical consequences.

A country is not one implementation of one port. Vietnam brings:

- a `Fiscalization` implementation (Viettel/VNPT/MISA, number ranges, submission rules);
- a **locale pack** — currency, date and number formats, receipt template requirements, and the
  channel-keyed tax rate table `docs/pos-spec.md` §5 requires;
- format validation the rest of the system cannot know — what a valid tax code looks like;
- a default personal-data retention period (`pos-spec.md` §11 makes it configuration *defaulting
  per country locale pack*);
- sometimes country-scoped vendor adapters. ShopeeFood exists in South-East Asia and nowhere else.

Filing that under `adapters/` says it is one thing when it is five, and it hides the unit a fork
actually adds or removes.

**Options considered for selection.**

1. **A fork deletes the directories it does not want.** Rejected, and it is the option people reach
   for first. It makes every upstream pull a conflict, forever, in the one place a fork most wants
   to stay current — because tax law changes and those fixes come from upstream.
2. **Everything compiled in, chosen at run time from a registry.** This is what
   [ADR-0013](0013-async-strategy.md) implies by saying a family member is added by "editing an
   enum or registry in the binary". Rejected for countries: the edge binary runs on a 4 GB mini-PC,
   and a store in Hanoi would carry Japanese and Indonesian tax code it can never execute. It also
   contradicts the requirement outright — "use a few instead of all" is not satisfied by shipping
   all and ignoring most.
3. **Cargo features on the binaries.** Chosen.

**Decision.**

*A country module lives at `countries/<cc>/`, at the repository root.* Lower-case ISO 3166-1
alpha-2, so `countries/vn/`, `countries/jp/`. Top level rather than nested under `crates/` because
it is the unit a fork adds, and because it holds more than a crate: receipt templates, translation
files, and test fixtures carrying real legal examples. A forker should find where their country goes
without reading a document.

*Each is a crate named `pos-country-<cc>` exposing one `CountryModule`.* That trait bundles the
locale pack with a factory for the country's `Fiscalization`, and it lives in a new `pos-country`
crate beside `pos-ports`. It is **not sealed**: a fork with a private country module — a proprietary
acquirer integration, an unpublished market — adds a path dependency and implements the trait from
outside this repository. A framework whose extension point only works for its own authors is not a
framework.

*Selection is a Cargo feature per country, named `country-<cc>`.* A binary's manifest reads:

```toml
[features]
default    = ["country-vn"]
country-vn = ["pos-country-vn"]
country-jp = ["pos-country-jp"]
```

So a fork serving only Vietnam edits **one line** and deletes nothing. Nothing else is compiled, so
nothing else is linked, and `cargo tree` tells the truth about what a store is running. CI builds
with `--all-features` so every country stays compiling, and the country registry is generated by a
macro over the enabled features rather than hand-maintained — a list somebody updates by hand is a
list that will disagree with the manifest.

*Feature unification is safe here, and this is the one place it is.* [ADR-0013](0013-async-strategy.md)
rejected feature-gating for `pos-ports` because Cargo unifies features across the graph, so a
gate would be documentation rather than a guarantee. That reasoning does not transfer: there is no
rule that Japanese tax code must be *unnameable* from a Vietnamese build, only that it must not be
*compiled into* one. Unification makes the union of enabled countries available, which is exactly
the intent.

*Countries and vendor families are different mechanisms, deliberately.*

| | Countries | Vendor families |
|---|---|---|
| How many active at once | **Exactly one.** A cell is one country ([ADR-0011](0011-country-in-hostname.md)) | Several. A tenant sells on Grab *and* ShopeeFood |
| Chosen | At compile time, by feature | At run time, from configuration |
| Mechanism | `CountryModule` registry over enabled features | The object-safe mirrors in `pos_ports::dynamic` |

ADR-0013's "edit an enum or registry in the binary" was written for the second column and is
correct there. Applying it to the first was the mistake this record fixes.

## The boundary: country module or configuration tree?

`docs/pos-spec.md` §5 places the tax rate table "in the store's locale pack" **and** names the
configuration key `store.tax.tax_class_rates`. Both, which reads as a contradiction and is not.

**The country module ships what the law says. Configuration overrides it.**

| Belongs to the country module | Belongs to the configuration tree |
|---|---|
| Currency | Which `tax_class` each menu item carries |
| Default channel-keyed tax rate table | An override of that table for one store |
| Invoice number format and its legal lifecycle | Whether tips and service charge are enabled |
| Tax-code format validation | The store's timezone |
| Default retention period | The retention period actually chosen |
| Date and number formatting, plural rules | Receipt header text, logo, and footer |

Two reasons the override exists rather than making the country module authoritative. A store may sit
in a special economic zone with a rate its country's default does not describe. And a legislative
change can land before a release ships — an operator must be able to correct a rate without waiting
for a build, because the alternative is charging the wrong tax legally.

Two reasons the country module holds the default rather than leaving it all to configuration. A
fresh store is then correct without anybody typing a rate table, which is the difference between a
fork that works and a fork that works once configured by somebody who knows Vietnamese tax law. And
an override is visible as an override, so "why is this store charging 8%?" has an answer.

**Timezone is configuration, not country.** Indonesia spans three and the United States spans six,
so a country-level timezone would be wrong in the countries where it mattered most.

## Consequences

- A fork selects countries by editing one line and never deletes a file, so pulling upstream tax
  fixes stays a fast-forward.
- The edge binary carries only the country it serves. On a 4 GB mini-PC that is not a nicety.
- `countries/` is a visible extension point, and `countries/zz/` is a compiled, contract-tested
  reference module rather than a documented aspiration. `ZZ` is CLDR's unknown region, so it can
  never collide with a real country.
- Cost: adding a country touches three files — its own manifest, the workspace members, and the
  binaries' feature lists. Deliberate and reviewable, and CI fails a country that is added to the
  workspace and to no feature list, so the third edit cannot be forgotten silently.
- Cost: a deployment serving two countries from one binary is possible (both features on) but is not
  the supported shape, because [ADR-0011](0011-country-in-hostname.md) puts each country in its own
  cell for legal reasons. The features compose; the deployment model still says one country per cell.
- `docs/roadmap.md` P10 keeps `fiscal-vn`, but it now fills in a shape that already compiles and
  already passes the `Fiscalization` contract suite, rather than inventing one at the point where a
  tax authority is waiting.
