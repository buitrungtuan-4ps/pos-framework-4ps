# ADR-0123 — A superseded box opens nothing new, and finishes everything it holds

**Status** Accepted · **Owner** @maintainers-architecture · **Last reviewed** 2026-09-10
**Answers** [ADR-0108](0108-the-lease-generation-is-authority.md)'s first "what this deliberately does not do", and with it [ADR-0049](0049-single-active-lease.md)'s P9e assignment
**Relates to** [ADR-0025](0025-receipt-number-authority.md) (the gapless counter this record deliberately does not fix) · [ADR-0055](0055-edge-ota-updater.md) (the install gate whose verdict this record deliberately diverges from) · [ADR-0111](0111-a-second-origin-may-address-the-edge.md) (the response header this borrows, and the CORS exposure it needs) · [ADR-0004](0004-cloud-owned-configuration.md) / ADR-0039 (the config-pull loop that learns the generation) · [ADR-0001](0001-offline-first-store-autonomy.md) and [ADR-0024](0024-protocol-version-negotiation.md) (a store keeps selling; a mismatch degrades to "not syncing", never to "not selling")

**Context.** ADR-0108 gave the edge a real lease standing — `pos_core::lease::lease_standing(held, authoritative)` over a generation the box takes **once** (`crates/pos-edge/src/lease_state.rs`, migration `0008_lease.sql`) and a generation the cloud publishes in the derived `lease` node. It then wired that standing to exactly one consumer: the OTA tick, which refuses an *install* for `Superseded | Invalid` (`crates/pos-edge/src/ota.rs:228`). It closed by naming what it had not done, in as many words:

> **It does not stop a superseded box selling.** `Superseded` refuses an *install*, and that is all. Read-only selling is ADR-0049's P9e assignment and touches every write path in `pos-edge::app`, with a far worse failure mode if it fires wrongly — a shop that cannot take money is a worse outcome than a shop running last week's binary. It wants its own slice, its own operator-visible refusal, and its own way back. Naming it here keeps its absence a decision.

This is that slice. So today a machine an operator has deliberately replaced goes on taking orders, minting receipt numbers and settling bills as though it were still the store — and the only thing the whole single-active-lease mechanism actually stops it doing is installing an update.

The hard part is not detecting the state. It is choosing *which* refusal, because the cost of firing wrongly is a shop that cannot trade. ADR-0108's own sentence is the brief, and it names three things this record must produce: a refusal, an operator-visible one, and a way back.

**Decision.**

1. **A superseded box opens nothing new. Everything already open runs to settlement.** The gate is on *creating* an order or a shift, and on nothing else. **Three** commands refuse — `Edge::open_shift`, `Edge::seat_table` and `Edge::open_inbound_order` — and every other command on `Edge` runs unchanged, including `add_line`, `fire_line`, `bump_ticket`, `confirm_inbound_order`, `reject_inbound_order`, `void_line`, `void_bill`, `open_bill`, `open_bill_for_order`, `settle_bill`, `clean_table`, `count_shift` and `close_shift`.

   This is a much narrower gate than "read-only selling" sounds, and the narrowness is the decision. A seated table's guests order in waves; refusing `add_line` would leave a table that can neither be completed here nor moved to the replacement, because the order lives in *this* box's log. So the floor **drains**: each open table takes its second round, gets its bill, settles and is cleaned — and cannot be seated again. The counter opens no new order. The relay takes no new channel order. The shift can be counted and closed, and not reopened. By the end of service the box holds nothing, and there is nothing left for it to do wrong.

   The rule is mechanically checkable, which is why it was chosen over a hand-curated list: **the three refused commands are exactly the three sites in `crates/pos-edge/src/app.rs` that mint an `OrderId` or a `ShiftId` from nothing** — the two calls to `next_order_id` and the one `ShiftId::new`. A fourth such site cannot be added without the grep that finds them changing, and the reviewer's question at that point is a one-liner: does this open something? `add_line` needs an order the projection already knows (`AppError::NoOpenOrder`), so it is gated transitively rather than by a second rule that could drift from the first; `confirm_inbound_order` is allowed for the opposite reason — the order it admits is already in *this* box's ledger, and refusing it would strand a guest whose order exists nowhere else.

2. **The gate fires on `Superseded` and not on `Invalid`, deliberately differing from the OTA gate beside it.** `Invalid` means the box holds a generation *ahead* of what the cloud published. Under take-once the likeliest cause is not a second machine — it is a **config rollback**, which can move the published node backwards even though it cannot move the cloud's `store_lease` row; `lease_state.rs`'s own test `a_generation_behind_what_the_box_holds_is_invalid_for_everyone` says so. Refusing to open orders on `Invalid` would therefore turn an admin clicking "roll back" on the Config screen into a store outage, and it would fire on **every** box in that store at once — which cannot be the right answer to "one of you is not the store". `Invalid` keeps trading, is logged, and reaches the console through the generation the heartbeat already reports (ADR-0108). Refusing an *install* on `Invalid` stays right for the same reason it always was: nothing is lost by not installing.

3. **The standing is a shared cell the config-pull loop writes and everything else reads.** `Arc<LeaseStanding>` in the shape `Origins` and `Pairing` already have — interior mutability, one `Arc`, written by the loop and read by the request path — because the reasons are identical and a second shape would be a second thing to reason about. `Edge` holds it and the four commands read it; `AppState` holds the same `Arc` so the HTTP layer can stamp it; the config-pull loop holds it and writes it on every pull, because that loop is the one thing that learns the authoritative generation. The loop takes the box's own lease as `Arc<dyn HeldLease>` — the narrow, dyn-safe view of `LeaseAuthority` that answers one question, "given this published generation, what am I?" — for the same reason it already takes `Arc<dyn DurableAuth>` inside `DeviceRevocations`: `LeaseAuthority` returns `impl Future` and cannot be a trait object, and a type parameter on `ConfigClient` would reach every test that builds one.

   Not the OTA tick and not the heartbeat, though both already hold a `LeaseAuthority`. A box with no rollout published never runs an OTA decision, and a heartbeat is a *reporter*; hanging the store's trading posture off either would make the gate depend on a loop that can legitimately be idle.

4. **A lease that cannot be read never demotes a box, and never promotes one.** The config-pull loop's write is skipped on error and the previous standing stands — the never-blank rule the same loop already applies to every config node. A SQLite hiccup must not stop a shop seating tables, and it must not un-supersede a box that has already been replaced either. `standing()` already refuses to answer `Active` on an unreadable lease (ADR-0108); this is the other half of that sentence, on the side where the failure costs money.

5. **The refusal is visible before it is hit.** A `403` on the tap that seats a table is a refusal an operator meets *after* deciding to seat it, and it says nothing about why this till and not the one beside it. So the standing rides every `/api/*` response in a `pos-lease-standing` header, exactly as ADR-0111 put the release version there and for the identical reason it gave — a supersession happens *during* service, so a value read once at pairing time is a value that was true once — and the store app draws a persistent banner from it: this till has been replaced, finish and settle what is open here, take new orders on the new machine. `GET /api/session` carries the same value in its body, so the state is answerable by a support engineer with `curl` and not only by a browser. `Invalid` draws its own, quieter banner: this box thinks it is ahead of the cloud, which is a thing a person should look at and not a thing the shop should stop for.

6. **The way back is to re-provision the box, and there is no other.** `LeaseAuthority` has two operations and no setter, and its own doc says why: *"a machine that must legitimately hold a newer one is a machine being re-provisioned, which starts from a fresh database."* This record does not add a local override and does not add a cloud "un-supersede" — either one would let two machines sell as one store, which is the single invariant ADR-0049 exists to hold. The banner therefore names the remedy rather than offering a button, and [`docs/guides/bring-a-store-online.md`](../guides/bring-a-store-online.md) is where the procedure lives, because the way back *is* provisioning: drain the floor on the old box, close its shift, let its outbox drain ([ADR-0117](0117-a-headless-store-keeps-a-log.md), roadmap D8), and provision it again from scratch if it is going back into service.

7. **Activating a box forgets any lease generation it inherited, and that is what makes decision 6 survive contact with the guide.** Take-once was meant to bind a generation to a *box*; it actually binds it to a **disk**, and the two differ the moment somebody moves the disk. `docs/guides/bring-a-store-online.md` tells an operator replacing a dead machine to do exactly that — copying `store.sqlite` across is the only way to recover events the old box committed and never published, because ADR-0046's edge half is unbuilt. Without a fix, the replacement boots holding the *dead* box's generation, reads itself `Superseded`, and this record's gate refuses to seat a table **on the machine that just replaced the broken one**: precisely the "fires wrongly" failure ADR-0108 spent a paragraph declining to risk. `LeaseAuthority` therefore gains a third operation, `forget`, and activation is its only caller — the one moment "this disk is now a different machine" is a fact rather than a guess, because the box is being issued its own cloud credential and a box that already holds one is refused a second activation. It is not a setter: it cannot name a generation, and the next pull takes the store's current one as a first sight. Nothing else in the tree may call it.

   The order the guide now states is load-bearing and was not before: **bump the lease, then activate the replacement.** The other order leaves the new box holding the generation it took before the bump, and it supersedes itself on the next pull — correctly, because a bump means "the machine changed" and the operator has just said that about the machine now trading.

8. **`open_inbound_order`'s refusal is `unavailable`, not a failure.** The relay pulls orders from the cloud and acknowledges what it accepted; a superseded box must leave a channel order **queued for the replacement**, not consume it or fail it. So the `OrderIn` refusal is `PortError::unavailable`, which is the vocabulary for "not from here, ask again", and not the `internal` that `port_error_from_app`'s catch-all would have produced. An order the guest already paid a marketplace for must not be dropped because the shop swapped a machine.

**Rejected.**

- **Gating at `EventStore::append`** — the tempting single chokepoint, and wrong twice over. It fires *after* the decision, so the refusal arrives as a write failure rather than as an answer; and it cannot tell a new order from a settlement, so the only gate it can express is "write nothing", which is the total refusal decision 1 exists to avoid.
- **Full read-only selling — refusing every write** — rejected on ADR-0108's own ground: a shop that cannot take money is worse than a shop running last week's binary, and a box that cannot settle strands the guests already eating on it. "Read-only" was the shorthand in ADR-0108's prose; the honest shape it points at is decision 1.
- **Refusing `settle_bill`** — rejected, and it is the closest call in this record. Settling allocates a gapless receipt number (ADR-0025) that the replacement box will also allocate, so allowing it does duplicate identifiers across the two machines. It is allowed anyway because the alternative is a table of guests who cannot pay, and because the duplication is **not created here**: a replacement starts from a fresh database and restarts that counter from the beginning whether or not the old box settles another bill. Naming it as residue below rather than pretending the gate solves it.
- **Treating `Invalid` like `Superseded`, matching the OTA gate** — rejected in decision 2. Symmetry with the install gate is worth less than not converting a config rollback into a fleet-wide outage.
- **Leaving the copied-disk hazard to the guide** — rejected. The first draft of this record fixed decision 7 with a sentence telling the operator to clear the row by hand. An instruction to run SQL on a shop's database at eight on a Saturday, while the till refuses to seat tables, is not a way back; it is a way to lose the data the copy existed to save.
- **A local override at the till** — rejected in decision 6. An operator who can un-supersede a box can put two machines on one store, and there is no message that makes that safe.
- **Refusing at the HTTP layer, per route** — rejected: it would state the rule in four route handlers instead of one application-layer check, leave the relay's intake path (which is not a route) ungated, and put a trading decision where a request gate lives.
- **A `ServerMessage` variant pushed over `/ws`** — rejected for now: the fan-out is a wire type in `pos-proto` and a new variant is a protocol question, where a response header is additive and already has a reader. If the banner's latency ever matters more than that, the header is not in the way.

**Consequences.**

*What changes for a shop.* Almost nothing, until the day someone bumps its lease. A store that has never been issued one reads `Active` and is untouched — that is every store today, and it is the same "safe to ship to a fleet that has never had it" property ADR-0108 built. On the day a replacement is activated, the old box stops being able to seat a table and says so on every screen.

*What it costs.* **Bumping a store's lease is now a trading decision, not only an OTA one.** It was already behind `ConsolePermission::ManageStores` with an audit entry (ADR-0108), and the console's replacement handoff is where it is made; but an operator who bumps the lease before the new machine is physically on the counter now has a shop that cannot seat its next table. The banner is what makes that legible in the thirty seconds after it happens rather than at the next tap; the guide is what should stop it happening at all.

*What it is worth.* ADR-0049's highest-level safety property — one store, one active machine — stops being a pure function with one caller and becomes something a replaced machine can actually feel. `production-readiness.md` **R4**'s remaining "deliberately not done" half closes; its other half, the invoice range, stays where ADR-0049 put it.

*What does not change.* No wire type, no `PROTOCOL_VERSION` move, no migration, no new dependency, no port. One response header is added and exposed across an origin the way `pos-edge-version` already is; one string field is added to `GET /api/session`'s body; both are additive.

**What this deliberately does not do.**

- **It does not stop two machines minting the same receipt numbers.** ADR-0025's counter is per-store and lives in the box's own SQLite, so a replacement restarts it. Draining the floor shortens the overlap to one service rather than removing it, and the real fix is the disjoint invoice range ADR-0049 assigned to `Fiscalization` and P10 — where `LeaseGrant::invoice_range` and `issue_replacement` are still sitting, written and unwired. Naming it here keeps its absence a decision, in the same words ADR-0108 used about this record.
- **It does not reconcile the two boxes' event logs.** Both drain their outboxes to the same store's stream, and both are legitimate history; the cloud's ingest is idempotent by event id (ADR-0045) so nothing is lost or double-counted, but a report over the swap day covers two machines' work and nothing marks the seam. A `device_id` is on every envelope, so the data to draw that seam exists.
- **It does not gate the print agents, the pairing routes or the device-admission events.** A superseded box that still has open tables still needs to print their bills and still needs to retire a device the console revoked. None of them opens an order.
- **It does not decide what the *replacement* does about the old box's open tables.** They are not visible to it, and moving them would mean moving an event log. In practice the old box finishes them, which is exactly what decision 1 leaves it able to do.

*How this was found.* Not by review: an audit of every `Edge` write command, run one command per agent against the tree, turned it up while arguing about `record_activation`. Fifteen of the twenty-two commands were classified independently before the run stopped, and all fifteen agreed with the gate as built — including `add_line`, the closest call. The copied-disk hazard was the one thing the reading found that the design had missed, and it was a shop-down bug.

**Tested by** `crates/pos-edge/tests/superseded.rs` — the three refusals and, more importantly, the far longer list of things that still work: a table seated *before* the supersession takes another round, fires it, bills it and settles it on a box that will not seat a new one. Beside it: `Invalid` seats a table (decision 2, the one a wrong answer turns into an outage); an unreadable lease changes nothing in either direction (decision 4); a channel order refused by a superseded box comes back `unavailable` so the relay leaves it queued (decision 7). `crates/pos-edge/src/lease_state.rs` unit-tests `HeldLease` over the in-memory twin; `crates/pos-edge/tests/config_client.rs` pins the wiring that made every earlier version of this decorative — **a pull settles the cell** — and that a loop composed without a lease leaves it alone. `crates/pos-edge/tests/activation.rs` plays out decision 7's scenario end to end: a box built from a copied disk reads `Superseded`, activates, and is trading again — with the durable row gone, so the next pull cannot undo it. `crates/pos-edge/tests/edge_version_header.rs` pins the `pos-lease-standing` header, its absence on `/healthz`, and its CORS exposure.
