# Architecture

**Status** Accepted · **Owner** @maintainers-architecture · **Last reviewed** 2026-08-18

How the system is built, and why each choice was made. Business behaviour is in [pos-spec.md](pos-spec.md).

---

## 1. Four principles

1. **The store is autonomous.** Every sale, print, and payment completes inside the store's LAN. The cloud is for administration, synchronisation, and reporting. If the internet disappears for a week, the store keeps trading.
2. **One binary per tier.** `pos_edge` at the store, `pos_cloud` in the cloud. Both are modular monoliths: internally split into modules with clear boundaries, externally a single static executable. No microservices, no runtime to install.
3. **Machines are cattle, not pets.** A store PC is a replaceable unit. Swap the hardware, enter an activation code, and the replacement is trading in 5–10 minutes.
4. **Configuration lives in the cloud.** Menus, prices, printers, roles, tax rules, feature flags — all of it is owned centrally and pushed down. A store never holds authoritative settings.

## 2. Store tier (`pos_edge`)

Runs as a Windows service or systemd unit on an ordinary PC or mini-PC.

| Concern | Implementation |
|---|---|
| Storage | SQLite in WAL mode, in-process. No database server to install or patch on 1,000 machines. |
| UI | SolidJS bundle embedded in the binary (`rust-embed`), served over the LAN. Clients are browsers. |
| Realtime | WebSocket push to every client: new lines, kitchen bumps, sold-out flags appear in under 50 ms. An item marked sold out or brought back is in what the edge serves before any device is told, so the price book a till reads again on hearing it already answers it. **A device whose link drops resumes where it left off.** Every frame on `/ws` carries the fan-out's `stream_id` and a `sequence`. A device that reconnects names the last one it applied (`/ws?stream_id=…&after_sequence=…`), and the edge sends every frame after it before carrying on live. The frames come from the last 1,024 kept in memory, one buffer shared by every device (about a megabyte). When the edge cannot replay, it answers `resync` and the device re-reads what is open, as a device that fell behind always has. That happens when the frames have gone, when the position is from before a restart (a restarted edge starts a new stream), or when the device can name no frame (`after_sequence` alone). A device that names nothing is served live, as before, but the till never connects that way: a socket that holds no position, which is every first connect, asks from nothing (`after_sequence=0`) and reads what is open once the edge says `resync`. A till's first socket is refused until it pairs, so the one that succeeds can open after the till has read the store and been used, and what was sent before it was subscribed would otherwise never reach it. While a `resync`'s reads are out, the till holds the frames that arrive and applies them once the reads settle, so a read answered before a change cannot undo it. Resuming across a restart, from the durable log, is roadmap-v3 **B6.5**. When the edge applies a new store configuration it sends `config_applied`, and each open till re-reads its floor, menus, layout, locale and reason codes without a new sign-in ([ADR-0160](adr/0160-everything-a-store-runs-differently-is-published-configuration.md)). The frame names the top-level nodes that changed (`changed_nodes`), except on the first configuration an edge applies after it starts. Those five reads each carry a weak `ETag` and `Cache-Control: private, no-cache`, and a read whose `If-None-Match` names the current tag gets a `304` with no body ([ADR-0173](adr/0173-the-till-declares-each-piece-of-store-data-once.md)). |
| Devices | ESC/POS printers (USB or LAN), cash drawers, payment terminals, barcode scanners. |
| Discovery | Publishes `pos.local` via mDNS. Clients pair by scanning a QR code containing `http://<ip>/pair?...`, or by typing `IP:port` plus a 6-digit code the store server writes at boot — to `pairing-url.txt` in its state directory on Windows, and to its log (`journalctl -u pos-edge`) on Linux. A store server is a headless service and has no screen ([ADR-0117](adr/0117-a-headless-store-keeps-a-log.md)). |
| Durability | Every sale is a transaction. Events land in a local outbox table before anything is sent anywhere. |
| Integrity | Every event carries `seq` and the hash of the one before it, so an edited or deleted record breaks the chain. The store verifies its own chain with no internet, and publishes its head to the cloud at each shift close as `store.chain.anchored` ([ADR-0131](adr/0131-a-chained-event-log.md)). The cloud files every anchor, one head per chain length per store, and **refuses one that contradicts a head it already holds** — which closes **recomputation**. It then **recomputes the chain from its own copies** of the events that anchor covers ([ADR-0132](adr/0132-the-cloud-recomputes-the-chain-it-holds.md)), which closes **truncation**: a store cut back and then traded on anchors *above* anything the cloud holds and looks like honest growth, but leaves two different events claiming one `chain.seq`, and the events say what the anchors cannot. A store hashes each record before the cloud stamps its owner on it ([ADR-0101](adr/0101-the-cloud-stamps-the-tenant.md)), so the cloud hashes its copy both as it holds it and with the tenant and brand put back to the nil ones a store writes; either matching is the store's own hash, and an edit to anything else still breaks the link. A missing record is reported as *incomplete* and never as tampering — a broker gap is ordinary, and [ADR-0040](adr/0040-reconciliation.md) exists to fill it. The guarantee reaches back to the **last anchor**, not the last event. Every refusal is listed on the console's **Chain integrity** screen (`GET /admin/chain-findings`), because a mechanism whose product is being noticed is worth little if nobody can see what it noticed. Tamper-**evident**, never tamper-proof: it makes what somebody did visible, it does not stop them. |

**Order writes are append commands.** Two devices adding items to the same table produce two commands that merge; they never overwrite each other. Edits to the *same line* merge with **terminal states winning** — a `VOIDED` or `SETTLED` line is never overwritten by a later edit — and other fields resolving last-writer-wins on `(event_time, device_id)`; both versions stay in the audit log. The merge is commutative and associative, so sync order cannot change the result ([ADR-0029](adr/0029-append-command-merge-semantics.md)).

## 3. Cloud tier (`pos_cloud`)

Four containers on a single VPS: `pos_cloud`, PostgreSQL, NATS, Garage (S3-compatible). An optional `monitoring` profile adds VictoriaMetrics and Grafana.

| Concern | Implementation |
|---|---|
| Transport | Stores dial out only, which solves 4G and CGNAT without port forwarding or VPNs. Events travel over **HTTPS** to the cloud's `/sync` surface by default, authenticated by the box's own device credential and acknowledged only once ingested ([ADR-0143](adr/0143-the-device-credential-syncs-and-events-travel-over-https.md)); a deployment that runs **NATS JetStream** can publish there instead. |
| Database | **PostgreSQL**, partitioned by `store_id`, row-level security per tenant, JSONB for flexible payloads, and **rollup tables** so every dashboard query is a small aggregate read (<10 ms). |
| Objects | **Garage** (or MinIO) for backups and OTA artifacts. |
| TLS | Caddy obtains and renews Let's Encrypt certificates. Later this is absorbed into `pos_cloud` via `rustls-acme`, removing a process. |
| Identity | Self-implemented auth: Argon2 password hashing, TOTP second factor, per-tenant API keys with scopes. |

### 3.1 Configuration tree

```
Tenant ─► Brand ─► Store ─► Device
   each level inherits from its parent and may override
```

Changes are versioned and shipped as deltas. A store applies a new version in under a second (hot reload) with no restart. If a delta cannot be applied, the store keeps the last known-good version and raises an alert. A store that has been offline too long, or has fallen too far behind, pulls a **full snapshot** instead of replaying deltas.

A value a store may run differently is a **setting**, listed in [`configuration.md`](configuration.md) ([ADR-0160](adr/0160-everything-a-store-runs-differently-is-published-configuration.md)). Its values are kept per scope in `setting_values`: the tenant, a brand, a store group or one store. A store runs the value of the most specific scope that sets one. The order is the store, then its store groups (the value written last, if two disagree), then its brand, then the tenant. A store with no value runs the default. The console writes a value with `PUT /admin/settings`, and every store it reaches is republished in the same request. A value its register entry marks as needing a recorded confirmation is written only with `notice_confirmed: true`, and its `setting.set` audit entry records the confirmed notice's key with who wrote it and when ([ADR-0169](adr/0169-a-setting-value-can-require-a-recorded-confirmation.md)). No other write can make a store start running such a value: a layer write (`PUT /admin/stores/{store_id}/config/{level}`), a rollback and a node publish, single or in a batch, are refused with `400` and the setting's key as `CONFIRMATION_REQUIRED`, a release is refused the same way when it is scheduled, and a scheduled publish that would do it when it comes due is not applied and records why on its row. A write that leaves such a value as the store already runs it passes. The store's resolved values are written onto its tree's **Tenant** layer, where they merge field by field with the nodes the console publishes on the Store layer. A store that moves to another brand or store group is republished with `POST /admin/settings/publish`. A store the console creates is given the owner's new-store values with `POST /admin/settings/presets`. Each setting's value there is the store's country pack's, when the store's published `locale` names a country whose pack gives one (`CountryModule::setting_defaults`, [ADR-0183](adr/0183-a-country-pack-seeds-a-new-stores-settings.md)), and otherwise the register's preset; as before, only a setting the store does not set at its own scope is written, at that scope. A value a pack gave records the pack's country as `pack_country_code` in its stored document, which needs no migration as the row keeps the value whole in `doc`; the console's write of a pack's value on Store settings sends it too, and it is kept only when that pack gives the setting that value. Any other write leaves it absent, so a person's save makes the value theirs. A store with no published locale is given the presets alone.

A **rollback** restores a past version by writing its whole document onto the Tenant layer and emptying the other three, so the store runs exactly that version. The console's node forms (channels, tender, origins, QR guardrails, event retention, vendor policies) and its checks before a publish (a node's prerequisites, a release's timezone) read a node as the store runs it: from the four layers composed, so after a rollback they read what was restored, and a node's own fields on a tenant or brand layer are read with the store's. They leave out the node's settings fields, which only the settings write, so a node holding nothing but settings reads as unpublished. A device revocation and the OTA kill switch act on what the store runs too: after a rollback a revocation keeps every device the store had retired, and the kill switch halts the restored rollout. Both read it on the tree they write over, inside the publish's conditional-write retry, so a publish that lands while one is in flight is kept: a device retired meanwhile stays retired, and a rollout published meanwhile is the one the kill switch halts.

A **fee** a bill may add, such as a service charge or a packaging or delivery fee, is configuration too ([ADR-0159](adr/0159-a-fee-is-configuration.md)). Its rules are kept per scope in `fee_rules`: the tenant, a brand or one store, one row per rule and scope, keyed by the rule's `fee_id`. A brand's or a store's rule replaces the tenant's with the same `fee_id` for the stores it reaches. The console writes a rule with `PUT /admin/fees`, or `POST` for a new fee, and every store it reaches is republished in the same request: the store's rules are resolved, an item category a rule names is compiled into the items it holds, and the list is written whole as the `fees` node on the store's **Store** layer, as the `integrations` node is. A store that moves to another brand is republished with `POST /admin/fees/publish`, and one whose rules name a category that has gained items with every menu publish, which writes the store's `fees` node in the same version as its `menu`, composed on the tree it writes.

Employee PINs sync down as hashes so login works offline. A store's staff, what each may do — alone, or with another person's code and PIN for each act ([ADR-0158](adr/0158-the-till-enforces-each-persons-own-permissions.md) decision 4) — and those hashes are one node, `permissions`, which a publish writes onto the store's tree; removing an assignment, archiving a person or archiving a role publishes it to every store the change reaches at once, so offboarding never waits for someone to press publish ([ADR-0158](adr/0158-the-till-enforces-each-persons-own-permissions.md) decision 7). Nor does a migration that changes what roles grant: it queues every store whose configuration holds a `permissions` roster (a `staff` list), wherever a rollback left it, and the cloud publishes their people again by itself, at start-up and then every few minutes, giving a store whose node is already current no new version ([`pos-spec.md`](pos-spec.md) §9). Printers and displays follow a *store discovers → admin approves* flow: the store reports what it found on the network, and an administrator assigns roles from the dashboard.

A **package** is a tenant's versioned bundle of screens, flows, rules and data definitions ([ADR-0189](adr/0189-a-store-runs-a-package-version-hq-pins.md)). HQ creates a package with `POST /admin/packages` and publishes a version with `POST /admin/packages/{package_id}/versions`, whose body carries the version's label, `time_slots`, `data`, `screens`, `flows` and `reactions`. `POST /admin/packages/{package_id}/versions/dry-run` takes the same body and runs the publish's own checks without storing anything (ADR-0190 decision 8): it answers `200` with `accepted`, the `min_edge_version` the publish would compute, and `refusals`, the first fault the checks meet, each with its `field`, a stable `reason` token (a publish's code, or for a screen what is wrong with it, such as `MISSING_PROPERTY`) and, for a screen, its `screen_index` in `screens`, its `node_index` in the tree's pre-order and the property or parameter it names; for a flow, its `flow_index` in `flows`, the `step_id` at fault (a cycle names its first step) and in `name` the id, action, screen or prerequisite it names; for a reaction, its `reaction_index` in `reactions` and in `name` the id, target, action or parameter. A refusal about the flows or reactions together (too many flows, too many reactions to one trigger) has no index. The publish and the dry run share one function, so a draft the dry run accepts is one the publish accepts, but for a version published in between. All three need `console.packages.manage`. A version is kept in `package_versions`, tenant-scoped under RLS like the catalog, and is stored once: the store has no update and no delete, and the role tenant queries run as is granted neither. The server mints the version's id and computes its `min_edge_version`: the latest of the release that introduced the `package` node, the one that checks a data part when the version has one, and the `since` of every component and act its screens name and every act its flows and reactions run. It refuses content over 1 MiB, and content `pos_core::package::check_content` refuses: a blank label, or a time slot that is malformed, repeated or has a window that is not whole. Its flows and reactions are checked as the edge checks them on apply (`pos_core::flow::check_flows`, `pos_core::reaction::check_reactions`), each variant alone and then together, with every condition compiled by `pos-rules` in the dialect of ADR-0193 and an edge guard reading only the views the edge holds (`pos_rules::Variable::EDGE`). A step's or a reaction's screen is not resolved, as on the edge, because a screen the version does not declare is drawn from the release's default package. Then every translation key the version names (a time slot's name, a screen's translation-key properties as the component catalogue types them, and the data part's field, unit, consent purpose, object type, list and list entry labels) needs a non-empty `en` value in the tenant's grid (ADR-0190 decision 6, `pos_core::package::check_keys`), as a receipt template's keys do; a key without one is refused with `UNKNOWN_TRANSLATION_KEY`, its field, and in `name` the key, and for a screen its `screen_index` and `node_index`. Only the cloud runs this check, as the grid an edge holds may be older than the version. The store runs the version pinned on its `package` node (`pos_proto::package::PublishedPackage`): `PACKAGE_MODE_LOCKED` with `locked_version_id`, or `PACKAGE_MODE_CHOOSE` with `allowed_version_ids`, `default_version_id` and the store's `chosen_version_id`. No pin means the default package of the store's release. The pinned version reaches the store as the node's `content`, carrying its `package_version_id`, its `version_label`, the `min_edge_version` it needs and its named `time_slots`; the parts join it as the phases that type them land. Brand and store are resolved in the cloud by the pin. Device, role, sales channel and time slot are resolved on the store, for each part, by `pos_core::package::resolve`. The till implements the same rule in `ui/src/package/variant.ts`. Both run the vectors in `crates/pos-proto/testdata/package_variants.json`. The rule:

1. A variant is a candidate when every dimension its selector states matches. The device is matched by `device_id` or by `device_class`, never both. The role matches when it is one of the signed-in person's roles. The time slot must be the store's current slot. A token from a newer release matches nothing.
2. The candidate stating the most dimensions wins.
3. If two candidates state the same number, the first dimension in the order device, role, sales channel, time slot decides.
4. If they are still tied, a device named by id wins over one named by class.
5. If they are still tied, the variant listed first wins. This step is reached only when a person holds two roles that each have a variant.

The pin is five settings on the `package` node (`docs/configuration.md`). `package.mode`, `package.locked_version_id`, `package.allowed_version_ids` (at most 32) and `package.default_version_id` are written with `PUT /admin/settings` at any scope. Three rules apply beyond the register (`pos_cloud_config::package_pin`):

- Every id must name a published version of one of the tenant's packages. A write that names any other id is refused with `UNKNOWN_PACKAGE_VERSION`.
- A lock holds below it. While a scope that reaches a store sets `package.mode` to `PACKAGE_MODE_LOCKED`, a `package` value written at a narrower scope that reaches the same store is refused with `409 PACKAGE_LOCKED_ABOVE`. A narrower value written before the lock is kept, and does not reach the store while the lock lasts. The lock's own scope may still change or lift it. This is lock by path (roadmap-v3 B7.2) for the `package` node only.
- `package.chosen_version_id` is written at the store and only through `PUT /admin/stores/{store_id}/package/choice`. The route refuses with `409 PACKAGE_NOT_CHOOSING` unless the store's resolved mode is `PACKAGE_MODE_CHOOSE`, and with `NOT_ALLOWED` unless the version is one of its resolved allowed versions. A `null` clears the choice. ADR-0189 gives the choice to a store's people, through the store permission `admin.package.choose`. A store's people cannot sign in to the console yet, so in this release the route needs `console.config.publish` and HQ chooses for the store. Giving that choice to the store's own people needs its own ADR ([roadmap-v4](roadmap-v4.md), phase 4).

The console's Settings page leaves the `package` settings out, because the package page sets them.

Every settings publish, from a write, a choice or `POST /admin/settings/publish`, also compiles the pinned version into the store's document, as `content` on the `package` node of its Tenant layer (`pos_cloud_config::package_pin::compile`). A lock compiles `locked_version_id`. A choice compiles `chosen_version_id` while it is allowed, and otherwise `default_version_id` while that is allowed. No pin removes `content`, so the store runs its release's default package. The pinned version is compiled in only when the release the store last reported ([ADR-0078](adr/0078-sync-and-ota-closure.md)) is at least the version's `min_edge_version`. Otherwise the store keeps the content it runs and waits, for one of these reasons:

- `EDGE_TOO_OLD`: its reported release is older than the version needs.
- `RELEASE_UNKNOWN`: it has never reported a release.
- `VERSION_MISSING`: the pinned version is not a published version.
- `PIN_UNRESOLVED`: the pin names no version the store may run.
- `UNREADABLE`: the package store or the store's release could not be read.

A waiting store is compiled again on the next publish that reaches it. It is also compiled when it reports a new release: the OTA report hands the store to a bounded queue (256 stores; a report beyond that is dropped and the next publish covers it). A worker then republishes the store's settings only if its pinned version can now be compiled in and its document does not carry it yet. A publish never makes a report, so the two cannot feed each other. `GET /admin/stores/{store_id}/package` answers the version the store is pinned to, the one its document carries, and why it waits when the two differ. Rolling back is pinning the previous version again, which publishes like any other write.

The edge checks a pulled document's package before it applies anything (`pos_edge::config_client::checked_package`). The `package` node must read as one, its content must pass the rules the cloud checks at publish, and its `min_edge_version` must be at most this binary's release (`pos_edge::version::VERSION`, the same value the OTA report sends). A document whose package fails is refused whole, as ADR-0189 decision 6 says, and the store keeps the document it runs. The refusal is kept in a `PackageStanding` (`PACKAGE_MALFORMED`, `PACKAGE_INVALID` or `EDGE_TOO_OLD`), and the version is held, like any refusal, so it is not pulled again each interval. A document that passes puts the package on the session as `EdgeSession::package`, and no pin leaves it `None`, the default package of the release. A document restored at boot whose package this binary cannot run is applied without it. A build that is not a release reports `0.0.0`, so it runs only a version that needs no newer edge. The flows a package carries are re-checked by the flow engine on the edge (ADR-0192). Each heartbeat reports the package as `package`, which carries the version the store runs (absent for the default package) and, while a document stands refused, `refused` with its configuration version, its package version and the reason. The cloud keeps the latest report on the store's liveness row (migration 0090), and the console's fleet view shows it, with an older edge reporting nothing. `GET /api/package` on the edge answers the same two facts, read-only, for its diagnostics. Each read of it records which version the paired till asking was served and when (`pos_edge_app::app::DeviceReads`, in memory, at most 64 tills, the oldest read dropped first, so after a restart a till is reported again once it next reads), and each heartbeat reports them as `devices`, one `{device_id, package_version_id, read_at_ms}` per till. The cloud refuses a report naming a till twice or more than 64 (`INVALID_VALUE`), keeps the latest on the liveness row (migration 0094), and the fleet view answers `devices` with the report's `reported_at_ms` and its `tills`, each with `behind`, true when it read another version than the store reports running. A till that missed a `config_applied` and still draws the version it read before is shown as behind on the console's fleet table. A device id names a device, never a person. Development, replay and simulator builds made through the justfile stamp `dev_edge_release` as their release, and so do the `minimal-edge` builds of CI's replay, perf gate and nightly jobs, so they run the package versions this tree publishes. A test holds that stamp at or above the cloud's `PACKAGE_NODE_SINCE`.

The store's current time slot is the first slot in the package's `time_slots`, in the order they are listed, that has a weekly window holding the store's local time. A store is therefore in at most one slot. Every part has one base variant, which states nothing. A version is refused at publish, and again on apply, if two of its variants share a selector, if a variant names its device twice or if a variant names an undeclared slot (`pos_core::package::check_variants`).

A package's **conditions** are written in a restricted dialect of CEL ([ADR-0193](adr/0193-conditions-and-reactions-are-written-in-cel.md)) and evaluated by one crate, `pos-rules`, which the cloud, the edge and (compiled to `wasm32`) the till share. `Rules::compile` refuses a condition outside the dialect before it can run: a loop macro (`all`, `exists`, `exists_one`, `map`, `filter`) or any function off the allow-list (comparison, boolean logic, integer arithmetic, `in`, indexing, `size`, `contains`, `startsWith`, `endsWith`, and `has()`); more than 1,024 characters, 256 nodes or a depth of 32, where brackets nested deeper than 32 are refused from the text before the parser recurses; a `double` literal or `double()`; a struct literal; and any name but the views `order`, `line`, `bill`, `channel`, `device`, `role` and `now`. The facts a condition reads hold no fraction, so an amount is an integer in minor units. A field the facts lack, an overflow or a division by zero is an evaluation error, never a guess. **The till runs the same engine** (`crates/pos-till-rules`): `pos-rules` and `pos_core::flow` built for `wasm32-unknown-unknown` with the `till-rules` profile (size first, fat LTO: about 290 kB gzipped, and `pnpm rules` fails the build over 400 kB, ADR-0193 decision 2), by `pnpm rules`, which `pnpm build` runs first, so the module comes from the same commit as the till. It imports nothing and exports three functions: the till copies a JSON request into a buffer the module reserves (`till_rules_input`, at most 1 MiB), asks (`till_rules_call`), and copies the JSON answer out (`till_rules_output`). The requests are `load` (every variant of a package's flows, compiling every condition once), `available` and `missing` (the flow functions above, for a flow and the variant the till chose, where a step whose `done_when` holds over the facts counts as done, as the edge sees it) and `holds`. Every error is an answer, `{"ok":false,"error":…}`; facts are whole numbers, strings, booleans, lists and objects, never `null` or a fraction. The till instantiates it once, when it is next idle after the store's first load (`ui/src/rules/boot.ts`): building the evaluator is tens of milliseconds of main thread on a slow till, and started during sign-in it held the store's own reads back. It loads the flows of the version the store runs, and only once a step of them has a condition or a prerequisite, something only the module answers: a package with none needs nothing answered, so the till neither downloads the module nor builds the evaluator (the default package's guest step has neither, so a store on it loads nothing). The flows are those which `GET /api/package` carries as `running.flows` (every variant of each, omitted when the version has none; a store on the default package is answered `running: null` and the till runs its own default package's flows), and loads them again whenever they change (`ui/src/state/flows.ts`). On a tap the till chooses each flow's variant for the order's channel and asks: a dine-in seat that a step runs asks the guest count first (`guestStep`), with no Skip when the step is required, and a line waits on a missing prerequisite (`missingFor`), from the count this till seated the table with, heard on `sales.order.opened`, or read with what is open (`guest_count` on `GET /api/orders/live`, omitted for an order opened without one, which the till records as a count not given), so a till that reloads knows the count of each table with a line on it as the edge does; a table whose count it does not know (a table seated by another device, with no line yet, after a reload) holds nothing back. `POS_DEMO_PROFILE=guests-required` runs the demo store locked to a version whose guest count is required. a till whose module cannot load offers what it offered before, and the edge still re-checks every command.

A package's **flows** ([ADR-0192](adr/0192-a-flow-is-a-graph-of-steps-the-edge-re-checks.md)) ride its content as `flows`, each with its variants (`pos_proto::flow::Flow`). A flow is started by a catalogue action and has 1 to 64 steps; a package has at most 32 flows, counted by `flow_id`. Each step shows a package screen or runs a catalogue action, is `STEP_KIND_REQUIRED` or `STEP_KIND_OPTIONAL`, may apply only when its `applies_when` holds, and waits for its `prerequisites`. `pos_core::flow::check_flows` refuses, at publish and on apply, an id that is not `a`–`z`, `0`–`9` and `_`, a duplicate step, a step that does not do exactly one thing, a kind this release does not know, an unknown action, screen or prerequisite, prerequisites that wait on each other, a condition that does not compile, a required step whose act needs the cloud (`ACTION_EFFECT_EXTERNAL`) with no `offline` branch (`NO_OFFLINE_BRANCH`), and a branch that does not name exactly one of a well-formed note key (`skip_note_key`, skip the step showing it) and another step of the same flow (`step_id`, go there instead) (`BAD_OFFLINE_BRANCH`, [ADR-0214](adr/0214-a-tills-external-lookup-is-one-catalogue-act.md) decision 5); the cloud also refuses a note key without English text, as any key a version names. The console's step editor offers the branch for a step whose act needs the cloud. A step is satisfied when it is done, when it does not apply, or, if optional, when it was skipped; the till offers the steps whose prerequisites are satisfied (`available_steps`) and names the one missing (`missing_prerequisite`). A required step with a `done_when`, a condition over the edge's own facts, is an **edge guard**: before a command for an action whose step waits on it, the edge evaluates it (`unmet_guard`) and refuses with `409 FLOW_PREREQUISITE_UNMET` naming the step. A guard whose condition cannot be answered refuses: it fails closed. An edge guard's `applies_when` must also read only edge facts, since the edge evaluates both. The edge runs `check_flows` when it applies a package (`checked_package`; a failing flow refuses the whole document, as any invalid package does), with `pos_edge_app::app::flows::EdgeConditions` over `pos-rules`; a step's `screen_id` is not resolved there until a package carries its screens. Before adding a line, firing an order or a course, and opening a bill, the edge chooses each flow's variant by the order's channel and answers its guards from the order's own facts: `order.guest_count` (absent when none was recorded), `order.line_count` and `order.channel`, and `channel`. A guard not done refuses the command with `409 FLOW_PREREQUISITE_UNMET`, whose sentence names the flow and the step; the till shows it with the step's id. The flows checked are those of the version the order opened under, which `sales.order.opened` names (decision 5): a publish while an order is open does not change its rules, and an order opened under the default package has none. The edge holds at most four versions (`flows::RETAINED_MAX`), each with its conditions compiled once, and lets go first of one no open order references; it does not rebuild them from events. An order whose version it no longer holds, after that or after a restart, is checked under the version the store runs now, and the edge logs that it did so. After a restart the edge holds no version, so every order open at the time is checked under the version the store runs now, and the edge logs it.

A package's **reactions** ([ADR-0193](adr/0193-conditions-and-reactions-are-written-in-cel.md) decision 5) ride its content as `reactions`, each with its variants (`pos_proto::reaction::Reaction`): *when* a trigger fires on the till (`REACTION_TRIGGER_SCREEN_ENTERED` with its `screen_id`, `REACTION_TRIGGER_STEP_COMPLETED` with its `flow_id` and `step_id`, `_LINE_ADDED`, `_ORDER_OPENED` or `_BILL_OPENED`), *if* its condition (`if`, CEL over the till's views) holds, *then* one catalogue act (`then.action_id`) with parameters fixed in the package (`then.params`, every required one given; an id parameter left out is the subject's, the order, table or bill the trigger fired for, as for a button). `pos_core::reaction::check_reactions` refuses, on apply beside the flows, an id that is not `a`–`z`, `0`–`9` and `_`, a trigger this release does not know or that names the wrong things, a screen or step the package does not declare, more than 16 reactions (counted by `reaction_id`) for one trigger, an act that is not `ACTION_EFFECT_UI` or `ACTION_EFFECT_EDGE_WRITE`, a parameter the act does not take or a required one left out, and a condition that does not compile; the cloud authors versions with none until the console designs them (phase 4). `GET /api/package` carries the running version's reactions as `running.reactions` (omitted when it has none), and **the till runs them** (`ui/src/state/reactions.ts`): a trigger fires once the edge has confirmed the act it follows (a table seated is `_ORDER_OPENED`, and `_STEP_COMPLETED` for the flow steps a seat with a guest count completes; a table's line, `_LINE_ADDED`; its bill, `_BILL_OPENED`; its order screen shown, `_SCREEN_ENTERED` for `order`), and its reactions run after the next frame, never on a tap. For each, the variant chosen for the order's channel; at most 16, in the package's order; only an act whose every permission the signed-in person holds outright, since a reaction never asks for an approver; only when its condition holds over the order's facts, a condition the till cannot answer counting as not holding (the rules module is fetched once a reaction has a condition); and no chaining: an act a reaction runs, and a screen it opens, fire nothing. The till runs `ui.screen.open` (through the router, `ui/src/components/ScreenReactions.tsx`) and the prints `billing.check.print` (by the bill, order or table it fired for) and `reports.shift.print_x`, through the edge-write path; any other act is passed over, and the edge checks every command a reaction sends as it checks any other. `POS_DEMO_PROFILE=reactions` runs the demo store on a version that prints a check when a bill opens and an X report when a table is seated, with permissions enforced and the X report's withheld, so the second never runs.

A package's **screens** ([ADR-0190](adr/0190-a-screen-is-drawn-from-the-package.md), [ADR-0203](adr/0203-a-component-reads-its-own-data.md)) ride its content as `screens`, each with its variants (`pos_proto::screen::Screen`), left off the wire while it declares none. A screen is a `screen_id` and a tree of nodes, at most 400 and 12 levels deep. Each node names a component of the release's catalogue (`pos_proto::screen::CATALOGUE`) by `component_id` and gives it `properties`, each a literal of the kind the catalogue gives it: `PROPERTY_KIND_TRANSLATION_KEY`, `_TOKEN` (one of the values the property lists), `_INT` (within its bounds), `_BOOL`, `_ACTION`, an `action_id` from the action catalogue with the `params` the package fixes, or `_FIELD`, the name of a field of the gateway endpoint the screen's lookup calls (`a`–`z`, `0`–`9` and `_`, starting with a letter, at most 64; ADR-0214). A package never says where data comes from: each component reads one fixed part of the screen's context, and supplies the ids it shows to the acts it binds (an `action_button` the screen's `order_id` and `table_id`, and the `values` a person typed into the screen's `lookup_field`s). Each component also names the device classes it is drawn on, an optional `fallback_component` and the release that introduced it. The catalogue is held by `docs/snapshots/components.txt`, which refuses a removed component, property, token, supplied parameter or device class, and both front ends read it from `packages/package-renderer/src/components.ts`. `pos_core::package::check_screens`, which `check_content` runs in the cloud before a version is stored and on the edge before one is applied, refuses more than 64 screens, a `screen_id` that is not `a`–`z`, `0`–`9` and `_`, a screen whose variants share a selector or lack a base, a tree over 400 nodes or 12 levels, a component this release does not have or does not draw on a device class the variant may run on (every class, for a variant that names none), children under a component that holds none, a property the component does not take or leaves out when required, a value not of its kind (a malformed key, a token not listed, a number out of bounds), an act the catalogue does not have, a fixed parameter the act does not take or of the wrong kind, a fixed amount or entry, and a required parameter neither supplied nor fixed. It answers `INVALID` on the field `screens`, naming the screen and node by position. Whether every key has an `en` value is left to the cloud's translation grid. The till has one renderer, which the console builds too ([ADR-0209](adr/0209-the-console-previews-a-screen-with-the-tills-renderer.md)): its core is `packages/package-renderer/` (the tree walk, the limits, the contexts, variant resolution, the two catalogues and the five components that draw from the package alone, `BASE` in `base.tsx`), which imports only `solid-js`, resolved from the front end that builds it (`resolve.dedupe`, and a `paths` entry in its `tsconfig.json`), and is given each front end's words (`Words`: the till's are `ui/src/package/words.tsx`). It mounts, for each node, the implementation `ui/src/package/registry.tsx` holds for its component, `BASE` and the till's regions (a `Record` over the catalogue, so a catalogued component without one does not compile); a node naming a component the till's release lacks draws a slot saying the till needs an update and the rest of the screen draws; a tree over the limits is not drawn and the host screen draws its own. The hosting screen gives the components its subject (`order_id`, `table_id`), which acts it can run, and runs them. The screens this release ships are its **default package**, `ui/src/package/default-package.json`, which a `pos-core` test holds to `check_screens`, so the till cannot ship a screen a published version could not hold. A screen moves into it one at a time, its own components kept in the screen's file beside the state they read (`scripts/step-budget.mjs` resolves a route's taps there), with the same DOM and every replay green. The floor is drawn from it (`screen_frame`, `page_header`, `floor_alerts`, `floor_plan`), and so is the order screen, a table's or a counter order's (`order_layout`, `order_column` and `order_menu` around `order_header`, `order_notices`, `order_move`, `order_bill`, `menu_toolbar`, `menu_fields` and `menu_buttons`, each a region the order screen hands over), taking payment (`screen_frame` with `width` `narrow` around `pay_back` and `pay_flow`), the counter (`counter_frame`, `counter_flow`), the kitchen board (`kds_frame` around `kds_header`, `kds_notices`, `kds_stations` and `kds_tickets`), the pass (`screen_frame`, `page_header` at `size` `extra_large`, `expo_tickets`) the guests' QR orders (`guests`: `page_header`, `confirm_queue`), today's takings (`today_body`), the drawer's shift (`shift_screen`), devices (`devices_body`), pairing (`pair_body`), setup (`setup_body`) and signing in (`sign_in_screen`), the last four inside a `screen_frame` whose `width` is `medium` or `small`. Every route of the till is drawn from the default package but one, `/screen/:id`, which draws a screen the running version adds; only the claim page of a box not yet a store server is drawn from neither, since it comes before the router (`ui/unit/default-package.test.ts`). A screen hands its regions to the renderer through one context, `RegionsContext` in `packages/package-renderer/src/regions.tsx`, under their component ids, and the catalogue's entry for each is `region(id)`. `GET /api/package` carries the running version's screens as `running.screens` (omitted when it has none), and the till draws them (`ui/src/state/package-screens.ts`, `ui/src/package/screen.tsx`). A screen the version declares is drawn in place of the default package's screen of the same `screen_id`, and any other stays the default package's. A screen whose `screen_id` the default package does not have is drawn at `/screen/:id` (`ui/src/screens/VersionScreen.tsx`), with no regions, and an `ui.screen.open` act opens it there; that route draws neither a screen of the release's own, which opens at its own route, nor an id the running version does not declare (the slot that says the till needs an update). The variant drawn is the one for the till's device class (ADR-0201 decision 3, `ui/src/lib/device-class.ts`): the `device_class` the `TERMINAL` entry on the `devices` node that the device is bound to names (`pos_proto::devices::PublishedDevice::device_class`, left off the wire while unset), which `GET /api/session` answers as `device_class` and which the till reads again when the `devices` node changes; and, where it names none, the device is bound to no terminal or the binding cannot be read, the class read from the screen through the named breakpoints, terminal from 64rem and tablet from 48rem, the phone below. The edge reads the binding for it only when some terminal in the node names a class. The console sets the class on a terminal (`POST /admin/devices/proposals/{id}/device-class`, column `device_class` from migration 0095), and the devices publish carries it as saved, nothing where nobody set one. A tree is mounted again only when the variant chosen changes. On a till screen, a package's `action_button` runs the acts a reaction runs, through the same runners (`ui/src/state/reactions.ts`): `ui.screen.open`, through the router reactions use, and the prints `billing.check.print` and `reports.shift.print_x`, each only when the signed-in person holds every permission it needs without an approver. None of them moves money; and the screen's lookup, `integrations.lookup.run` (below), which only reads. Any other act it binds draws disabled. It acts on the subject its screen gives: the order screen supplies its `table_id` and, once the edge has opened it, its `order_id`, or a walk-in's `order_id` (`orderHost` in `ui/src/package/screen.tsx`), and every other screen supplies none, so a screen that needs a table opens only from the order screen. A print on its way takes no second tap, and a refused or unanswered one is said under the button.

A version names its **homes** ([ADR-0210](adr/0210-a-role-names-its-home-screen-in-the-package.md)): `home_screens`, a variant list of `HomeScreen { screen_id }` whose selectors state at most `role_id` and `device_class`, left off the wire while it is empty. `pos_core::package::check_homes`, which `check_content` runs in the cloud and on the edge's apply, refuses a selector stating anything else, two homes with one selector, homes without a base, and a home naming a screen the version does not declare; the dry run answers it on the field `home_screens` with `NO_BASE_HOME`, `SAME_HOME_SELECTOR`, `HOME_SELECTOR` or `UNKNOWN_HOME_SCREEN` and the home's position in `name`. A version that states homes needs at least `HOME_SCREENS_SINCE` (`pos_cloud_config::packages`). `GET /api/package` carries them as `running.home_screens`, and after a sign-in the till opens the home it resolves for its device class and the signed-in person's roles (`homeRoute` in `ui/src/components/ScreenReactions.tsx`): the screen's own route, or `/screen/:id` for one the version adds. A version with no homes, a home that needs a table, or one the till cannot open lands on `/` as before. The store knows each person's roles ([ADR-0213](adr/0213-a-store-knows-each-persons-roles.md)): the people compiler gives each member of the `permissions` node `role_ids`, the ids of the active roles they hold at the store, sorted and once each, left off the wire when they hold none; the edge keeps them beside its roster and `GET /api/session` answers the signed-in person's as `role_ids` (empty when nobody is signed in). The till chooses a screen's role variant and a role's home with them (`roleIds` in `ui/src/state/session.ts`): when several of the person's roles match, the variant listed first in the version wins, and with none the base applies. A role id is never put in an event or a log; `Debug` of a member or a roster prints only how many. A version a selector of which states a role needs at least `ROLE_VARIANTS_SINCE`; an older edge would run it with the base for everyone. A flow's and a reaction's variants are still chosen by sales channel alone, on the edge and the till alike. The console's screen designer sets the base home (*Home screen after sign-in*). From the homes, `pos_core::package::tap_warnings` counts taps (ADR-0210 decisions 2 to 6): for the base role and every role a selector states, on every device class, each declared screen the till would resolve is a node, a `ui.screen.open` with a fixed `screen_id` is an edge of one tap, any other action property offers its act at its screen's distance plus one, a flow's step screens are reached at what its start act costs, and a screen the version does not declare ends the graph. A `COMMON` act over `COMMON_TAPS_MAX` (2) or a `RARE` one over `RARE_TAPS_MAX` (3) is a warning: the dry run answers it in `warnings` (reason `TAP_BUDGET`, the role or none for the base, the device class, the act, the cheapest `screen_index` and `node_index`, and the taps) once the content, flow, reaction and key checks pass, and a publish stores the count as `tap_warning_count` on the version. Nothing is refused.

The tenant's **translation grid** ([ADR-0043](adr/0043-translation-grid.md)) reaches the store whole: the edge pulls `GET /sync/stores/{store_id}/translations` with its config key at start and every 10 minutes (`pos_edge::grid_client`), holds it within its bounds (at most 20,000 keys, 32 locales a key and 1 KiB a key or text, `pos_edge_app::labels`; a grid past them is refused whole and the held one kept), and keeps a copy in its state directory (`translations.json`, replaced whole) so a store that restarts offline still has its labels. The grid holds labels HQ wrote, never personal data. `GET /api/package` answers `running.labels`, the grid's entries for every translation key the running version names, and nothing else, so the till's boot reads no more than before. The till shows a package label from its own catalogue where it has the key, then from these in its language, then in English, and otherwise draws nothing, never the key (`ui/src/state/labels.ts`). A grid change reaches a till when it next reads its package.

A package's **data part** ([ADR-0194](adr/0194-custom-data-is-declared-and-personal-fields-are-kept-apart.md)) rides its content as `data` (`pos_proto::package::PackageData`), left off the wire while it declares nothing. It declares `custom_fields` on an existing object (`DATA_OBJECT_ORDER`, `_LINE`, `_BILL`, `_TABLE`, `_SHIFT`), at most 64 per object; `object_types`, at most 32, each with at most 64 fields; and `lists`, at most 500 entries each, that a `choice` field draws from. A field has a `custom_field_id`, a `label_key`, a `field_type` (`CUSTOM_FIELD_TYPE_INT`, `_BOOL`, `_CHOICE`, `_DATE`, `_QUANTITY` with a `unit_key`, or `_TEXT` of at most 1 KiB), whether it is `required`, and `personal`, which nothing defaults. A personal field also names its `retention_days` and its `consent_purpose_key`. A field, type or list entry is never removed: it is marked `deprecated`. `pos_core::package::check_data`, which `check_content` runs in the cloud and on the edge, refuses a data part that breaks a ceiling or repeats an id, a list with no entry, a field on an existing object that names no object or one of an object type that names one, a malformed label key, an absent or unknown type, a `choice` without a declared list or a `quantity` without a unit, a field that does not say whether it is personal, `text` that is not personal, a personal field without its retention period of at least a day or its consent purpose (and a field that is not personal with either), a personal field on a shift, and personal fields of one object or type whose periods differ ([ADR-0206](adr/0206-a-personal-custom-value-stays-on-its-store-and-expires-on-its-own-clock.md) decisions 2 and 8). A personal field declared in full is accepted: each personal record keeps its own period and an erasure reaches the store that holds it, so decision 11's refusal is lifted. A box whose package declares one runs with full-disk encryption ([`go-live.md`](go-live.md) step 21, decision 10). `pos_core::package::check_evolution` checks a version against an earlier one of its package (ADR-0194 decision 6): every field, object type, list and list entry the earlier one declares is still declared, a field stays on the same object or in the same type with the same type and list, and a personal field stays personal; a change is deprecation, or a new field. These are declarations only. A version's data part is published as the `data` of `POST /admin/packages/{package_id}/versions`. The cloud checks it with `check_content`, refusing a fault with `INVALID`, and then with `check_evolution` against every earlier version of the package, refusing with `NOT_ADDITIVE`. A version that declares data needs at least the edge release that checks it (`DATA_PART_SINCE`).

The **edge enters custom data** (`pos_edge_app::app::custom_data`, [ADR-0206](adr/0206-a-personal-custom-value-stays-on-its-store-and-expires-on-its-own-clock.md)). `Edge::set_custom_fields` sets fields on an order, line, bill, table or shift the edge knows, and needs `data.record.write` and the object's own permission: an order's or a line's `sales.line.add`, a bill's `billing.bill.open`, a table's `sales.table.manage`, a shift's `cash.shift.open` (decision 7). `Edge::save_custom_record` creates a record of an object type, or changes one, under `data.record.write`. Each checks its values against the package the store runs with `pos_core::package::check_entry`: a declared, non-deprecated field named once, a value of its type, a current entry of its list, text of at most 1 KiB, a required field never cleared and, on a new record, given; a personal value needs its consent purpose among those the person agreed to. The non-personal values go into `data.custom_field.set` or `data.custom_record.changed`; the personal ones go, in the same transaction, to the subject store under the object's or record's subject, with `consent.<purpose label key>` set to when consent was given (decision 6). A new subject expires `retention_days` after it is collected (decision 1); an edit keeps that clock, and a masked subject is never written again, so new personal values start a new one. The event carries only the `subject_id`. The edge folds both events into its projection, at most 16,384 objects and 4,096 records, the oldest by id dropped first, so a restart reads them back from the log while it keeps them (ADR-0145). A refusal names the field and the fault, never the value (`CUSTOM_ENTRY_REFUSED`, `422`). Two writes to custom data never interleave on one edge, so two first writes to one object share one subject. The till reaches this through `POST /api/custom-fields` and `GET /api/custom-fields?object=…&object_id=…`, `POST /api/custom-records`, `GET /api/custom-records?object_type_id=…` (newest first, at most 200), `GET /api/custom-records/{id}`, `POST /api/custom-records/{id}/values` and `POST /api/custom-records/{id}/slip` (acts `data.custom_field.set`, `data.custom_record.create` and `data.custom_record.change`, whose values are `ENTERED`, so a package never binds them and a reaction cannot fill one in, and `data.custom_record.print`: `Edge::record_slip` decides whether a slip is the save's own or a reprint, and `Printers::print_record_slip` prints it as [`pos-spec.md`](pos-spec.md) describes). A value is sent as at most one of `integer`, `boolean`, `list_entry_id`, `calendar_date`, `quantity` or `text`, and none clears it; with `consented_purpose_keys` beside the values. No answer of these routes carries a personal value: an object or record answers with its non-personal values and its `subject_id`. Showing a saved personal value again is `GET /api/subjects/{subject_id}` (decision 5), which needs `data.personal.read` (risk HIGH): it returns that one subject's fields, consent times, `collected_time`, `retain_until_time` and `masked_time`, and there is no list and no search. Every call writes the decision's audit entry as a log line with the target `audit`, naming the action `data.subject.read`, the employee, the device and the subject, never a value. That line is in the store's own log only and is not sent to the cloud; a durable, synced audit trail would be an additive event and is not built.

An **erasure reaches a store by subject id** ([ADR-0206](adr/0206-a-personal-custom-value-stays-on-its-store-and-expires-on-its-own-clock.md) decision 4). The cloud names the subjects a store must mask on its `erasures` config node, `{ "subject_ids": [...] }`, at most 1,000 (`pos_proto::erasures`, read the same way by the cloud's validator and the edge). The config loop applies it beside the session swap, as it does the device deny-list (`pos_edge::config_client::erasures`). For each id it has not already confirmed, `Edge::erase_subjects` (`pos_edge_app::app::erasures`) masks the subject's record with the same one-way `[REDACTED]` masking its expiry uses and appends `data.subject.masked` (the `subject_id` and `masked_time`, written by the box with no employee), the record and the event in one transaction, serialised with custom-data writes. A record already masked by its expiry keeps its stamp and is confirmed with it; a subject the store holds no record of is confirmed at the time of the erasure, as the store holds nothing personal for it. The edge folds the event into its projection, at most 1,000 subjects, so a node applied again, after a restart too, confirms nothing twice. A malformed node, or one over its cap, is refused whole and logged; a write that fails holds the config version back so the next pull tries again. The log names the subject and the count, never a value.

The till's **Records** screen (`/records`, `ui/src/screens/Records.tsx`, drawn from the default package's `records` screen and its `records_body` component) enters custom records. `GET /api/package` answers the running version's data part as `running.data`, and the status bar offers the screen where it declares an object type. The screen shows each object type, its records newest first, and a form that offers each field not deprecated in the form its type takes (a whole number, a yes or no, an entry of its list, a date, a quantity typed in units to thousandths, or free text), with labels from the tenant's grid. *New* needs `data.record.write`. A change sends only the fields that changed; the edge re-checks every value and names a refusal (`CUSTOM_ENTRY_REFUSED`). A personal value is sent only once the consent for its field's purpose is ticked, labelled with the tenant's text for that purpose, and is never drawn again: after a save the field is empty and the record says a personal value is held. *Show personal values* reads the record's subject through `GET /api/subjects/{subject_id}` and is offered only to a person whose own role grants `data.personal.read`. Fields on an existing object (an order, a bill) have no till panel yet.

The cloud **projects custom data** into one table, `custom_values`, keyed by tenant, store, object and field (store-postgres migration 0092). On each tick the rollup projector also folds every store's new `data.custom_field.set` and `data.custom_record.changed` events (`pos_cloud_reports::custom_data`): a value sets its row, a cleared value deletes it, and a page's writes and the store's cursor in `custom_value_cursors` commit together, so each event is folded once. A row holds the existing object's kind or the record's object type, the typed value, the package version, the time it was set and, at most, the `subject_id` of the object's personal record. No personal value reaches the cloud ([ADR-0206](adr/0206-a-personal-custom-value-stays-on-its-store-and-expires-on-its-own-clock.md) decision 3). A **report** reads it through `GET /admin/stores/{store_id}/custom-values/summary` (and `summary.csv`), behind `console.data.read`: how many of a store's objects of one kind (`object`) or records of one object type (`object_type_id`) hold each value of one field, the most first, at most 500 groups, optionally among those whose filter field holds one value (a list entry, yes or no, or a whole number). It refuses a field no version of the tenant's packages declares (`UNKNOWN`) and one any version declares personal (`PERSONAL_FIELD`, ADR-0194 decision 7). It never reads, groups or returns a `subject_id`. The same pass folds the stores that hold each subject into `custom_subjects` (migration 0093): a row for each store whose `data.custom_field.set` or `data.custom_record.changed` names a `subject_id`, with `masked_time` set from the store's `data.subject.masked`. Only ids are kept. When a pass folds a confirmation, the projector takes every id that store has confirmed off its `erasures` node (`pos_cloud::erasures::prune_confirmed`); a publish that fails is logged and the ids stay until the store's next confirmation. The owner's erasure (`POST /admin/subjects/{subject_id}/erase`, [ADR-0076](adr/0076-subject-request-tooling.md), `console.subjects.manage`) of a subject the cloud's own `subjects` table does not hold adds its id to the `erasures` node of every store `custom_subjects` names that has not confirmed it (`pos_cloud::erasures::append_erasure`, inside the conditional-write retry; a full node is refused with `400`), audits `subject.erase` with how many stores hold it and how many are pending, and answers `erased: false` with `pending_store_ids` until each store confirms. A subject no store names is still `404`. `GET /admin/subjects/{subject_id}/stores` answers, per holding store and at most 64, whether it has confirmed (`masked`) and whether an erasure waits for it (`erasure_pending`), audited as `subject.stores`; no value is read. The console's **Subject requests** screen asks it when a lookup finds no cloud record, lists the stores with each one's standing, and offers the erasure while a store holds the subject unasked. The console's **Custom data** screen, under Overview, asks it for the store picked: it offers each object kind and object type with only the fields no version declares personal, a filter by a choice, yes-or-no or whole-number field, and labels from the tenant's translation grid in the console's language, then English, then the key itself.

### 3.2 Synchronisation

```
sale ──► SQLite txn + outbox ──► HTTPS /sync (or NATS JetStream) ──► cloud ingest (idempotent by ULID)
                                                        │
                                                        ├─► store partition (raw events)
                                                        └─► rollup tables ──► dashboards
```

Identifiers are **ULIDs**: generated offline, sortable by time, collision-free when thousands of stores merge. Ingestion is idempotent, so at-least-once delivery is safe. A nightly reconciliation compares event counts and checksums between each store and the cloud; a mismatch lists the missing IDs and re-pushes them.

## 4. Fleet operations

**Provisioning.** Creating a store yields a one-time activation code. The installer exchanges it for long-lived credentials stored in the OS keystore (TPM/DPAPI on Windows, keyring on Linux). No secrets ship inside installers. That one credential is all a box needs: it authenticates config sync, the heartbeat, the order relay and event publishing, for the box's own store only, and archiving the device in the console revokes it ([ADR-0143](adr/0143-the-device-credential-syncs-and-events-travel-over-https.md)).

**Single-active lease.** Exactly one server may be active per store. A replacement machine takes the lease; if the old machine returns from the dead it becomes read-only. This prevents split-brain and duplicate receipt numbers.

**Over-the-air updates.** Signed with minisign. Rolled out in canary rings (for 50 stores, two rings; for 1,000, four). Each update runs a self-test after install and rolls back automatically on failure. Because a rollback of the binary requires a rollback of the data, the database file is copied to `.pre-update` before migration, and **migrations within a release may only add** — never drop or rename. A kill switch halts a rollout instantly.

**Two signing keypairs, both public keys baked into the binary.** Key A signs day-to-day releases; key B is the sealed spare. If A is lost or leaked, one release switches the fleet to B — no need to visit 1,000 machines. The cloud publishes a revocation list that edges check before installing. Private keys never live on the CI runner or the VPS: releases are signed by hand from an offline USB key.

## 5. Ports and adapters

`pos-core` never calls NATS, PostgreSQL, S3, or a printer. It calls **ports** — traits owned by this project. Every external technology is one implementation of one port.

| Port | Responsibility | Current implementation |
|---|---|---|
| `EventStore` | Append and read events, outbox | SQLite / PostgreSQL |
| `ConfigStore` | Config snapshots and deltas | SQLite (edge-local) — see note |
| `MessageLink` | Durable store↔cloud channel | HTTPS to `/sync` (`cloud-sync-http`), or NATS JetStream |
| `BlobStore` | Large objects (backups, artifacts) | Garage / MinIO |
| `MetricsSink` | Numeric telemetry | VictoriaMetrics |
| `Signer` / `KeyVault` | Signature verification, key storage | minisign, OS keystore |
| `ClockSource` | Time and drift detection | SNTP |
| `IdGenerator` | ULID generation | in-house |
| `PrinterDriver` | ESC/POS, print queue | in-house |
| `PaymentTerminal` | Card terminals (FFI or TCP) | per acquirer |
| `Fiscalization` | Legal invoicing per country | `fiscal-vn` first |
| `DeliveryVendor` / `ShippingDispatch` / `ErpSink` | Marketplaces, couriers, ERP | per vendor |
| `OrderIn` | Inbound orders from outside the store | marketplaces, `POST /v1/orders`, QR ordering |
| `CloudSync` | Store→cloud request/response: activation exchange, OTA artifact fetch | HTTP to the cloud |
| `DeviceRegistry` | Which devices a store has admitted, and who is signed in on each | SQLite (edge-local) |
| `IntakeLedger` | What a caller's `(channel, reference)` produced, so a retry is not a second order | SQLite (edge-local) |
| `SubjectStore` | Where personal data lives, keyed by `SubjectId`, so the immutable log never holds any | SQLite (edge-local) |
| `StoreWake` | Hears the cloud's wake that a store's configuration changed, so it pulls now rather than at the next poll | core NATS on the edge's existing connection (`link-nats`) |
| `KeyKeeper` | The cloud's environment key: wraps and unwraps tenant keys, nothing else | the file keeper (`integration_secret`, development only) in `pos-cloud` |

**`ConfigStore` has one adapter, not two.** The row said "SQLite / PostgreSQL" and no PostgreSQL implementation of this port exists — the only `impl ConfigStore` outside the fakes is `store-sqlite`. What the cloud has is a *different* thing that happens to store configuration: `pos-cloud`'s own config-tree seam over its Postgres tables, which publishes nodes down to stores. The port is the store's local view of the config it was given; the cloud's is the authoring side. Naming both "ConfigStore" in one cell implied a swappable adapter a fork could pick, and there is none to pick.

The list above is authoritative and counts **twenty-two** ports. [ADR-0006](adr/0006-ports-and-adapters.md) named fifteen: it omitted `OrderIn`, which [ADR-0012](adr/0012-qr-ordering-via-cloud.md) depends on, and [ADR-0021](adr/0021-corrected-port-list.md) supersedes it with sixteen. [ADR-0053](adr/0053-cloud-sync-port.md) adds the seventeenth, `CloudSync`, for the store↔cloud calls that need an answer back — distinct from `MessageLink`, which stays outbound-only so the store still sells offline. [ADR-0091](adr/0091-durable-edge-auth-state.md) adds the eighteenth, `DeviceRegistry`, so that pairing and sign-in survive a restart instead of being erased by one; it stores a SHA-256 of each device token and never the token. The nineteenth, `IntakeLedger` ([ADR-0064](adr/0064-edge-order-in.md)), is a port that was named as one when it landed and registered late — see below. The twentieth, `SubjectStore` ([ADR-0107](adr/0107-the-buyer-is-a-subject.md)), is the place a **store** keeps personal data: `pos_proto::pii` makes a name in an event a compile error and [`pos-spec.md`](pos-spec.md) §15 says why, so a B2B invoice's buyer is filed here — in the settle's own transaction — and the event carries only the subject id. It has no read-them-all, because a port that can enumerate personal data is a port that can export it. A record may carry its own expiry, `retain_until` ([ADR-0206](adr/0206-a-personal-custom-value-stays-on-its-store-and-expires-on-its-own-clock.md) decision 1): the store's sweep, `mask_before(cutoff, now)`, masks an unmasked record whose `retain_until` is at or before `now`, and one without it, such as a buyer's, when it was collected at or before the cutoff the store's `default_retention_days` gives (store-sqlite migration 0016 adds the column and its index). The twenty-first, `StoreWake` ([ADR-0195](adr/0195-the-cloud-wakes-a-store-to-pull-its-config.md)), is receive-only and carries a signal, not data: the cloud wakes a store on `pos.store.<store_id>.config` with the version a publish produced, after the store's config-tree save commits, and the store runs the same pull it runs every 30 s, at once, at most once a second, and once more on every reconnect; a store without the bus keeps the poll alone. Each heartbeat reports `config_wake`: `CONFIG_DELIVERY_WAKE` or `CONFIG_DELIVERY_POLL`, and the 95th-percentile and longest time from wake to apply over the store's latest 128 wakes, which the cloud keeps on the store's liveness row (migration 0091) and the fleet view shows. `MessageLink` stays outbound-only, and configuration still reaches a store one way. The twenty-second, `KeyKeeper` ([ADR-0217](adr/0217-secrets-are-sealed-under-versioned-tenant-keys.md)), is the cloud's environment key: it wraps a tenant key under its newest version and unwraps one under the version it names (`WrappedKey::keeper_version`), and a key never leaves it. Its contract: what is wrapped unwraps intact; a wrap never holds the key in clear and two wraps differ; a changed byte or another environment's wrap is refused, never opened to another key; a version it does not hold is `NOT_FOUND`. `pos_cloud::keys::EnvironmentKeys` is the keeper over key material the process holds (XChaCha20-Poly1305, a random nonce per wrap, bound to the version), and the **file keeper** is that over `integration_secret` as version 1, for development and demonstrations only; production must not run on it.

**A discrepancy that was recorded rather than papered over, and is now closed.** `IntakeLedger` ([ADR-0064](adr/0064-edge-order-in.md)) spent two slices as a trait in `pos-ports` that its own record called a port while having no `PortName` variant, no contract suite, and no row in the table above; it reported its failures under `PortName::OrderIn`. It escaped the "every port has a suite" gate because that gate iterates `PortName::ALL`, so a trait added without a variant is invisible to it. It now has the variant, a six-case suite both `pos-fakes` and `store-sqlite` pass, a row above, and its own error label.

**The blind spot itself is still there**, and worth stating plainly: the gate can only check ports that were registered, so it can never be the thing that catches an *unregistered* one. What catches that is the rule that a new port needs an ADR ([ADR-0021](adr/0021-corrected-port-list.md)) and a reviewer who reads it — which is a process control, not a test, and it is the one that failed here.

**Dependency rule, enforced by a CI test:** `pos-core` and `pos-ports` may depend only on `std`, `serde`, and pure computation crates. Adapters depend on core; core never depends on an adapter. Only the binaries know which adapters are wired in.

**Contract tests.** Each port ships a shared test suite that every implementation must pass — for example, `EventStore` must return events in order, be idempotent by ULID, and survive a simulated crash mid-transaction. This is what makes "swappable" a verified fact rather than a claim.

**Minimum state machine in core.** `pos-core` contains an explicit table of *state × event → new state*, plus invariants, for Order, Bill, Shift, and Table. Examples of invariants: a settled bill accepts no new lines; a fired line can only be voided with a reason and a permission; a closed shift accepts no transactions; and, for a settled bill, `sum(payment.applied_to_bill) == bill.total_due` — the honest form of “payments sum to the bill”, with tips a separate ledger and change in the gap between tendered and applied ([ADR-0028](adr/0028-settlement-and-payment-invariant.md)). This table is the machine-readable twin of [pos-spec.md](pos-spec.md), and property-based tests are written against it.

## 6. Integration surface

### 6.1 Vendor groups (inbound adapters)

| Group | Examples | Notes |
|---|---|---|
| Delivery marketplaces | Grab Food, ShopeeFood | Orders arrive as events; store offline ⇒ vendor sees "busy" |
| Payment terminals | per acquirer | Unknown-result branch always exists; reconciliation resolves it |
| E-invoicing | Viettel, VNPT, MISA | Number ranges pre-allocated so invoices can be issued offline |
| ERP | SAP and others | Nightly posting of revenue and consumption |
| Shipping dispatch | Ahamove, Grab Express | Create, cancel, track; courier status becomes an event |

Adapters contain **only the vendor's protocol**. The legal lifecycle of an invoice lives in the country module; the store only knows "allocated numbers plus a queue".

The lifecycle of three families is proposed and not yet built: a card is taken through the store's terminal, with an unknown answer parking the bill ([ADR-0154](adr/0154-a-card-is-taken-through-the-stores-terminal.md)); a QR payment is confirmed by its gateway through the cloud, and by hand when it cannot be ([ADR-0155](adr/0155-a-qr-payment-is-confirmed-by-its-gateway-through-the-cloud.md)); and an e-invoice is issued by the store from its range and submitted by the cloud ([ADR-0156](adr/0156-a-store-issues-its-e-invoice-and-the-cloud-submits-it.md)).

Which process runs an adapter, and how a tenant chooses a vendor, is [ADR-0153](adr/0153-a-vendor-is-a-provider-the-cloud-chooses.md): a device on the store's network is driven by the edge, a service on the internet by the cloud, and either is picked by a *connection* the tenant configures in the console from a settings schema the adapter itself describes. A vendor's credentials stay in the cloud. Each adapter describes itself with a `ProviderDescriptor` from `crates/pos-providers` — an id shaped `<family>.<vendor>`, the countries it serves, and a typed settings schema — and each binary lists the descriptors it was built with in one `Registry` (the cloud's is `crates/pos-cloud/src/providers.rs`). The console reads the cloud's through `GET /admin/integrations/providers`. The couriers and the ERP are listed today. A tenant's *connections* are stored by the cloud (`/admin/integrations/connections`, behind `console.integrations.manage`): a provider id, a scope (tenant, brand or store), settings checked against the provider's schema, and secret fields sealed with XChaCha20-Poly1305 under the tenant's own key (below) — bound to their tenant, connection and field, and never returned by any read. **Tenant keys** ([ADR-0217](adr/0217-secrets-are-sealed-under-versioned-tenant-keys.md)): each tenant has a random 32-byte key, generated on its first secret and kept only wrapped by the environment key (`KeyKeeper`, §5) in `tenant_keys` (store-postgres migration 0100: tenant, `key_version` from 1, the wrapping `keeper_version`, the wrapped bytes; row-level security on and nothing granted to `app_tenant`). A value sealed under version `n` is stored as `t<n>.` and the hex of its nonce and ciphertext; a value with no prefix is the format before tenant keys, version 0, sealed directly under `integration_secret`, and keeps opening while that key is configured. A request reads the tenant's versions (at most 16), unwraps them, seals under the newest and opens under any (`pos_cloud::keys::Keys`, `TenantSealer`); a key or a value is never logged, only versions. Until a production keeper exists the cloud runs the file keeper over `integration_secret`. **Rotation never stops the service** (decision 3): `pos-cloud keys rotate --tenant <id>` makes the tenant's next version, which new seals use at once while the older keep opening; `pos-cloud keys rotate --environment` re-wraps every tenant key under the keeper's newest environment-key version (a keeper that holds several). A **re-seal pass** runs every 15 minutes over every tenant (`pos-cloud keys reseal --tenant <id>` runs it at once for one): it opens each connection's and endpoint's value under an older version or from before tenant keys and seals it again under the newest, at most 200 values a tenant and 2,000 a run, writing each record only at the version it read so a person's edit wins, and retires the older versions once nothing is sealed under them. Each tenant it changes is audited as `tenant_key.reseal` with its counts. **Erasure by key** (decision 4): `pos-cloud keys erase --tenant <id> --confirm <id> --approval <reference>` needs the tenant id typed twice and the owner's approval reference, moves any value from before tenant keys under the tenant's key first (and erases nothing if one cannot be moved), deletes every version of the tenant's key, and audits `tenant_key.erase` with the count and the reference. It cannot be undone; a vendor credential that may have leaked is also replaced at the vendor. Rotations are audited as `tenant_key.rotate` and `tenant_key.rewrap`, by version only. A scope may hold one enabled e-invoice or ERP connection at most; the other families are plural. `PUT /admin/config/integrations` resolves which connections serve one store — its own, then its brand's, then the tenant's, with only the most specific e-invoice or ERP connection kept — and publishes them as the store's `integrations` node (`pos_proto::integrations`). The node carries each connection's id, family, provider and name, plus the non-secret settings of a driver the store runs itself (a card terminal), and nothing else: no secret, and no setting of a family the cloud drives. An absent node means every family runs its offline path. The edge applies it into its session and lists it at `GET /api/integrations`. **Order connectors** ([ADR-0083](adr/0083-integration-doctrine.md) decision 3, roadmap-v3 B9.3): a delivery vendor sends its own webhook to `POST /connectors/{tenant_id}/{connection_id}/orders` (`crates/pos-cloud/src/connectors/`). The vendor holds no API key; its signature, under the `webhook_secret` sealed on the tenant's connection, is its credential. The connection must be enabled, scoped to one store, and of a provider this cloud has a connector for (`OrderConnector`: how the vendor signs, and how its order reads); anything else, unknown or another tenant's, is one `404`. Each connection may send 20 a second, and a body is at most 64 KiB. A bad signature is `401`; a body that is not the vendor's order `400`. The vendor's item codes go through the connection's `item_map` setting (one `code=menu_item_id` per line), and one unmapped item refuses the whole order with `422`, naming it. The order is submitted to the same relay `/v1/orders` uses, on `SALES_CHANNEL_DELIVERY`, with no quoted price (the store prices it), and its idempotency key is the vendor's reference prefixed by the connection id, so a vendor's retry finds its order and two vendors never collide. The order carries no vendor id and no delivery address, and nothing answers the vendor back (accept, reject, ready, busy): those change the intake port and carry personal data, and wait on their own decision. The only connector is the sandbox `delivery.demo`, a made-up format signed `x-demo-signature: sha256=<hex HMAC-SHA256 of the body>`, which proves the framework end to end with fake data; no other connection calls a vendor yet. **A store answers its vendor through the cloud** ([ADR-0215](adr/0215-a-delivery-order-names-its-vendor.md) decision 4): `POST /sync/stores/{store_id}/delivery/answers`, with a credential bound to the store that holds `relay_orders`, names the vendor (`vendor_id`, the connection's id), the order's `external_reference` as the store received it (absent only for busy) and one generic answer: `DELIVERY_ANSWER_ACCEPT` with `prep_minutes` 1 to 240, `_REJECT` with a `reason_code_id`, `_READY`, or `_BUSY` with `prep_minutes` 0 to 240. A malformed answer is `400` on its field; a vendor that is not an enabled connection serving this store, with a connector and an `answer_url` setting, is `404`. The connector builds the vendor's request (`OrderConnector::answer`, pure; the demo vendor's is `{"order_ref", "answer", "prep_minutes", "reason"}` signed as its webhooks are) under the vendor's own reference (the connection prefix stripped) and the connection's sealed `webhook_secret`, and the cloud posts it to `answer_url` over the outbound client behind the webhook guard within five seconds, with an `Idempotency-Key` that is the same for the same answer about the same order. It answers `204` when the vendor took it and `503` when the vendor refused, could not be reached or did not answer in time; the log names the connection, the answer and the outcome, nothing personal. A connector whose vendor takes no answers says so (`409`).

### 6.2 Public API and webhooks (outbound)

Served at `api.<domain>`, versioned `/v1`, documented by generated OpenAPI.

- **Webhooks** are a **cursor over the event log**, not a separate queue. A dead endpoint means its cursor falls behind; nothing accumulates and nothing pushes back into ingestion. Delivery is at-least-once, signed with HMAC-SHA256 plus a timestamp, keyed by ULID for idempotency, retried with backoff into a dead-letter list, isolated per endpoint (bounded concurrency, circuit breaker, auto-disable after 24 hours of failure). Order is explicitly **not** guaranteed; receivers sort by ULID. An endpoint may name the event types it is sent (`event_types`, migration 0097, roadmap-v3 B6.2); the cursor then moves past every other event without sending it, and naming none sends every event, as before.
- **Cursor feed** `GET /v1/events?page_size=&page_token=` for consumers that prefer to pull and replay.
- **Writes:** menu and sold-out changes (which flow straight into the config tree and reach every store in under a second), and `POST /v1/orders` for external sales channels, which reuses the same `OrderIn` port as marketplaces.
- **SSRF protection is mandatory:** HTTPS only, private and loopback ranges blocked, resolved IP pinned, redirects not followed.

### 6.3 The gateway (a store's external calls)

A store never calls the internet; an external call goes through the cloud ([ADR-0198](adr/0198-a-store-reaches-the-internet-only-through-the-cloud.md)). **Built so far: the endpoint registry.** A tenant declares *gateway endpoints* at `/admin/integrations/gateway-endpoints` (reads behind `console.data.read`, writes behind `console.integrations.manage`, audited as `integrations.gateway_endpoint.*`): a display name, an `https` URL, `GATEWAY_METHOD_GET` or `_POST`, the request and response fields by name with a kind each (`GATEWAY_FIELD_KIND_STRING`, `_INTEGER`, `_BOOLEAN`; at most 32 a side, named in lower case), `deadline_ms` (3000 when absent, 100 to 10000), `idempotent`, `enabled`, and secret headers. The URL is vetted by the webhook guard (`webhook::ssrf::vet`) before anything is stored and is refused on `url` when it is not `https`, carries credentials, or resolves to a non-public address. A secret header's name is a header token the gateway does not set itself (not `host`, the framing headers or `idempotency-key`), its value one line; at most eight, sealed under the tenant's key exactly as a connection's secrets, bound to the tenant, the endpoint and `header:<name>`, and never returned: a read names them in `secret_headers_set`, and the audit keeps the URL without its query. Records live as `jsonb` in `gateway_endpoints` (migration 0098), tenant-scoped under RLS. The console's **Gateway endpoints** screen (`dashboard/src/screens/GatewayEndpoints.tsx`, in the access group beside Integrations, for the roles that manage integrations) lists them, creates, edits at the version read and deletes them; a request's and an answer's fields are typed one per line as `name text|number|yes-no [required]` and secret headers as `Name: value`, and a saved header is named, never shown, and can be removed. No field can be marked personal until ADR-0198 decision 9's processor declaration exists. **And the call.** A store calls `POST /sync/stores/{store_id}/gateway/calls` with a credential bound to the store that holds the `call_gateway` scope (every box's device credential carries it, and a store API key does when an admin grants it), naming the endpoint, its `idempotency_key` for the act (1 to 64 letters, digits, `-` and `_`) and its `values` by field name. The cloud refuses before calling anything: an endpoint that is not the tenant's or not enabled (`404`), a value undeclared, missing or of the wrong kind (`400` on `values.<field>`), a key already used for another endpoint in 24 hours (`409`), more than ten calls a second from the store or fifty to the endpoint (`429`, `Retry-After`), and an endpoint whose breaker is open after five failures in a row (`429`, a minute). Otherwise it opens the secret headers, builds the request (a `GET`'s values as its query, a `POST`'s as a JSON object, with `Idempotency-Key`), and sends it over the outbound HTTPS client (`outbound.rs`), which vets the URL again before every attempt, dials only the vetted addresses, follows no redirect and reads at most 256 KiB, all within the endpoint's deadline; an idempotent endpoint is retried at most twice on a transport failure or a `5xx`. It answers `200` with `GATEWAY_OUTCOME_ANSWERED` and the declared response fields (anything else the target answers is dropped), or `GATEWAY_OUTCOME_REFUSED` with `GATEWAY_REFUSAL_TIMEOUT`, `_UNREACHABLE`, `_TARGET_ERROR` (with the target's status) or `_MALFORMED_ANSWER`. An answer the target gave is kept for the key 24 hours in `gateway_calls` (migration 0099) and replayed for a repeat; a call that never reached it, or timed out, is not, so a retry calls again. The log names the call's id, the endpoint, the outcome, the status and the time taken, never a value, a header or a body. **The till connects to its edge alone**: every UI asset the edge serves carries `Content-Security-Policy: connect-src 'self' ws://<host> wss://<host>`, the host being the request's own `Host` when it is a plain `host[:port]` and `'self'` alone otherwise, so a page the edge served can reach no other origin, and an external call can only go through the edge to the cloud. The till served by its edge makes only root-relative requests, opens `/ws` on the same origin and loads its rules module and lazy chunks from `/assets`; a shell served from elsewhere addresses the edge cross-origin under ADR-0111 and is not covered by a header the edge sets on its own pages. The policy names `connect-src` only. Every browser replay fails on a connection the policy refused. **The edge's half** ([ADR-0214](adr/0214-a-tills-external-lookup-is-one-catalogue-act.md)): the act `integrations.lookup.run` (`ACTION_EFFECT_EXTERNAL`, rare; the only act that goes out through the gateway) calls `POST /api/gateway/calls` with the endpoint's id, its `values` and, on a retry of the same act, the till's own `idempotency_key`. The route needs the permission `integrations.lookup.run`, which no role holds until a tenant grants it on the console. The edge names a key (a ULID) when the till sends none, refuses a malformed id or key or more than 32 values before anything leaves the box, and posts the call to the cloud over the box's device credential (`server/gateway_link.rs`, `cloud_http/gateway.rs`), waiting eleven seconds: the longest deadline plus one. It answers `200` with the call's id, the key and the declared `result`, or a refusal the till translates: `GATEWAY_OFFLINE` (`503`, at once, when the box has no link to its cloud or the cloud cannot be reached or does not take the call), `GATEWAY_TIMEOUT` (`504`), `GATEWAY_REFUSED` (`502`, the target's own error, an answer without the declared fields, or a target the cloud could not reach) and `GATEWAY_BUSY` (`429`); the cloud's `400` and `409` come back as `INVALID_ARGUMENT` and its `404` as `UNKNOWN_GATEWAY_ENDPOINT`. A lookup writes no event, and its log line names the endpoint, the outcome and the cloud's status, never a value or a result. **The till's half** (`ui/src/state/lookup.ts`, `ui/src/package/lookup.tsx`): a package screen holds `lookup_field`s, each a box for one request field (`field`, `label_key`, and `kind` `text` or `number`, a whole number sent as one), an `action_button` binding `integrations.lookup.run` with the endpoint's id fixed, and `lookup_result`s, each drawing one response field of the answer under its label (`field`, `label_key`). A `lookup_field` naming `order_id` or `table_id` draws nothing and sends the screen's own id. The package carries the field names and their labels; the edge holds no endpoint declarations. The button is enabled when the person holds the permission without an approver; a tap paints the answer pending, and the request leaves after that frame (ADR-0196). The till sends its own key and repeats it only for a retry after `GATEWAY_TIMEOUT` with nothing typed since. The answer is held in the till's memory while the screen is shown and dropped with what was typed when it goes; it is never logged, stored or put in an event, and an answer that arrives after the screen has gone is dropped. A refusal is said under the button in the till's words for its token (`GATEWAY_OFFLINE`, `_TIMEOUT`, `_REFUSED`, `_BUSY`, `UNKNOWN_GATEWAY_ENDPOINT`). A version naming either component or the act is floored at the release that introduced them. **A lookup in a flow** (ADR-0214 decision 5, `ui/src/state/flows.ts`): an answer completes, for the table or order the screen is for, every step of its flows that runs `integrations.lookup.run`, so a step waiting on one is no longer held back. When the lookup is refused `GATEWAY_OFFLINE`, each such step with an `offline` branch is passed instead: one with `skip_note_key` says its note under the button in place of the refusal, and one with `step_id` opens that step's screen when it shows one. Any other refusal passes nothing. The till keeps which steps were passed in memory only; the edge enforces none of them, since a lookup step has no `done_when`.

## 7. Multi-country: cells

**Latency is not the reason to split.** Because the cloud is off the sales path, a store in Tokyo served by a cloud in Vietnam performs identically to one next door: only dashboards feel the extra round trip.

**Law is the reason to split.** Data-protection regimes constrain where residents' personal data lives. So each country gets a **cell**: an independent deployment (VPS, database, broker, storage, domain) with its own country module. Cells do not know about each other. One cell failing has no effect on another, and personal data never crosses a border.

Creating a cell is not new engineering — it is the existing fork-and-deploy flow pointed at a new environment: add a GitHub Environment, add a VPS, run the workflow.

**Naming rule: redirect, never proxy.** A cell is named by a **cell id** (`vn1`, `jp1`), not a country ([ADR-0179](adr/0179-cells-the-directory-and-the-front-door.md), which supersedes [ADR-0011](adr/0011-country-in-hostname.md)'s country label and its 301 in part). Every cell holds the same minisign-signed, PII-free **directory** (`tenant_slug → cell_id`, `country → default cell` with a `*` fallback, `cell_id → base URL`), so any cell can answer "where is this tenant" and **redirect** there: `302` for a browser, `307` or `308` for an API, never `301`, and never a proxy. A device resolves its cell once, from its activation-code prefix or `/.well-known/pos-cell`, and stores its `cloud_url`. A tenant's home cell follows its country, never the visitor's location; GeoDNS, where a fork adds it, only shortens the path.

**Built, levels 0 and 1.** Today one deployment is the only cell, which is level 0 of ADR-0179: with no directory configured, the cell answers for itself. An optional `[cell]` section in `cloud.toml` names the cell (id, country alias, home country, base URL, the country it runs in) and is checked at boot; without one the deployment is the cell `default`. The boot logs which cell it is, `GET /admin/cell` reads it and the console's Fleet screen shows it, each warning when the servers run outside the home country. A cell given a directory file and the directory key's public half (`[cell] directory_path` and `directory_public_key`) checks the file's minisign signature, its content and its version at boot and every five minutes; a file that fails is refused with its reason on the same screen, and the directory already held is kept. A cell with the key and no accepted directory answers for no tenant rather than for every one. A store whose published country differs from its cell's home country is warned about and never refused: `GET /admin/stores/{store_id}/cell-standing` says so, and a person with `console.stores.manage` answers it with a reason through `POST /admin/stores/{store_id}/cell-acknowledgement`, recorded as the audit action `store.cell_country.acknowledge`. That entry is the answer, and it stands only while the store and its cell still have the two countries it named. The console's store hub shows the warning and takes the answer, and the store settings form's country hint warns before a country that is not the cell's is published. A vendor connection records the country its vendor processes data in (`processing_country`), and its read says when that is not the cell's home country (`processing_outside_cell`); a difference is never refused. The console's Integrations screen takes it, shows it in the table and flags another country than the cell's. Each cell's non-secret deploy values live in `deploy/cells/<cell>.env`; `bootstrap.sh` writes the `[cell]` section from them once, and every off-box backup records the country it rests in (`BACKUP_COUNTRY`), warning when that is not the cell's home country. `GET /.well-known/pos-cell` is public and answers from memory: this cell's id, base URL, alias, home country and directory version, and, for `?tenant=<slug>`, the tenant's home cell, its base URL and whether it is this one (`404` when the directory does not list the tenant, `503` while a cell configured for a directory holds none). It never redirects. The front door redirects a request for a tenant homed in another cell (its hostname's first label is the tenant slug) to that cell's base URL with the same path and query: `302` for a browser navigation, `307` for anything else, never `301` and never a proxy, with a host-only `cell_id` cookie naming the home cell. A request to the cell's own host, an unlisted tenant, a tenant homed here, and every request to a single cell pass through untouched. An activation code may name the cell that issued it as a prefix, `VN1-XXXX-XXXX-XXXX` ([ADR-0181](adr/0181-the-activation-code-names-its-cell.md), C4): `pos-core` reads the code's twelve symbols from the end and the cell id before them, case-insensitively and never folded, and a code is redeemed by its twelve symbols alone, so a prefix is a routing hint and never part of the credential. A code with no prefix reads as it always has. A cloud with a `[cell]` section issues every code with its cell id as the prefix (`POST /admin/activation-codes`); a single cell issues none. A refused code whose prefix names another cell gets the same `403` plus the directory's answer: a `code` detail `OTHER_CELL` with that cell's base URL in the message, or `UNKNOWN_CELL`, and a code issued here redeems whatever prefix it is typed with. The store's `/setup` field keeps a prefix as typed and the edge presents the code to its configured cloud as typed; it does not yet resolve the prefix to another cell itself. The signed "cell moved" notice (C9) waits on its own slice. An HQ that names other cells in an optional `[federation]` section reads their stores' daily rollups through each cell's public `/v1` API with a `read_rollups` key that cell issued, and `GET /admin/hq/rollups` answers them per store, shown on the Fleet screen as **HQ: other cells** with each store's days and events or why it was not read: only aggregates cross a cell boundary, never personal data, and the address is always the signed directory's, with 10 seconds and 1 MiB per store, no redirect followed and 30 seconds for the whole read. A path-based scheme (`/jp`) stays rejected: it forces every Japanese request to terminate TLS in another country — destroying the legal reason for cells — adds a round trip, creates a global single point of failure, and breaks session isolation because browsers do not treat paths as security boundaries.

**Four disciplines are paid for on day one** even with a single country, because they cannot be retrofitted cheaply: internationalisation of every string; locale packs as first-class configuration (currency, timezone, date and number formats, receipt templates); host parsing that already understands a hostname label (now a cell id); and a timezone on every store.

## 8. Operations

**Health.** `/health` means the process is alive; `/ready` means database, broker, and storage are reachable and no migration is running. Deployment waits on `/ready`.

**Resilience at the edge.** All calls to the cloud use retry with exponential backoff and jitter, and **never block a sale**. Unsent events wait in the outbox. This is why the cloud needs no automatic failover.

**Backups.** Four things matter, and they are not equal:

| Data | Loss impact | Where it goes |
|---|---|---|
| Cloud PostgreSQL (+ continuous WAL archiving → RPO in minutes) | Chain-wide data loss | Garage, then replicated off-box |
| Per-store SQLite replicas | That store loses unsynced data | Garage |
| OTA artifacts | Lose fast rollback | Garage |
| **Signing keys and infrastructure config** | Lose the ability to update the fleet | **Never in the cloud** — offline USB plus sealed paper, in two locations |

A weekly job restores a random store backup *and* the cloud database to a scratch instance and verifies totals. A backup never restored is not a backup.

**Cloud can be rebuilt from the stores.** Each store keeps an event until it is synced **and** older than the store's retention: 90 days by default, set per store in the cloud ([ADR-0145](adr/0145-the-edge-keeps-events-until-synced-and-n-days-old.md)). It never deletes an event the link has not acknowledged, or one an order still open depends on. So a cloud data loss within that window is recoverable from the stores. **What is missing** is the other half: an internal command that resets a cursor and asks the edges to replay from a given ULID. The data is there, but nothing yet asks for it.

**Resource limits are mandatory configuration**, not good intentions:

| Risk | Control |
|---|---|
| JetStream growth while a store is offline | `max_age` and `max_bytes` per stream, alert at 80% |
| Docker logs (unbounded by default) | `max-size` and `max-file` in compose |
| Old images after each deploy | prune step in the deploy job |
| Backup generations | retention policy |
| SQLite WAL growth if replication stalls | watchdog on WAL size |
| PostgreSQL growth | retention job plus partition archiving |
| In-process memory | bounded channels and caches (see AGENTS.md) |
| Metric cardinality | labels limited to store, adapter, event type, status |

**Hardware baseline.** Store server: x86-64, 4 GB RAM, SSD/NVMe (never an SD card), Windows 10+ or Linux. Cloud: 4 cores, 24 GB RAM, **local NVMe** — `fsync` is the first bottleneck in the whole system, and network block storage multiplies it by ten. Printers that open a cash drawer must be USB-attached, or all POS devices must sit on a separate VLAN, because port 9100 has no authentication.

**Menu images** are converted server-side to WebP in two sizes — a thumbnail (≤30 KB) for lists and QR menus, and a detail image (≤150 KB) — then synced to stores like any other configuration, so they display offline.

|---|---|---|---|
| Rust | C-level performance, memory safety, single static binary, good FFI for terminal SDKs | Go (weaker FFI, larger binaries), Node/JVM (memory, packaging) | edge <1% CPU |

| PostgreSQL | Partitioning, RLS, JSONB in one node; strong backup ecosystem | One database per store (operationally explosive) | 2,000–5,000 inserts/s vs ~222/s peak |
| Rollup tables | Dashboards always read small aggregates | ClickHouse + CDC (two more systems) | <10 ms queries |
| SolidJS | Fine-grained reactivity, no virtual DOM, small bundle — smooth on cheap tablets | React (heavier on weak devices), Leptos (younger ecosystem; decision recorded and closed) | ~7 KB runtime |

| minisign | Simple signing, self-managed keys, free | Commercial code-signing certificates | — |
| ULID | Offline generation, time-sortable, merge-safe | UUIDv4 (unsortable), auto-increment (collides across stores) | — |

## Appendix B — Rejected technologies and the admission rule

**Admission rule.** To add any infrastructure component, answer all four: (1) what does it replace? (2) what number proves it is needed? (3) how much RAM, how many processes, how many failure modes does it add? (4) can it be removed if we are wrong? Fewer than four answers means no.

| Rejected | Reason | Reconsider when |
|---|---|---|
| Valkey / Redis | All five of its jobs are already covered: caching → rollups plus page cache (queries already <10 ms); sessions → signed cookies; queues → JetStream; pub/sub → NATS and WebSocket; rate limiting → in-process counters. Its strength is read-heavy caching across many instances; this workload is *light and write-heavy* (~40 events/s peak). | Multiple cloud instances **and** PostgreSQL CPU-bound on reads |
| HAProxy / Nginx | Only one backend exists; Caddy already provides automatic TLS and will be absorbed into `pos_cloud` | Load balancing several instances (Caddy also does this) |
| Kubernetes / service mesh | Four containers on one host | Not at any foreseeable scale (GKE remains an optional lane) |
| Kafka | JetStream is sufficient and far lighter | — |
| ELK / full log shipping | Errors and metrics are shipped; full logs stay at the store and are pulled on demand | — |
| Patroni / auto-failover | The cloud being down for 30 minutes stops no sales | If the cloud ever enters the sales path |
| ClickHouse | Rollups answer in <10 ms | Large ad-hoc analytics over years of raw events |
| Replacing NATS with PostgreSQL queue + SSE | Feasible and saves one process, but requires 500–1,000 lines of hand-written ack, redelivery, deduplication and backpressure logic — exactly where "orders vanish for no reason" bugs live | Only behind the `MessageLink` port, with a fleet simulator to prove it |

## Appendix C — Dependency inventory and in-house strategy

About 25 named open-source components (200–400 transitive crates). The strategy is to **own the boundaries, not the implementations** — but four items are worth writing ourselves, ranked by benefit per unit of risk:

1. **WAL shipping** (replacing Litestream). Removes the two heaviest copyleft components (Garage/MinIO disappear entirely, because S3 only exists to satisfy Litestream), cuts 300 MB–1 GB of RAM, drops RPO below one second, and lets us compress with a shared dictionary — meaningful on metered mobile links. Blast radius is low: the outbox, not this, is what protects revenue.
2. **Dashboard** (replacing Grafana). Removes the last copyleft dependency, saves 200–400 MB, and reads rollups directly. A bug here produces an ugly chart, nothing more.
3. **Small formats** — ULID, TOTP, minisign verification, SNTP, mDNS. 50–200 lines each; removes dozens of transitive crates. **Write the format, never the cryptographic primitive:** HMAC, SHA-2, Ed25519, Argon2 stay as vetted crates.
4. **Serial port access** via native Win32/termios calls — removes the last weak-copyleft dependency and gives precise control over terminal timeouts.

**Do not write:** NATS (we use under 1% of its capacity — there is no performance to reclaim), tokio and hyper (years of scheduler tuning), SolidJS (already among the fastest), rclone (zero cost as a cron job), and above all **SQLite, PostgreSQL, TLS, and cryptographic primitives** — a category where mistakes do not show up in tests. A wrong cipher still encrypts and decrypts; only the attacker notices the timing leak.

**Counter-intuitive note:** do *not* replace VictoriaMetrics with plain PostgreSQL tables. At ~0.5–1 byte per sample versus 40–60 bytes per row, "simplifying" would burn hundreds of GB per month. Either keep it, or write a proper columnar store (delta-of-delta timestamps, XOR-compressed values, ~500 lines). At 50 stores or fewer, a third option works: sample sparsely (every 60–120 s, ~15 metrics) straight into PostgreSQL — roughly 20–40 MB/day — and skip the monitoring profile entirely.
